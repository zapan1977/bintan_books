# 18장. 최종 종합 프로젝트: 로컬 데이터 플랫폼 구축과 검증

이 장에서는 지금까지 학습한 구성 요소를 하나의 로컬 프로젝트로 연결한다. 빈 작업 디렉터리에서 Docker Compose 환경을 준비하고, MySQL·MongoDB·PostgreSQL에 합성 데이터를 입력한다. Flink CDC와 Kafka를 이용해 변경 이벤트를 전달하고, Canonical Schema로 정규화한 뒤 Iceberg Raw·Clean·Mart 계층에 저장한다. ClickHouse Serving Mart와 Superset Dashboard를 구성하고, Airflow 백필과 장애 복구까지 수행한다.

최종 프로젝트의 목적은 많은 서비스를 실행하는 데 있지 않다. 다음 질문에 답할 수 있는 재현 가능한 환경을 만드는 데 있다.

- 세 원천 데이터베이스의 변경이 실제로 전달되는가?
- INSERT·UPDATE·DELETE가 Raw와 Clean에서 올바르게 표현되는가?
- Iceberg Snapshot과 Time Travel로 이전 상태를 확인할 수 있는가?
- ClickHouse Mart의 수치가 Iceberg와 일치하는가?
- Superset Dashboard가 의도한 Dataset과 필터를 사용하는가?
- Airflow 백필을 다시 실행해도 중복이 발생하지 않는가?
- 장애 후 복구가 서비스 정상뿐 아니라 데이터 정합성까지 회복했는가?

이 장은 독자가 앞 장의 개념과 개별 실습을 완료했다는 전제로 작성한다. 모든 서비스를 한 번에 시작하기보다 작은 범위의 성공을 확인하면서 확장한다.

## 3. Docker Compose 구성

### 3.1 서비스 구성 원칙

전체 Compose 파일은 이미지와 환경에 따라 달라질 수 있으므로, 이 장에서는 서비스별 핵심 설정과 연결 경계를 제시한다. 앞 장에서 이미 검증한 서비스 정의를 재사용하고, 각 서비스의 이름과 내부 포트를 일관되게 유지한다.

| 서비스 그룹 | Compose 이름 예 | 내부 연결 |
|---|---|---|
| Source | mysql·mongodb·postgres | 서비스 이름과 내부 포트 |
| Transport | kafka | kafka:9092 |
| Stream | flink-jobmanager·flink-taskmanager | Flink REST·RPC |
| Catalog | polaris | REST Catalog Endpoint |
| Storage | ozone | S3 호환 Endpoint |
| Batch | spark | Spark Submit·Catalog |
| Serving | clickhouse | HTTP 8123·Native 9000 예시 |
| Orchestration | airflow-* | PostgreSQL Metadata DB |
| Visualization | superset | PostgreSQL Metadata DB·Redis |

### 3.2 기본 네트워크

~~~yaml
networks:
  data-platform:
    driver: bridge

services:
  mysql:
    networks:
      - data-platform

  mongodb:
    networks:
      - data-platform

  postgres:
    networks:
      - data-platform

  kafka:
    networks:
      - data-platform
~~~

Compose 네트워크 안에서는 localhost가 자기 자신인 컨테이너를 의미한다. Superset에서 ClickHouse를 연결할 때 ClickHouse 서비스 이름이 clickhouse라면 localhost가 아닌 clickhouse를 사용한다.

### 3.3 Healthcheck 기준

~~~yaml
services:
  postgres:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres -d ecommerce"]
      interval: 10s
      timeout: 5s
      retries: 5

  clickhouse:
    healthcheck:
      test: ["CMD", "wget", "--spider", "-q", "http://localhost:8123/ping"]
      interval: 10s
      timeout: 5s
      retries: 5
~~~

이미지에 wget이나 curl이 없으면 해당 healthcheck는 실패한다. healthcheck 명령이 이미지에 존재하는지 먼저 확인한다.

### 3.4 단계별 시작

~~~bash
docker compose up -d postgres mysql mongodb
docker compose ps

docker compose up -d kafka
docker compose ps

docker compose up -d polaris ozone
docker compose ps

docker compose ps

docker compose up -d clickhouse
docker compose ps
~~~

실제 서비스 이름은 사용하는 Compose 파일과 일치시킨다. 각 단계 사이에 로그와 접속을 확인한다.

## 4. 세 Source DB에 합성 데이터 적재

### 4.1 공통 데이터 모델

세 데이터베이스에 같은 의미의 고객 데이터를 넣되, 소스별 표현 차이를 의도적으로 남긴다.

| 의미 | MySQL | PostgreSQL | MongoDB |
|---|---|---|---|
| 식별자 | id BIGINT | id BIGINT | id 또는 _id |
| 이메일 | email | email | email |
| 생성 시각 | created_at DATETIME | created_at TIMESTAMP | created_at BSON Date |
| 변경 시각 | updated_at DATETIME | updated_at TIMESTAMP | updated_at BSON Date |
| 상태 | status VARCHAR | status TEXT | status String |

### 4.2 MySQL 입력

~~~bash
docker compose exec mysql mysql \
  -u root \
  -pchange-this-mysql-password \
  -e "CREATE DATABASE IF NOT EXISTS ecommerce;"
~~~

~~~sql
CREATE TABLE ecommerce.customers (
    id BIGINT PRIMARY KEY,
    email VARCHAR(255) NOT NULL,
    status VARCHAR(32) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    updated_at DATETIME(6) NOT NULL
);

INSERT INTO ecommerce.customers
    (id, email, status, created_at, updated_at)
VALUES
    (1, 'alice@example.com', 'ACTIVE', CURRENT_TIMESTAMP(6), CURRENT_TIMESTAMP(6)),
    (2, 'bob@example.com', 'ACTIVE', CURRENT_TIMESTAMP(6), CURRENT_TIMESTAMP(6));
~~~

CDC를 사용하려면 MySQL Binary Log, 사용자 권한, Server ID 등 Connector 요구사항을 별도로 설정한다.

### 4.3 PostgreSQL 입력

~~~bash
docker compose exec postgres psql \
  -U postgres \
  -d ecommerce \
  -c "SELECT version();"
~~~

~~~sql
CREATE TABLE public.customers (
    id BIGINT PRIMARY KEY,
    email TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TIMESTAMP(6) NOT NULL,
    updated_at TIMESTAMP(6) NOT NULL
);

INSERT INTO public.customers
    (id, email, status, created_at, updated_at)
VALUES
    (3, 'charlie@example.com', 'ACTIVE', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP),
    (4, 'diana@example.com', 'ACTIVE', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);
~~~

PostgreSQL CDC를 사용하려면 Logical Replication, Publication, Replication Slot과 Connector 권한을 준비한다.

### 4.4 MongoDB 입력

~~~bash
docker compose exec mongodb mongosh \
  --username cdc_user \
  --password change-this-mongodb-password \
  --authenticationDatabase admin \
  --eval "use ecommerce; db.customers.insertOne({id: 5, email: 'eve@example.com', status: 'ACTIVE', created_at: new Date(), updated_at: new Date()})"
~~~

MongoDB의 Database·Collection·사용자·Replica Set·Change Stream 조건은 MongoDB CDC Connector의 요구사항을 따른다.

### 4.5 Source 입력 검증

~~~sql
-- MySQL
SELECT COUNT(*) AS row_count, MAX(updated_at) AS last_updated
FROM ecommerce.customers;

-- PostgreSQL
SELECT COUNT(*) AS row_count, MAX(updated_at) AS last_updated
FROM public.customers;
~~~

~~~javascript
use ecommerce
db.customers.countDocuments()
db.customers.find().sort({id: 1})
~~~

Source 입력 결과와 시각을 실습 기록에 남긴다. 이후 단계에서 기대값으로 사용한다.

## 5. INSERT·UPDATE·DELETE CDC 검증

### 5.1 INSERT 검증

MySQL·MongoDB·PostgreSQL 중 하나에 새 고객을 입력한다. 먼저 Source에서 레코드를 확인하고, 그 다음 Kafka 이벤트와 Flink 처리 결과를 순서대로 확인한다.

~~~sql
INSERT INTO ecommerce.customers
    (id, email, status, created_at, updated_at)
VALUES
    (101, 'insert@example.com', 'ACTIVE', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);
~~~

기대 흐름은 다음과 같다.

~~~mermaid
sequenceDiagram
    participant S as Source DB
    participant C as CDC Connector
    participant K as Kafka
    participant F as Flink
    participant I as Iceberg
    S->>C: INSERT commit
    C->>K: CDC event
    K->>F: consume event
    F->>I: write Raw event
~~~

### 5.2 UPDATE 검증

~~~sql
UPDATE ecommerce.customers
SET
    status = 'SUSPENDED',
    updated_at = CURRENT_TIMESTAMP
WHERE id = 101;
~~~

UPDATE 이벤트가 Raw에 append되는지, Clean에서 최신 상태로 반영되는지 확인한다. Raw와 Clean의 Row Count가 동일해야 한다고 가정하지 않는다. Raw는 여러 변경 이벤트를 보존하고 Clean은 키별 현재 상태를 보존할 수 있기 때문이다.

### 5.3 DELETE 검증

~~~sql
DELETE FROM ecommerce.customers
WHERE id = 101;
~~~

DELETE 이벤트가 무시되면 Clean과 Mart에 삭제된 고객이 계속 남는다. Raw에는 삭제 이벤트와 키를 보존하고, Clean에서는 물리 삭제·삭제 플래그·유효 기간 중 어떤 정책을 사용할지 정한다.

### 5.4 CDC 검증표

| 작업 | Source | Kafka | Raw | Clean | Mart |
|---|---|---|---|---|---|
| INSERT | 새 행 생성 | INSERT 이벤트 | 이벤트 추가 | 행 생성 | 집계 반영 |
| UPDATE | 행 변경 | UPDATE 이벤트 | 변경 이력 추가 | 최신 상태 반영 | 집계 갱신 |
| DELETE | 행 삭제 | DELETE 이벤트 | 삭제 이벤트 추가 | 삭제 정책 적용 | 집계 제외 또는 감소 |

실제 CDC Connector가 UPDATE를 before·after 두 행으로 내보내는지, RowKind로 표현하는지는 Connector 문서와 실행 결과를 기준으로 한다.

## 6. Kafka 이벤트 확인

### 6.1 Topic 확인

~~~bash
docker compose exec kafka kafka-topics.sh \
  --bootstrap-server kafka:9092 \
  --list
~~~

Topic 이름은 Connector와 Flink Job 설정에 따라 달라질 수 있다. Source별 Topic과 통합 Topic을 구분해 기록한다.

### 6.2 이벤트 소비

~~~bash
docker compose exec kafka kafka-console-consumer.sh \
  --bootstrap-server kafka:9092 \
  --topic cdc.customers \
  --from-beginning \
  --max-messages 10
~~~

이 명령은 교육용 확인 방법이다. 이미 다른 Consumer가 읽었다고 이벤트가 사라지는 것은 Consumer Group 설정과 Offset 정책에 따라 다르다. 운영에서는 테스트 Group을 별도로 사용한다.

### 6.3 이벤트 확인 항목

- Source 식별자가 포함되어 있는가?
- INSERT·UPDATE·DELETE가 구분되는가?
- 키가 보존되는가?
- Event time과 Ingest time이 존재하는가?
- Source position이나 Event ID가 중복 제거에 사용할 수 있는가?
- 개인정보가 로그에 평문으로 노출되지 않는가?

## 7. Flink CDC와 Iceberg Raw 실행

### 7.1 Flink Job 제출

~~~bash
docker compose exec flink-jobmanager flink run \
  -d \
  /opt/flink/jobs/multi-source-cdc-job.jar
~~~

Flink CDC Job JAR의 경로와 실행 인자는 실제 이미지와 프로젝트 구성에 맞게 변경한다. 장시간 실행되는 CDC Job을 Airflow의 주기 DAG에서 매번 새로 제출하지 않도록 Job ID와 실행 상태를 관리한다.

### 7.2 Flink 상태 확인

~~~bash
curl http://localhost:8081/jobs
curl http://localhost:8081/jobs/overview
~~~

Flink REST API의 호스트 포트는 Compose Port Mapping에 따라 달라진다. Job이 RUNNING이어도 Checkpoint와 Sink Commit이 정상이라는 뜻은 아니므로 Flink UI와 로그를 함께 확인한다.

### 7.3 Iceberg Raw 확인

Raw 테이블의 실제 조회 경로는 Catalog와 실행 엔진에 따라 다르다. 개념적으로 다음을 확인한다.

~~~sql
SELECT
    source_db,
    operation,
    COUNT(*) AS event_count,
    MAX(event_time) AS last_event_time
FROM lakehouse.raw.customers_cdc
GROUP BY source_db, operation;
~~~

INSERT·UPDATE·DELETE의 이벤트 수가 Source에서 수행한 테스트와 맞는지 확인한다. UPDATE와 DELETE가 Raw에서 보이지 않으면 Flink Source·Sink의 Changelog 처리 방식을 먼저 점검한다.

## 8. Iceberg Clean·Mart와 Time Travel

### 8.1 Clean 생성

Clean은 Raw 이벤트를 키와 이벤트 순서 기준으로 정제한다. 구현 방식은 Spark SQL, Flink SQL, Trino SQL 중 선택할 수 있으나, 여러 엔진의 문법을 섞어 하나의 실행 예제처럼 제시하지 않는다.

~~~sql
MERGE INTO lakehouse.clean.customers AS target
USING lakehouse.raw.customers_cdc AS source
ON target.customer_id = source.customer_id
WHEN MATCHED AND source.operation = 'DELETE' THEN DELETE
WHEN MATCHED AND source.operation IN ('UPDATE', 'INSERT') THEN UPDATE SET
    email = source.email,
    status = source.status,
    updated_time = source.event_time
WHEN NOT MATCHED AND source.operation <> 'DELETE' THEN INSERT (
    customer_id,
    email,
    status,
    created_time,
    updated_time
) VALUES (
    source.customer_id,
    source.email,
    source.status,
    source.created_time,
    source.event_time
);
~~~

[검토 필요: 위 MERGE 문법과 CDC DELETE 처리는 선택한 실행 엔진과 Iceberg Runtime에서 검증해야 합니다. 같은 키에 여러 이벤트가 있는 경우 먼저 최신 이벤트를 선택하는 전처리 단계가 필요할 수 있습니다.]

### 8.2 Mart 집계

~~~sql
CREATE TABLE IF NOT EXISTS lakehouse.mart.customers_by_source
USING iceberg
AS
SELECT
    source_db,
    COUNT(*) AS total_customers,
    SUM(CASE WHEN status = 'ACTIVE' THEN 1 ELSE 0 END) AS active_customers,
    CURRENT_TIMESTAMP AS last_updated
FROM lakehouse.clean.customers
GROUP BY source_db;
~~~

Mart의 재실행 정책을 정한다. 기존 집계를 계속 INSERT하면 중복 Snapshot 또는 중복 행이 생길 수 있으므로, 대상 파티션 교체·MERGE·테이블 교체 중 하나를 선택한다.

### 8.3 Time Travel

Iceberg Time Travel은 과거 Snapshot 또는 시각을 기준으로 테이블 상태를 조회하는 기능이다. 조사 자료는 Snapshot ID와 timestamp 기반 조회 예시를 제시한다.

~~~sql
-- Snapshot 목록 확인
SELECT snapshot_id, committed_at, operation
FROM lakehouse.clean.customers.snapshots
ORDER BY committed_at DESC;

-- 시각 기반 조회의 개념적 예시
SELECT COUNT(*)
FROM lakehouse.clean.customers
FOR SYSTEM_TIME AS OF TIMESTAMP '2026-08-30 09:00:00';
~~~

실제 Time Travel 문법은 Spark·Trino·Flink와 Iceberg 연동 방식에 따라 다르다. 위 SQL을 모든 엔진에서 동일하게 실행할 수 있다고 가정하지 않는다.

[검토 필요: Apache Iceberg 1.11.0 기준 Spark·Trino·Flink별 Time Travel 문법, Snapshot metadata table 이름과 시간대 처리 방식을 확정해야 합니다.]

### 8.4 Time Travel 검증 시나리오

1. Snapshot A의 Row Count를 기록한다.
2. UPDATE 또는 DELETE를 수행한다.
3. Snapshot B가 생성되었는지 확인한다.
4. 현재 테이블에서 변경 결과를 확인한다.
5. Snapshot A를 기준으로 이전 상태를 조회한다.
6. 현재 상태와 이전 상태의 차이를 기록한다.

Time Travel은 백업 자체가 아니다. Snapshot과 참조 파일의 보존 기간이 지나면 과거 상태를 조회하지 못할 수 있다.

## 10. Airflow 백필과 멱등성 검증

### 10.1 백필 실행 준비

백필 전에 다음을 기록한다.

- 대상 논리 날짜 또는 파티션
- Source 데이터의 존재 여부
- Raw Snapshot ID
- Clean과 Mart의 현재 Row Count·Sum
- ClickHouse의 현재 Row Count·Sum
- 중복 방지 전략
- 복구 시 되돌릴 Snapshot 또는 백업

### 10.2 백필 DAG

~~~python
from datetime import datetime, timezone

from airflow.sdk import dag
from airflow.providers.standard.operators.bash import BashOperator


@dag(
    dag_id="final_project_backfill",
    start_date=datetime(2026, 1, 1, tzinfo=timezone.utc),
    schedule=None,
    catchup=False,
    max_active_runs=1,
)
def final_project_backfill():
    rebuild_clean = BashOperator(
        task_id="rebuild_clean",
        bash_command=(
            "/opt/airflow/scripts/rebuild_clean.sh "
            "--logical-date 2026-08-30"
        ),
    )

    rebuild_mart = BashOperator(
        task_id="rebuild_mart",
        bash_command=(
            "/opt/airflow/scripts/rebuild_mart.sh "
            "--logical-date 2026-08-30"
        ),
    )

    verify = BashOperator(
        task_id="verify_result",
        bash_command=(
            "/opt/airflow/scripts/verify_result.sh "
            "--logical-date 2026-08-30"
        ),
    )

    rebuild_clean >> rebuild_mart >> verify


final_project_backfill()
~~~

실제 날짜를 코드에 고정하지 않고 Airflow의 논리 날짜를 전달하려면 현재 Airflow 버전의 Template Context 사용법으로 변경한다.

### 10.3 멱등성 실험

1. 백필 전 Clean·Mart·ClickHouse의 기준값을 기록한다.
2. 동일 논리 날짜를 한 번 실행한다.
3. Row Count·Sum·Freshness를 기록한다.
4. 같은 논리 날짜를 다시 실행한다.
5. 두 실행의 최종 결과를 비교한다.

| 항목 | 첫 실행 | 두 번째 실행 | 기대 |
|---|---:|---:|---|
| Clean 행 수 | 기록 | 기록 | 동일 또는 정책에 맞음 |
| Mart 합계 | 기록 | 기록 | 동일 |
| ClickHouse 행 수 | 기록 | 기록 | 의도 없는 증가 없음 |
| 최신 시각 | 기록 | 기록 | 처리 정책에 맞음 |
| Quality Gate | 통과 | 통과 | 동일 |

Airflow의 retries가 멱등성을 만들어 주지 않는다. 외부 SQL과 파일 작업 자체가 재실행에 안전해야 한다.

## 11. 장애 발생 후 재시작과 복구

### 11.1 장애 시나리오

최종 프로젝트에서는 다음 장애를 순서대로 실습한다.

| 시나리오 | 재현 방법 | 확인할 결과 |
|---|---|---|
| PostgreSQL healthcheck 실패 | PostgreSQL 중지 | Superset·Airflow 의존성 |
| Kafka Consumer 중단 | Flink 또는 Consumer 중지 | lag 증가와 재개 |
| Flink Checkpoint 실패 | Checkpoint 저장소 접근 제한 | Job 상태와 복구 |
| ClickHouse 적재 지연 | 적재 Task 중지 | Serving freshness |
| 디스크·로그 증가 | 테스트 로그 생성 | 사용량과 회전 |
| 메모리 부족 | 서비스 동시 실행 증가 | OOM·재시작 |
| Volume 초기화 | 테스트 Volume만 제거 | 전체 재구축 |

### 11.2 복구 전 상태 기록

~~~bash
docker compose ps
docker stats --no-stream
docker system df
docker compose logs --no-color --since 30m > incident-logs/before-recovery.log
~~~

다음 값을 별도 기록한다.

- Kafka Topic과 Consumer Group Offset
- Flink Job ID·Checkpoint·Savepoint
- Iceberg 최신 Snapshot ID
- ClickHouse Row Count·Sum·last_updated
- Airflow DAG Run과 Task 상태
- Superset Dashboard의 마지막 갱신 시각

### 11.3 복구 순서

~~~mermaid
flowchart TD
    A["Stop unsafe writes"] --> B["Preserve logs and state"]
    B --> C["Recover infrastructure"]
    C --> D["Recover processing"]
    D --> E["Validate data"]
    E --> F["Release dashboard"]
~~~

인프라가 복구되었다고 곧바로 Dashboard를 공개하지 않는다. Kafka lag이 감소하고, Flink Checkpoint와 Iceberg Commit이 정상이며, ClickHouse와 Superset의 결과가 검증된 뒤 사용자 화면을 확인한다.

### 11.4 Flink 재시작

Flink Job이 Checkpoint 또는 Savepoint에서 복구 가능한지 확인한다.

~~~bash
flink run \
  -s object-storage-savepoint-path \
  /opt/flink/jobs/multi-source-cdc-job.jar
~~~

실제 Savepoint 경로와 Job 인자는 사용하는 배포 방식에 맞게 변경한다. 기존 Job이 아직 실행 중인지 확인한 뒤 재제출한다.

### 11.5 Iceberg Snapshot 복구

1. 장애 전 마지막 정상 Snapshot을 식별한다.
2. 잘못된 Commit 이후의 Snapshot과 영향을 확인한다.
3. 다른 Reader·Writer가 없는지 확인한다.
4. 엔진의 rollback 절차를 실행한다.
5. Row Count·Schema·대표 쿼리를 확인한다.
6. 복구 검증이 끝난 후에만 downstream 적재를 재개한다.

Snapshot rollback 명령은 17장의 개념적 예시를 사용하되, 실행 엔진에 맞는 공식 문법을 확인한다.

### 11.6 ClickHouse 재적재

ClickHouse 재적재는 대상 기간 또는 Batch ID를 기준으로 수행한다. 전체 테이블을 삭제하고 다시 넣는 방식은 학습용 작은 데이터에만 제한한다.

~~~sql
-- 실제 운영에서는 대상 기간과 키를 명시한다.
ALTER TABLE mart.customers_by_source
DELETE WHERE last_updated < toDateTime('2026-08-30 00:00:00');
~~~

ALTER TABLE DELETE의 비동기 처리와 Merge 상태는 ClickHouse 버전과 테이블 엔진에 따라 확인한다. 실행 직후 Row Count가 최종 상태를 의미한다고 단정하지 않는다.

## 12. 전체 환경 초기화 후 재구축

### 12.1 초기화의 의미

전체 환경 초기화는 컨테이너를 다시 만드는 작업이 아니라 데이터 Volume과 실행 상태를 삭제하고 처음부터 구성하는 작업이다. 이 과정에서 PostgreSQL Metadata, Kafka Log, Iceberg 파일, ClickHouse Part가 사라질 수 있다.

초기화 전 반드시 다음을 확인한다.

- 테스트 환경인가?
- 보존할 백업과 로그가 없는가?
- Compose와 초기화 스크립트가 재현 가능한가?
- 환경 변수와 계정 정보를 다시 만들 수 있는가?
- 삭제할 Volume 이름을 정확히 알고 있는가?

### 12.2 안전한 중지

~~~bash
docker compose ps
docker compose config --volumes
docker compose down
~~~

이 단계는 컨테이너를 중지하는 과정이다. Volume은 기본적으로 남아 있을 수 있다.

### 12.3 명시적 테스트 Volume 삭제

~~~bash
docker volume ls
docker volume rm <explicit_test_volume_name>
~~~

실제 Volume 이름을 확인하지 않은 상태에서 docker compose down -v나 docker system prune --volumes를 실행하지 않는다. 이 책의 실습에서는 테스트 프로젝트의 Volume만 대상으로 한다.

### 12.4 처음부터 재구축

~~~bash
docker compose config
docker compose up -d postgres mysql mongodb
docker compose up -d kafka
docker compose up -d polaris ozone
docker compose up -d flink-jobmanager flink-taskmanager
docker compose up -d clickhouse
docker compose up -d airflow-postgres airflow-scheduler airflow-api-server
docker compose up -d redis superset
~~~

각 단계가 healthy인지 확인한 뒤 2장부터 다시 진행한다. 전체 서비스를 한 번에 시작해 오류가 발생하면 어느 서비스가 원인인지 구분하기 어려워진다.

- [ ] 복구 후 데이터 품질을 재검증했다.

## 15. 핵심 정리

- 최종 프로젝트의 핵심은 서비스 수가 아니라 데이터 흐름과 검증 경계를 재현하는 것이다.
- CDC 이벤트는 Source별 차이를 보존하면서 Canonical Schema로 통일해야 한다.
- Raw·Clean·Mart는 서로 다른 grain과 책임을 가져야 한다.
- INSERT·UPDATE·DELETE는 Source, Kafka, Flink, Iceberg, ClickHouse 각 계층에서 별도로 검증한다.
- Iceberg Time Travel은 이전 Snapshot 조회 수단이며, 백업과 동일하지 않다.
- Airflow 백필 재실행은 멱등성이 보장될 때만 안전하다.
- 장애 복구 후 컨테이너 상태만 확인하지 말고 Row Count·Sum·Freshness·Checksum을 다시 확인한다.
- Volume 초기화는 데이터 삭제이므로 테스트 Volume과 대상 이름을 확인한 뒤 실행한다.
- Windows 11과 Apple Silicon Mac의 이미지 플랫폼·마운트·리소스 차이를 기록해야 한다.

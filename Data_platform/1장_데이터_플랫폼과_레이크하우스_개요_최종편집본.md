# 1장. 데이터 플랫폼과 레이크하우스 개요

## 이 장의 목표

이 장에서는 데이터 플랫폼의 기본 개념과 전체 구성 구조를 이해합니다.

다음 질문에 답할 수 있어야 합니다.

- 데이터 플랫폼은 어떤 문제를 해결하는가?
- 데이터 웨어하우스, 데이터 레이크, 레이크하우스는 어떻게 다른가?
- OLTP와 OLAP은 왜 분리하는가?
- 배치 처리와 스트림 처리는 언제 선택하는가?
- CDC는 운영 데이터베이스와 분석 계층 사이에서 어떤 역할을 하는가?
- Kafka, Flink, Iceberg, Ozone, Polaris, ClickHouse, Airflow, Superset은 각각 무엇을 담당하는가?

이 장에서는 제품별 설치와 세부 설정을 다루지 않습니다. Windows 11과 Apple Silicon 환경 준비는 2장, Docker Compose 프로젝트 설계는 3장, Kafka·CDC·Iceberg·Flink·ClickHouse의 상세 기능은 뒤의 장에서 설명합니다.

## 1. 데이터 플랫폼이 필요한 이유

애플리케이션은 주문, 결제, 고객, 상품, 거래와 같은 업무 데이터를 데이터베이스에 기록합니다. 초기에는 애플리케이션이 사용하는 데이터베이스에서 필요한 데이터를 바로 조회해도 문제가 크지 않습니다.

하지만 데이터가 축적되고 분석 요구가 늘어나면 운영 데이터베이스가 담당해야 하는 일이 많아집니다.

- 고객 요청에 대한 트랜잭션 처리
- 주문과 결제 데이터 저장
- 현재 상태 조회
- 통계와 리포트 생성
- 분석 및 머신러닝용 데이터 제공
- 다른 시스템으로의 데이터 전달

운영 데이터베이스에서 대규모 분석 쿼리까지 수행하면 서로 다른 작업이 같은 CPU, 메모리, 디스크, 네트워크를 사용하게 됩니다. 그러면 분석 작업이 트랜잭션 처리에 영향을 주거나, 반대로 업무 트랜잭션이 분석 작업을 지연시킬 수 있습니다.

데이터 플랫폼은 이 문제를 데이터의 흐름과 책임을 분리하는 방식으로 해결합니다. 원천 시스템에서 데이터를 수집하고, 원본을 보존하고, 필요한 변환을 수행한 뒤, 분석과 서비스에 적합한 형태로 제공합니다.

데이터 플랫폼은 특정 제품 하나를 가리키는 말이 아닙니다. 데이터 수집·저장·처리·제공·관리 기능을 연결한 기술 구조와 운영 체계 전체를 의미합니다.

## 2. 데이터 플랫폼의 기본 계층

| 계층 | 역할 | 이 책의 구성 요소 |
|---|---|---|
| 데이터 소스 | 트랜잭션과 업무 데이터 생성 | Percona Server for MySQL, PostgreSQL, MongoDB |
| 수집·전달 | 변경 데이터와 이벤트 수집 | Flink CDC, Apache Kafka |
| 원본 저장 | 원본 이벤트와 데이터 파일 보존 | Apache Ozone, Apache Iceberg |
| 처리·정제 | 데이터 변환, 표준화, 품질 검증 | Apache Flink, Apache Spark |
| 카탈로그 | 테이블과 메타데이터 접근 경로 관리 | Apache Polaris |
| 서빙 | 분석 쿼리와 BI용 데이터 제공 | ClickHouse, Iceberg Mart |
| 오케스트레이션 | 작업 순서와 실행 일정 관리 | Apache Airflow |
| 소비 | 대시보드와 분석 결과 제공 | Apache Superset |

이 책은 이 계층을 Windows 11과 Apple Silicon Mac의 Docker Compose 환경에서 단계적으로 구현합니다.

~~~mermaid
flowchart TD
    A["Percona MySQL<br/>PostgreSQL<br/>MongoDB"] --> B["Flink CDC"]
    B --> C["Apache Kafka"]
    C --> D["Iceberg Raw<br/>Apache Ozone"]
    D --> E["Apache Flink"]
    E --> F["Iceberg Cleaned"]
    F --> G["ClickHouse Mart"]
    G --> H["Apache Superset"]
    I["Apache Airflow"] -. 작업 실행 관리 .-> E
    J["Apache Polaris"] -. Iceberg 카탈로그 .-> D
~~~

이 구조에서 각 구성 요소는 서로 다른 책임을 가집니다.

- 운영 데이터베이스는 업무 트랜잭션을 처리합니다.
- Kafka는 변경 이벤트를 전달하고 재소비할 수 있게 합니다.
- Ozone은 객체와 데이터 파일을 저장합니다.
- Iceberg는 데이터 파일을 테이블과 스냅샷으로 관리합니다.
- Flink는 이벤트를 정제하고 실시간으로 처리합니다.
- ClickHouse는 분석과 조회에 적합한 데이터를 제공합니다.
- Airflow는 작업의 실행 순서를 관리합니다.
- Superset은 최종 분석 결과를 사용자에게 보여 줍니다.

## 3. 데이터 웨어하우스

데이터 웨어하우스는 여러 데이터 소스에서 수집한 데이터를 분석과 의사결정에 사용할 수 있도록 통합한 저장 구조입니다.

W. H. Inmon은 데이터 웨어하우스를 주제 중심(subject-oriented), 통합(integrated), 시간에 따라 변화하는(time-variant), 비휘발성(nonvolatile) 데이터의 집합으로 설명했습니다. (출처: W. H. Inmon, *Building the Data Warehouse*)

### 3.1 주제 중심성

데이터 웨어하우스는 애플리케이션 화면이나 원천 테이블의 구조보다 비즈니스 주제를 중심으로 데이터를 구성합니다.

대표적인 주제는 다음과 같습니다.

- 고객
- 주문
- 상품
- 거래
- 결제
- 매출

### 3.2 데이터 통합

여러 시스템에서 생성된 데이터를 공통된 기준으로 정리합니다.

예를 들어 한 시스템이 고객 식별자를 customer_id로 저장하고 다른 시스템이 cust_no로 저장한다면, 분석 계층에서는 이를 하나의 표준 속성으로 통합할 수 있습니다.

날짜 형식, 통화 단위, 코드값, 식별자 규칙도 통합 대상입니다.

### 3.3 시간에 따른 이력

운영 시스템은 현재 상태를 빠르게 조회하는 데 초점을 두는 경우가 많습니다. 데이터 웨어하우스는 과거의 상태와 변화 추이를 분석할 수 있어야 합니다.

- 지난 분기의 고객 등급은 무엇이었는가?
- 특정 시점의 상품 가격은 얼마였는가?
- 월별 주문 금액은 어떻게 변했는가?
- 특정 기간의 거래량은 얼마였는가?

### 3.4 사전에 정의된 구조

전통적인 데이터 웨어하우스는 데이터를 적재하기 전에 테이블과 컬럼 구조를 정의합니다. 이를 스키마 온 라이트(schema-on-write)라고 합니다.

이 방식은 데이터 구조와 품질을 통제하기 쉽습니다. 반면 새로운 데이터 형식이나 컬럼을 자주 추가해야 하는 환경에서는 스키마 변경 절차가 부담이 될 수 있습니다.

데이터 웨어하우스가 반드시 특정 저장 방식으로 구현되는 것은 아닙니다. 전통적인 관계형 시스템은 행 기반 저장을 사용할 수 있고, 현대 분석 시스템은 컬럼 지향 저장을 활용할 수 있습니다.

## 4. 데이터 레이크

데이터 레이크는 구조화·반구조화·비구조화 데이터를 원본에 가까운 형태로 저장하는 구조입니다.

데이터 레이크는 저장 시점에 모든 데이터 구조를 확정하지 않고, 사용 시점에 필요한 스키마를 해석하는 스키마 온 리드(schema-on-read) 방식을 사용하는 경우가 많습니다.

저장 대상의 예는 다음과 같습니다.

- 관계형 테이블에서 추출한 데이터
- JSON 문서
- 애플리케이션 로그
- CDC 이벤트
- 이미지와 문서
- Parquet, ORC, Avro 데이터 파일

### 4.1 장점

데이터 레이크는 데이터 형식이 다양하거나, 원본을 보존해야 하거나, 향후 사용 목적이 아직 확정되지 않은 환경에서 유용합니다.

이 책에서는 Apache Ozone을 객체 저장 계층으로 사용합니다.

### 4.2 한계

객체 저장소에 파일을 저장하는 것만으로는 데이터베이스 테이블과 같은 관리 기능이 자동으로 제공되지 않습니다.

- 최신 파일을 판단하기 어려움
- 동시 변경 충돌을 관리하기 어려움
- 스키마 변경 이력 관리가 어려움
- UPDATE와 DELETE의 의미를 일관되게 처리하기 어려움
- 파일 수가 증가할수록 메타데이터 관리가 복잡해짐
- 데이터 소유자와 품질 정보를 별도로 관리해야 함

객체 저장소 자체와 테이블 포맷은 구분해야 합니다. Apache Iceberg와 같은 오픈 테이블 포맷은 객체 저장소 위에 스키마, 스냅샷, 테이블 메타데이터와 같은 관리 기능을 추가합니다.

## 5. 데이터 레이크하우스

데이터 레이크하우스는 데이터 레이크의 확장성과 유연성에 데이터 웨어하우스의 테이블 관리, 스키마 관리, 트랜잭션, 분석 기능을 결합한 아키텍처입니다.

AWS와 Databricks는 레이크하우스를 데이터 레이크의 확장 가능한 저장소와 데이터 웨어하우스의 구조화·거버넌스·트랜잭션 기능을 결합한 구조로 설명합니다. (출처: [AWS, What is a Data Lakehouse?](https://aws.amazon.com/what-is/data-lakehouse/), [Databricks, What is a Data Lakehouse?](https://www.databricks.com/blog/data-lakehouse-examples))

### 5.1 주요 기능

- 데이터 파일을 스키마와 스냅샷을 가진 테이블로 관리
- 컬럼 추가와 같은 스키마 변화 관리
- 특정 시점의 테이블 상태 조회
- 과거 데이터 재처리와 변경 전후 비교
- 여러 엔진에서 동일한 테이블 접근

이 책에서는 Apache Flink를 실시간 처리에, Apache Spark를 배치 처리에, Apache Iceberg를 테이블 관리에, ClickHouse를 분석 서빙에 사용합니다.

### 5.2 오픈 레이크하우스

오픈 레이크하우스는 저장소, 테이블 포맷, 처리 엔진, 카탈로그 등 데이터 플랫폼의 계층을 단일 공급자에 종속시키지 않고 공개 표준과 개방형 구현으로 구성하려는 접근입니다.

| 계층 | 구성 요소 |
|---|---|
| 객체 저장 | Apache Ozone |
| 테이블 포맷 | Apache Iceberg |
| 카탈로그 | Apache Polaris |
| 이벤트 스트리밍 | Apache Kafka |
| 스트림 처리 | Apache Flink |
| 배치 처리 | Apache Spark |
| 분석 서빙 | ClickHouse |
| 오케스트레이션 | Apache Airflow |
| 시각화 | Apache Superset |

레이크하우스가 모든 환경에서 데이터 웨어하우스보다 우월한 것은 아닙니다. 워크로드, 데이터 품질 요구, 운영 역량, 쿼리 패턴에 따라 적합한 구조가 달라집니다.

## 6. OLTP와 OLAP

### 6.1 OLTP

OLTP(Online Transaction Processing)는 애플리케이션의 업무 트랜잭션을 처리합니다.

- 고객 정보 등록
- 주문 생성
- 주문 상태 변경
- 결제 승인
- 상품 재고 차감
- 계좌 잔액 변경

OLTP 시스템에서 중요하게 보는 요소는 짧고 반복적인 트랜잭션, 동시성 제어, 원자성, 무결성, 예측 가능한 응답 시간입니다.

이 책의 Percona Server for MySQL, PostgreSQL, MongoDB는 운영 트랜잭션 계층입니다.

### 6.2 OLAP

OLAP(Online Analytical Processing)은 많은 데이터를 읽고 집계하여 분석합니다.

- 일별·월별 주문 금액
- 지역별 매출 추이
- 상품별 판매량
- 시간대별 거래량
- 고객 유형별 재구매율

OLAP 쿼리는 많은 행을 읽고 여러 컬럼을 조합하며 집계, 그룹화, 조인을 수행하는 경우가 많습니다. 따라서 단일 행의 트랜잭션을 처리하는 OLTP와 다른 저장 구조와 실행 전략이 필요합니다.

### 6.3 비교

| 구분 | OLTP | OLAP |
|---|---|---|
| 목적 | 업무 트랜잭션 처리 | 분석과 집계 |
| 주요 연산 | INSERT, UPDATE, DELETE, 단건 SELECT | 대량 SELECT, JOIN, GROUP BY |
| 데이터 범위 | 현재 업무 상태 중심 | 현재 및 과거 이력 |
| 접근 단위 | 특정 행 또는 소수 행 | 많은 행과 여러 컬럼 |
| 스키마 | 정규화 중심 | 분석 목적의 반정규화·집계 구조 |
| 중요 요소 | 무결성, 동시성, 트랜잭션 | 스캔 효율, 집계, 분석 편의성 |
| 이 책의 구성 요소 | Percona MySQL, PostgreSQL, MongoDB | Iceberg Mart, ClickHouse |

지연 시간에 관한 고정 수치는 적용하지 않습니다. 실제 성능은 데이터 크기, 쿼리 형태, 인덱스, 파티션, 하드웨어, 동시 실행 수에 따라 달라집니다.

### 6.4 동일 데이터에 대한 다른 쿼리

운영 시스템에서는 특정 주문을 조회할 수 있습니다.

~~~sql
SELECT
    order_id,
    customer_id,
    order_status,
    total_amount
FROM orders
WHERE order_id = 10001;
~~~

분석 시스템에서는 여러 기간의 주문을 지역별로 집계할 수 있습니다.

~~~sql
SELECT
    order_date,
    region,
    count(*) AS order_count,
    sum(total_amount) AS total_amount
FROM order_mart
WHERE order_date >= '2026-01-01'
GROUP BY order_date, region
ORDER BY order_date, region;
~~~

## 7. 배치 처리와 스트림 처리

### 7.1 배치 처리

배치 처리는 일정 시점까지 모인 데이터를 하나의 작업 단위로 처리합니다.

- 전일 주문 데이터 집계
- 시간 단위 로그 처리
- 월말 매출 리포트 생성
- 과거 기간 데이터 재계산
- 대량 원본 데이터의 정제

배치 작업은 처리 대상의 시작과 끝이 비교적 명확합니다. 따라서 전체 작업을 계획하고 실패한 작업을 다시 실행하거나 특정 기간부터 재처리하기 쉽습니다.

Apache Spark는 이 책에서 대규모 배치 변환과 집계에 사용합니다.

### 7.2 스트림 처리

스트림 처리는 데이터가 계속 발생하는 동안 이벤트가 도착하는 대로 처리합니다.

- 주문 이벤트 발생 시 집계 갱신
- 결제 이벤트 기반 이상 패턴 확인
- 데이터베이스 변경 이벤트 전달
- 시간 창 단위 집계
- 중복 이벤트 제거와 공통 스키마 변환

스트림 처리에서는 이벤트 순서, 이벤트 시간, 늦게 도착한 이벤트, 상태 저장, 장애 복구를 고려해야 합니다.

Apache Flink는 이 책에서 스트림 처리 엔진으로 사용합니다.

### 7.3 비교

| 구분 | 배치 처리 | 스트림 처리 |
|---|---|---|
| 처리 대상 | 일정 시점까지 모인 데이터 | 계속 유입되는 이벤트 |
| 데이터 범위 | 유계 데이터 | 무계 데이터 |
| 실행 방식 | 예약 또는 수동 실행 | 상시 실행 |
| 주요 관심사 | 전체 처리량과 재실행 | 지연, 상태, 순서, 복구 |
| 대표 구성 요소 | Apache Spark | Apache Flink, Apache Kafka |

Spark에도 Structured Streaming이 있고 Flink도 유계 데이터를 처리할 수 있습니다. 두 엔진을 배치 전용과 스트리밍 전용으로 단정해서는 안 됩니다.

## 8. CDC가 필요한 이유

CDC(Change Data Capture)는 소스 데이터베이스에서 발생한 변경 사항을 감지하고 하류 시스템으로 전달하는 기술입니다.

변경 사항에는 일반적으로 다음 작업이 포함됩니다.

- INSERT
- UPDATE
- DELETE
- 일부 시스템의 스키마 변화

운영 데이터베이스를 주기적으로 조회하는 폴링 방식은 구현이 단순할 수 있지만, 같은 데이터를 반복해서 읽어야 하고 삭제나 변경 순서를 정확히 파악하기 어려울 수 있습니다.

CDC는 데이터베이스의 변경 로그 또는 변경 스트림을 활용하여 변경 내용을 이벤트로 전달합니다.

### 8.1 CDC와 폴링 비교

| 구분 | 로그 기반 CDC | 쿼리 기반 폴링 |
|---|---|---|
| 변경 감지 | 트랜잭션 로그 또는 변경 스트림 | 주기적인 SELECT |
| 장점 | 변경 내용을 직접 이벤트로 전달 | 초기 구현이 비교적 단순 |
| 소스 부하 | 변경 로그 읽기 중심 | 반복 조회로 증가할 수 있음 |
| 삭제 감지 | 삭제 이벤트를 통해 처리 가능 | 별도 삭제 표시가 필요할 수 있음 |
| 순서 처리 | 로그와 커넥터 정책에 의존 | 조회 시점과 조건에 의존 |
| 적합한 상황 | 지속적인 변경 전달과 재처리 | 소규모·저빈도 동기화 |

폴링이 항상 잘못된 방식은 아닙니다. 데이터가 적고 변경 빈도가 낮으며 삭제와 순서에 대한 요구가 낮다면 사용할 수 있습니다.

### 8.2 데이터베이스별 경계

| 데이터베이스 | 변경 정보의 주요 원천 |
|---|---|
| Percona Server for MySQL | Binary Log |
| PostgreSQL | WAL 및 논리적 복제 |
| MongoDB | Replica Set 기반 Change Streams |

실제 CDC 설정과 커넥터 지원 범위는 데이터베이스 및 Flink CDC 버전에 따라 달라집니다. CDC를 사용한다고 해서 전체 파이프라인이 자동으로 Exactly-once가 되는 것도 아닙니다.

## 9. 원본 데이터에서 서빙 데이터까지

| 단계 | 데이터 | 목적 |
|---|---|---|
| 원본 | 운영 데이터베이스의 데이터 | 업무 트랜잭션 처리 |
| 이벤트 | CDC 변경 이벤트 | 전달, 재소비, 재처리 |
| 정제 | 공통 스키마 데이터 | 표준화, 품질 검증 |
| 서빙 | 분석용 Mart | BI와 분석 쿼리 |

메달리온 구조와 연결하면 다음과 같습니다.

| 레이어 | 의미 | 이 책의 구성 |
|---|---|---|
| Bronze | 원본에 가까운 데이터 | Kafka 이벤트, Iceberg Raw |
| Silver | 정제·표준화된 데이터 | Iceberg Cleaned |
| Gold | 소비 목적에 최적화된 데이터 | Iceberg Mart, ClickHouse Mart |

서빙 데이터는 빠른 분석을 위해 집계되거나 반정규화될 수 있습니다. 그러나 서빙 데이터만 남기면 원본 변경을 다시 확인하거나 집계 로직을 변경해 과거 데이터를 재생성하기 어려울 수 있습니다.

따라서 이 책에서는 Iceberg Raw를 원본에 가까운 데이터의 기준점으로 사용하고, ClickHouse를 조회와 분석을 위한 서빙 계층으로 사용합니다.

## 10. 구성 요소별 역할

### Apache Kafka

Kafka는 이벤트 스트리밍 플랫폼입니다. 데이터베이스 변경 이벤트를 처리 엔진과 저장 계층 사이에서 전달합니다.

- 소스와 처리 엔진의 결합도 감소
- 이벤트 보관
- 소비자별 독립 처리
- 장애 이후 이벤트 재소비
- 여러 하류 시스템으로 이벤트 전달

Kafka의 토픽, 파티션, 오프셋, KRaft 구성은 5장에서 다룹니다. (출처: [Apache Kafka Documentation](https://kafka.apache.org/documentation/))

### Apache Flink와 Flink CDC

Flink는 이벤트 스트림을 처리하고 상태를 관리합니다. Flink CDC는 데이터베이스 변경 정보를 읽어 이벤트로 전달합니다.

이 책에서는 CDC 이벤트 정제, 공통 스키마 변환, 중복 처리, 윈도우 집계, Iceberg 적재에 Flink를 사용합니다.

### Apache Iceberg

Iceberg는 객체 저장소의 데이터 파일을 테이블로 관리하는 오픈 테이블 포맷입니다.

- 테이블 스키마 관리
- 데이터 파일과 메타데이터 연결
- 스냅샷 관리
- 과거 상태 조회
- 스키마 변화 관리
- 여러 엔진에서의 테이블 접근

상세 스냅샷과 매니페스트는 9장에서 다룹니다. (출처: [Apache Iceberg Specification](https://iceberg.apache.org/spec/))

### Apache Ozone과 Apache Polaris

Ozone은 객체와 데이터 파일을 저장합니다. Polaris는 Iceberg 테이블의 카탈로그 계층으로 사용합니다.

| 구성 요소 | 책임 |
|---|---|
| Apache Ozone | 객체와 데이터 파일 저장 |
| Apache Iceberg | 파일을 테이블과 스냅샷으로 관리 |
| Apache Polaris | Iceberg 카탈로그와 접근 경로 관리 |

### ClickHouse

ClickHouse는 분석과 서빙 계층입니다.

- 일별·시간별 집계
- 지역·상품·고객별 분석
- 사전 집계된 Mart 조회
- 대시보드용 데이터 제공

이 책에서는 Iceberg를 원본·정제 데이터의 기준 저장 계층으로, ClickHouse를 조회와 분석을 위한 서빙 계층으로 사용합니다. ClickHouse의 Iceberg 연동과 기능 제한은 13장에서 다룹니다. (출처: [ClickHouse Iceberg Table Engine](https://clickhouse.com/docs/engines/table-engines/integrations/iceberg))

### Apache Airflow

Airflow는 데이터 작업의 실행 순서와 일정을 관리합니다. Flink와 Spark가 데이터 변환을 수행한다면 Airflow는 작업의 실행 흐름을 관리합니다.

### Apache Superset

Superset은 ClickHouse Mart를 조회하여 대시보드와 차트를 제공합니다. 데이터 수집과 정제는 수행하지 않습니다.

## 11. 주문 데이터로 전체 흐름 이해하기

1. 사용자가 주문을 생성하면 주문 정보가 소스 데이터베이스에 저장됩니다.
2. Flink CDC가 데이터베이스의 변경 정보를 읽습니다.
3. 변경 이벤트가 Kafka로 전달됩니다.
4. 이벤트가 Iceberg Raw 테이블에 저장됩니다.
5. Flink가 이벤트를 공통 스키마로 정제합니다.
6. 정제 결과가 Iceberg Cleaned 테이블에 저장됩니다.
7. 분석 목적에 맞는 Mart를 생성합니다.
8. ClickHouse가 분석 쿼리와 서빙을 담당합니다.
9. Superset이 대시보드로 결과를 보여 줍니다.

이 과정에서 소스 데이터베이스, 이벤트 스트리밍, 원본 저장, 정제, 서빙은 서로 다른 책임을 가집니다.

## 12. 이 책의 설계 원칙

1. 운영 데이터베이스와 분석 계층을 분리합니다.
2. 변경 데이터를 CDC 이벤트로 전달합니다.
3. 원본 이벤트를 보존하여 재처리 가능성을 확보합니다.
4. 저장소와 테이블 포맷을 구분합니다.
5. 정제 데이터와 서빙 데이터를 분리합니다.
6. 오케스트레이션과 데이터 처리를 구분합니다.
7. 로컬 Docker Compose 환경을 운영 환경과 동일하게 간주하지 않습니다.

## 장 요약

데이터 플랫폼은 데이터를 수집·저장·처리·제공·관리하는 전체 구조입니다. 데이터 웨어하우스는 통합된 분석 데이터를 관리하고, 데이터 레이크는 다양한 형식의 원본 데이터를 저장합니다. 레이크하우스는 객체 저장소와 오픈 테이블 포맷을 이용해 두 접근의 장점을 결합합니다.

OLTP는 업무 트랜잭션에, OLAP은 대규모 분석에 적합합니다. 배치 처리는 모인 데이터를 처리하고, 스트림 처리는 계속 유입되는 이벤트를 처리합니다. CDC는 운영 데이터베이스의 변경을 이벤트로 전달하며, Kafka·Flink·Iceberg·ClickHouse는 이 데이터 흐름의 서로 다른 단계를 담당합니다.

다음 장에서는 Windows 11과 Apple Silicon Mac에서 Docker Desktop과 Docker Compose를 준비합니다.

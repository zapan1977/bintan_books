# 17장. 로컬 데이터 플랫폼 장애 처리와 복구

16장에서는 MySQL·MongoDB·PostgreSQL의 변경을 Kafka와 Flink CDC로 수집하고, Iceberg Raw·Clean·Mart를 거쳐 ClickHouse와 Superset으로 제공하는 전체 파이프라인을 구성했다. 파이프라인이 여러 구성 요소로 나뉘면 한 곳의 장애가 다음 계층으로 전파될 수 있다.

Docker 컨테이너가 시작되지 않으면 CDC가 중단되고, Kafka Consumer lag이 증가한다. Flink Checkpoint가 실패하면 상태를 안전하게 저장하지 못할 수 있다. Iceberg Commit이 실패하면 데이터 파일과 Snapshot의 관계를 확인해야 한다. ClickHouse 적재가 지연되면 Superset Dashboard는 오래된 결과를 보여 줄 수 있다. 디스크나 메모리가 부족하면 여러 서비스가 동시에 종료될 수 있다.

이 장의 목표는 특정 명령을 외우는 것이 아니다. 장애가 발생했을 때 데이터를 더 훼손하지 않고, 어느 계층에서 문제가 시작되었는지 분리하며, 복구 후 결과의 정합성을 확인하는 절차를 익히는 것이다. 로컬 Docker Compose 환경을 기본으로 설명하고, Kubernetes·클라우드 저장소·운영형 백업은 확장 지점으로 표시한다.

## 1. 장애 대응의 기본 원칙

### 1.1 먼저 멈추고 범위를 고정한다

장애를 발견하면 무조건 컨테이너를 재시작하지 않는다. 재시작으로 상태가 바뀌거나 로그가 사라질 수 있고, CDC Job을 다시 제출하면 중복 처리가 발생할 수 있다.

초기 대응은 다음 순서로 진행한다.

1. 사용자와 데이터에 미치는 영향을 확인한다.
2. 현재 실행 중인 쓰기·삭제·정리 작업을 확인한다.
3. 추가적인 데이터 변경을 일시적으로 제한한다.
4. 로그와 상태를 보존한다.
5. 원인을 Source·Transport·Processing·Storage·Serving 계층으로 좁힌다.
6. 복구 전후의 검증 기준을 정한다.

### 1.2 장애 분류

| 계층 | 대표 장애 | 우선 위험 |
|---|---|---|
| Container | healthcheck 실패·재시작 반복 | 서비스 연쇄 중단 |
| Source | DB 연결·CDC 권한·로그 보존 문제 | 이벤트 누락 |
| Kafka | Consumer lag·Broker·Topic 문제 | 처리 지연·보존 기간 초과 |
| Flink | Checkpoint 실패·Backpressure | 상태 복구 불가·처리 정지 |
| Iceberg | Commit 충돌·Catalog 불가·파일 손상 | Snapshot과 파일 불일치 |
| ClickHouse | 적재 지연·Merge·디스크 부족 | Serving stale data |
| Airflow | DAG·Metadata DB·Worker 문제 | 재처리 지연 |
| Superset | SQL·Cache·RLS 문제 | 잘못된 화면·권한 노출 |
| Host | 디스크·메모리·CPU 부족 | 여러 서비스 동시 종료 |

### 1.3 데이터 위험도

장애의 긴급도는 서비스가 살아 있는지보다 데이터가 유실·중복·오노출될 가능성으로 판단한다.

| 위험 | 예 | 조치 |
|---|---|---|
| 데이터 유실 | Kafka 보존 기간 만료 전 복구 불가 | 추가 처리 중지·Source 재수집 검토 |
| 중복 | Flink Job 중복 제출·ClickHouse 재적재 | 영향 범위 고정·키·Snapshot 확인 |
| 잘못된 상태 | 잘못된 Iceberg Snapshot Commit | 신규 소비 중지·Snapshot 비교 |
| 오노출 | RLS 우회·Credential 과다 권한 | 계정·토큰 즉시 제한·감사 보존 |
| 가용성 저하 | Dashboard timeout | 조회 범위 축소·Serving 상태 확인 |

### 2.1 로컬 Compose 상태


### 2.2 최근 변경

다음 질문에 답한다.

- 최근 수정한 Compose 파일·환경 변수·이미지는 무엇인가?
- 최근 배포·DAG 변경·Schema 변경이 있었는가?
- 최근 대량 적재·백필·Compaction을 시작했는가?
- Docker Desktop의 CPU·메모리·디스크 설정을 변경했는가?

장애 발생 시각과 최근 변경 시각을 함께 기록한다. 원인을 모르는 상태에서 여러 설정을 동시에 바꾸면 원인과 결과를 구분할 수 없게 된다.

## 3. Docker Compose healthcheck 실패

### 3.1 healthcheck의 의미

healthcheck는 컨테이너 내부 또는 네트워크에서 특정 확인 명령을 실행해 서비스가 기대한 상태인지 판단한다. healthcheck 실패는 컨테이너 프로세스가 반드시 종료되었다는 뜻이 아니다. 반대로 컨테이너가 running이어도 애플리케이션이 요청을 처리하지 못할 수 있다.

| 상태 | 의미 |
|---|---|
| created | 컨테이너가 생성되었지만 시작되지 않음 |
| running | 주 프로세스가 실행 중 |
| healthy | healthcheck 성공 |
| unhealthy | healthcheck 연속 실패 |
| exited | 주 프로세스 종료 |

### 3.2 점검 명령

~~~bash
docker compose ps
docker inspect <container_name> --format '{{json .State.Health}}'
docker compose logs --tail=200 <service_name>
docker compose exec <service_name> sh
~~~

Windows PowerShell에서는 따옴표와 줄바꿈 규칙이 다를 수 있다. 명령을 복사하기 전에 사용하는 Shell에 맞게 확인한다.

컨테이너 안에서 healthcheck가 사용하는 명령을 직접 실행한다. 예를 들어 PostgreSQL은 pg_isready, Redis는 redis-cli ping, HTTP 서비스는 curl 또는 wget을 사용할 수 있다. 실제 이미지에 해당 도구가 설치되지 않았다면 healthcheck 자체가 실패한다.

### 3.3 PostgreSQL healthcheck 예시

~~~yaml
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U superset -d superset"]
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 30s
~~~

데이터베이스가 초기화 중인데 start_period가 너무 짧으면 정상적인 초기화도 실패로 판정될 수 있다. 반대로 retries와 timeout을 지나치게 늘리면 실제 장애를 늦게 발견한다.

### 3.4 healthcheck 원인별 점검

| 원인 | 확인 | 대응 |
|---|---|---|
| 서비스 미기동 | ps·events | depends_on·command 확인 |
| 포트 오류 | 컨테이너 내부 접속 | 내부 포트와 호스트 포트 구분 |
| DNS 오류 | 서비스 이름 조회 | Compose 네트워크·서비스명 확인 |
| 인증 오류 | 연결 로그 | 사용자·비밀번호·DB 이름 확인 |
| 초기화 지연 | DB 로그 | start_period·초기화 상태 확인 |
| 도구 누락 | healthcheck 명령 실행 | 이미지·명령 교체 검토 |
| 리소스 부족 | stats·Host 상태 | 메모리·디스크 확보 |

## 4. Kafka Consumer lag

### 4.1 lag의 의미

Consumer lag은 Kafka Topic에 기록된 최신 Offset과 Consumer Group이 처리한 Offset 사이의 차이다. lag이 발생했다고 곧바로 데이터가 유실된 것은 아니지만, 증가가 지속되면 Kafka 보존 기간을 넘겨 처리하지 못할 위험이 있다.

lag을 하나의 전체 숫자로만 보지 않는다. Topic, Partition, Consumer Group별로 어느 Partition에 집중되었는지 확인한다.

### 4.2 진단 명령

~~~bash
kafka-consumer-groups.sh +  --bootstrap-server kafka:9092 +  --describe +  --group flink-cdc-group
~~~

Windows에서 Kafka CLI를 호스트에서 실행할 수 없다면 Kafka 컨테이너 안에서 실행한다.

~~~bash
docker compose exec kafka kafka-consumer-groups.sh +  --bootstrap-server kafka:9092 +  --describe +  --group flink-cdc-group
~~~

실제 Kafka 이미지의 CLI 경로와 명령명은 배포판에 따라 다를 수 있다.

### 4.3 lag 원인 분리

| 관찰 | 가능 원인 |
|---|---|
| 모든 Partition lag 증가 | Consumer 전체 중단·Flink 정지·네트워크 |
| 한 Partition만 증가 | 키 편중·특정 레코드 처리 실패 |
| 처리량이 입력보다 낮음 | CPU·I/O·Backpressure·외부 Sink |
| Offset이 움직이지 않음 | Consumer 오류·Commit 실패·Job 정지 |
| lag이 줄지만 Raw가 늘지 않음 | Sink Commit·Schema·권한 문제 |

Consumer를 무작정 늘리기 전에 Topic Partition 수와 Flink Source 병렬도를 확인한다. Partition 수보다 많은 Consumer가 항상 처리량을 높이는 것은 아니다.

### 4.4 lag 대응

1. Flink Job과 Consumer Group의 상태를 확인한다.
2. 특정 Partition에 실패 이벤트가 몰렸는지 확인한다.
3. Iceberg Sink Commit과 Checkpoint 상태를 확인한다.
4. Kafka 보존 기간과 현재 lag 증가 속도를 계산한다.
5. 원인이 리소스라면 처리 병렬도와 메모리를 조정한다.
6. 원인이 잘못된 데이터라면 오류 이벤트를 격리하고 재처리 규칙을 정한다.

Kafka Offset을 수동으로 이동하기 전에 해당 Offset의 이벤트가 처리되지 않았는지 확인한다. Offset을 앞쪽으로 건너뛰면 데이터가 유실될 수 있다.

## 5. Flink Checkpoint와 Savepoint 실패

### 5.1 Checkpoint와 Savepoint의 차이

Checkpoint는 장애 복구를 위한 자동 상태 저장이고, Savepoint는 계획된 중지·업그레이드·이동을 위해 명시적으로 만든 상태 저장 지점으로 설명한다. 실제 저장 위치·형식·복구 옵션은 Flink 실행 방식과 버전에 따라 다르다.

Checkpoint가 반복해서 실패하면 Job이 실행 중이어도 복구 가능한 최신 상태가 갱신되지 않을 수 있다.

### 5.2 확인할 지표

| 항목 | 질문 |
|---|---|
| Checkpoint duration | 완료 시간이 계속 증가하는가? |
| Checkpoint size | 상태 크기가 갑자기 증가했는가? |
| 실패 원인 | timeout, storage, barrier, network 중 무엇인가? |
| Backpressure | Sink나 외부 저장소가 처리를 막는가? |
| TaskManager memory | Heap·Managed·Network 메모리가 부족한가? |

### 5.3 원인별 대응

| 원인 | 설명 | 우선 대응 |
|---|---|---|
| 저장소 접근 실패 | Checkpoint 경로·권한·네트워크 문제 | 경로와 Credential 확인 |
| timeout | 상태 크기·Backpressure·병렬도 | 병목 Task와 저장 시간 측정 |
| 메모리 부족 | 상태·버퍼·JVM 사용량 증가 | 메모리와 상태 크기 점검 |
| Sink commit 실패 | Iceberg·외부 시스템 오류 | Sink 로그와 Snapshot 확인 |
| Job 중복 실행 | 같은 CDC Job을 중복 제출 | Job ID와 제출 이력 확인 |

### 5.4 복구 예시

운영형 Flink 배포에서 Savepoint에서 Job을 재시작하는 개념적 명령은 다음과 같다.

~~~bash
flink run -s s3://flink-savepoints/savepoint-12345 +  /opt/flink-jobs/orders-cdc-job.jar
~~~

로컬 Docker Compose에서는 S3 경로가 Ozone Endpoint 또는 로컬 볼륨 경로로 바뀔 수 있다.

[검토 필요: Flink 2.2.1과 Flink CDC 3.6.0 조합에서 Checkpoint·Savepoint 저장소 URI, 재시작 옵션, State Backend, Ozone S3 호환 설정을 실제 배포 방식에 맞게 확인해야 합니다.]

## 6. Iceberg Commit 실패와 테이블 복구

### 6.1 파일 수준 복구의 한계

Iceberg 테이블은 Data File만으로 구성되지 않는다. Catalog가 가리키는 Metadata, Snapshot, Manifest List, Manifest와 Data File의 관계가 함께 있어야 쿼리 엔진이 테이블을 해석할 수 있다.

따라서 Data File만 복사하거나 metadata.json만 복사하는 방식으로는 완전한 테이블 복구를 보장할 수 없다. 테이블 단위 복구 계획에는 최소한 다음을 포함한다.

- Catalog의 테이블 등록 정보
- 현재·이전 metadata.json
- Snapshot과 Manifest
- Data File
- 객체 저장소의 Versioning 또는 백업본
- Catalog DB 백업
- 복구 시점과 Snapshot ID 기록

### 6.2 Commit 실패 초기 대응

Iceberg Commit이 실패했을 때는 다음 순서로 확인한다.

1. 처리 엔진이 실제로 Commit을 실패했는지 확인한다.
2. Catalog에 새 Snapshot이 생성되었는지 확인한다.
3. 객체 저장소에 새 파일이 남았는지 확인한다.
4. 다른 Writer가 같은 테이블에 Commit했는지 확인한다.
5. Snapshot 목록과 Commit 시각을 저장한다.
6. 재시도 전에 중복·고아 파일 가능성을 판단한다.

Commit 오류 메시지만 보고 즉시 다시 실행하면 첫 번째 시도가 Catalog에 반영된 뒤 두 번째 시도가 중복 작업을 만들 수 있다.

### 6.3 Snapshot 확인과 Rollback

조사본은 Snapshot ID 또는 시각을 기준으로 이전 상태로 되돌리는 예시를 제시한다.

~~~sql
-- Snapshot 확인
SELECT snapshot_id, committed_at, operation
FROM lakehouse.raw.orders.snapshots
ORDER BY committed_at DESC;

-- 이전 Snapshot으로 롤백하는 개념적 예시
CALL lakehouse.system.rollback_to_snapshot(
    'lakehouse.raw.orders',
    8027658604211071520
);

-- 특정 시각으로 롤백하는 개념적 예시
CALL lakehouse.system.rollback_to_timestamp(
    'lakehouse.raw.orders',
    TIMESTAMP '2026-08-25 00:00:00'
);
~~~

Snapshot 조회 테이블과 rollback 프로시저의 이름·인자·지원 여부는 실행 엔진에 따라 다르다. 위 SQL은 특정 엔진에서 즉시 실행할 확정 명령이 아니라 복구 절차의 구조를 보여 주는 예시다.

[검토 필요: Apache Iceberg 1.11.0을 어떤 엔진으로 조작할지 확정하고, Spark·Trino·Flink별 Snapshot 조회와 rollback procedure 문법을 검증해야 합니다.]

### 6.4 삭제된 테이블의 Register

Catalog에서 테이블 등록 정보가 삭제되었지만 Metadata File과 Data File이 남아 있다면 Metadata File을 이용해 테이블을 다시 등록하는 절차를 검토할 수 있다.

~~~text
1. 객체 저장소에서 복구할 metadata.json을 식별한다.
2. 해당 Metadata가 참조하는 Manifest와 Data File이 존재하는지 확인한다.
3. 실행 엔진이 제공하는 register table 기능을 사용한다.
4. 테이블의 Row Count·Snapshot·Schema를 검증한다.
5. 복구된 테이블을 읽기 전용으로 열고 원인 분석을 끝낸다.
~~~

조사본에는 register_table 프로시저 예시가 포함되어 있으나, 이 기능의 이름과 인자 형식은 엔진과 Catalog 구현에 따라 달라질 수 있다.

[검토 필요: Polaris 1.7.0과 Spark·Trino에서 삭제된 Iceberg 테이블을 Metadata File로 재등록하는 공식 지원 방식과 권한을 확인해야 합니다.]

### 6.5 Iceberg 백업 기준

| 백업 대상 | 목적 |
|---|---|
| Metadata·Manifest·Data File | 테이블 파일 복구 |
| 객체 저장소 Versioning | 이전 버전 보호 |
| Cross-Region 또는 별도 저장소 복제 | 저장소 장애 대응 |
| Polaris Catalog DB | 테이블 등록·권한·Catalog 상태 복구 |
| Snapshot Tag 또는 별도 목록 | 특정 복구 지점 식별 |

백업이 존재하는 것과 복구가 검증된 것은 다르다. 정기적으로 별도의 테스트 환경에 복구해 Row Count, Schema, Snapshot, 대표 쿼리를 확인한다.

## 7. ClickHouse 적재 지연과 Serving 복구

### 7.1 증상 분류

ClickHouse 적재 지연은 Iceberg에서 읽는 단계, ClickHouse INSERT 단계, Merge 단계, 네트워크 단계, 리소스 단계로 나눈다.

| 증상 | 우선 확인 |
|---|---|
| Iceberg 최신 Snapshot이 보이지 않음 | Catalog·Reader·Spark/Flink Commit |
| INSERT가 오래 걸림 | 읽기량·네트워크·ClickHouse Query |
| INSERT는 성공했지만 조회가 오래됨 | Merge·ReplacingMergeTree·쿼리 조건 |
| 특정 파티션만 지연 | 작은 Part·Part merge·디스크 |
| Query가 실패함 | 메모리·권한·테이블·컬럼 |

### 7.2 ClickHouse 점검

~~~sql
SELECT
    query_id,
    query_start_time,
    query_duration_ms,
    read_rows,
    read_bytes,
    memory_usage,
    exception
FROM system.query_log
WHERE event_time >= now() - INTERVAL 30 MINUTE
ORDER BY query_start_time DESC;
~~~

System Table의 컬럼명과 기록 시점은 ClickHouse 설정과 버전에 따라 다를 수 있다. 대시보드 쿼리와 적재 Query를 구분할 수 있도록 query_id를 Airflow 또는 파이프라인 실행 ID와 연결한다.

### 7.3 중복 적재 대응

ClickHouse에 적재가 지연되어 재시도할 때 같은 기간을 다시 INSERT하면 중복이 생길 수 있다. 다음 중 하나를 선택한다.

- 대상 기간을 먼저 삭제한 뒤 INSERT
- 버전 컬럼과 키를 사용하는 테이블 엔진 설계
- 임시 테이블에 적재한 뒤 교체
- 적재 Batch ID를 기록하고 중복 Batch를 차단

ReplacingMergeTree를 사용하는 경우에도 merge가 완료되기 전 중복 행이 보일 수 있고, 조회 쿼리에 FINAL을 사용하면 비용이 증가할 수 있다. 따라서 재처리 정책과 조회 정책을 함께 검증한다.

### 7.4 ClickHouse 백업과 복구

조사본은 ClickHouse Native BACKUP·RESTORE와 별도 백업 도구를 복구 수단으로 제시한다.

~~~sql
BACKUP DATABASE mart
TO S3(
    'https://object-storage.example/backup/clickhouse/2026-08-30/',
    'access-key',
    'secret-key'
);

RESTORE DATABASE mart
FROM S3(
    'https://object-storage.example/backup/clickhouse/2026-08-30/',
    'access-key',
    'secret-key'
);
~~~

위 명령은 자격 증명과 S3 Endpoint를 코드에 기록하지 않는다는 원칙을 보여 주기 위한 예시다. 실제 백업 기능, S3 호환 Endpoint, 권한, 테이블 단위 복구 옵션은 ClickHouse 버전에서 확인한다.

[검토 필요: ClickHouse 26.6 기준 BACKUP·RESTORE의 S3 문법, Ozone S3 호환성, Object Storage 자격 증명 전달 방식과 복구 후 Merge 상태를 검증해야 합니다.]

## 8. 디스크 부족과 볼륨 장애

### 8.1 디스크 부족의 영향

로컬 데이터 플랫폼에서는 Docker 이미지·컨테이너 로그·PostgreSQL 볼륨·Kafka 로그·Iceberg 파일·ClickHouse Data Part가 같은 호스트 디스크를 사용할 수 있다. 디스크가 부족하면 단순히 새 파일을 만들지 못하는 데서 끝나지 않고 Checkpoint, Commit, Metadata DB, 로그 기록이 연쇄적으로 실패할 수 있다.

### 8.2 확인 명령

~~~bash
docker system df
docker system df -v
docker ps --size
docker compose exec clickhouse df -h
docker compose exec kafka df -h
~~~

호스트 운영체제의 디스크 사용량과 컨테이너 내부 Mount의 사용량을 모두 확인한다. Docker Desktop의 가상 디스크와 Windows 파일 시스템, macOS 파일 시스템의 실제 여유 공간이 다를 수 있다.

### 8.3 안전한 정리 순서

1. 어떤 디렉터리와 Volume이 용량을 사용하는지 식별한다.
2. 보존해야 할 데이터와 로그를 분류한다.
3. 중앙 로그 또는 백업이 확인된 로그만 정리한다.
4. Kafka 보존 정책과 Iceberg Snapshot 보존 정책을 확인한다.
5. 중지 가능한 비핵심 서비스를 중지한다.
6. 디스크를 확보한 뒤 서비스 상태와 데이터 정합성을 확인한다.

다음 명령은 사용하지 않는 리소스를 일괄 삭제할 수 있으므로 실행 전에 대상 목록을 확인한다.

~~~bash
docker system prune
~~~

Data Volume을 포함하는 정리 옵션은 Airflow·Kafka·PostgreSQL·ClickHouse 데이터까지 삭제할 수 있다. 사용자 확인 없이 Volume 삭제 명령을 실행하지 않는다.

### 8.4 로그 회전

Compose 서비스가 파일 로그를 남긴다면 회전과 보존 기간을 설정한다. Docker logging driver를 사용하는 예시는 다음과 같다.

~~~yaml
services:
  flink:
    logging:
      driver: json-file
      options:
        max-size: 10m
        max-file: "5"
~~~

이 설정은 Docker 로그의 최대 크기 예시다. 중앙 로그 보관이 필요한 경우 원본 보존 기간과 로컬 로그 회전의 관계를 정한다.

## 9. 메모리 부족과 OOM

### 9.1 OOM 증상

컨테이너가 갑자기 종료되고 Exit Code 137이 보이면 메모리 부족을 의심할 수 있다. 그러나 Exit Code만으로 원인을 확정하지 않는다. 프로세스가 SIGKILL된 이유, Docker Desktop의 메모리 한도, JVM Heap, Python 프로세스, ClickHouse Query 메모리를 함께 확인한다.

### 9.2 확인 명령

~~~bash
docker stats --no-stream
docker inspect <container_name> --format '{{.State.ExitCode}} {{.State.OOMKilled}}'
docker compose logs --tail=200 <service_name>
~~~

Windows 11과 Apple Silicon Mac에서는 Docker Desktop에 할당한 전체 메모리가 컨테이너별 사용량의 상한에 영향을 줄 수 있다. Spark·Flink·ClickHouse를 동시에 실행하는 전체 파이프라인은 최소 예제보다 훨씬 많은 메모리를 요구할 수 있다.

### 9.3 대응 순서

- 동시에 실행하는 서비스 수를 줄인다.
- Spark Executor·Driver와 Flink TaskManager의 메모리를 확인한다.
- ClickHouse 쿼리의 읽기 범위와 동시성을 줄인다.
- Superset Dashboard Chart 수와 결과 행 수를 줄인다.
- Kafka와 애플리케이션 버퍼가 과도하게 쌓이지 않는지 확인한다.
- Docker Desktop 메모리를 증설하고 동일 실험을 반복한다.

메모리를 무작정 늘리면 호스트 운영체제와 다른 컨테이너가 사용할 공간이 줄어든다. 서비스별 상한과 작업 병렬도를 함께 조정한다.

## 10. 볼륨 초기화와 복구

### 10.1 볼륨 초기화가 필요한 경우

실습 중 Schema가 꼬였거나 잘못된 테스트 데이터가 누적되어 처음부터 다시 시작해야 할 수 있다. 그러나 Volume 초기화는 복구가 아니라 데이터 삭제다.

실행 전에 다음을 확인한다.

- 어떤 서비스의 Volume을 삭제하는가?
- 백업·재현 가능한 Compose 파일이 있는가?
- 보존해야 할 로그·Metadata·Snapshot이 없는가?
- 초기화 후 다시 만들 수 있는 계정과 비밀값이 준비되었는가?

### 10.2 삭제 전 목록 확인

~~~bash
docker volume ls
docker compose config --volumes
docker compose down
~~~

여기까지는 컨테이너를 내리고 Volume 목록을 확인하는 단계다. 실제 Volume 삭제는 대상 이름을 명시하고 사용자 판단 후 실행한다.

~~~bash
docker volume rm <explicit_volume_name>
~~~

광범위한 prune 명령으로 모든 Volume을 삭제하면 다른 프로젝트의 데이터까지 사라질 수 있다. 이 장에서는 명시적으로 확인된 실습 Volume만 대상으로 한다.

### 10.3 초기화 후 확인

1. PostgreSQL Metadata Database가 새로 초기화되었는지 확인한다.
2. Kafka Topic과 Consumer Group을 다시 만든다.
3. Flink Checkpoint·Savepoint 경로를 정리하거나 새로 지정한다.
4. Polaris Catalog와 Iceberg Namespace를 확인한다.
5. ClickHouse Database·Table과 사용자 권한을 확인한다.
6. Airflow·Superset의 관리자와 Connection을 다시 설정한다.
7. 16장의 최소 파이프라인부터 다시 실행한다.

## 11. 구성 요소별 장애 복구

### 11.1 Flink

Flink 장애에서는 Job이 중지되었는지, Checkpoint가 최신인지, Kafka Offset과 Iceberg Commit이 어느 지점까지 진행되었는지 확인한다.

| 상태 | 대응 방향 |
|---|---|
| TaskManager만 재시작 | 최신 Checkpoint로 자동 복구되는지 확인 |
| Checkpoint는 있으나 Job 실패 | Checkpoint에서 재시작 |
| 계획된 변경 | Savepoint 생성 후 새 Job으로 이동 |
| Checkpoint 없음 | Kafka 보존 범위와 Source 재수집 가능성 확인 |
| Sink Commit 불명확 | Iceberg Snapshot과 이벤트 중복 검증 |

장기 실행 CDC Job은 재시작 전에 기존 Job이 완전히 종료되었는지 확인한다. 같은 Source 범위와 Sink를 가진 Job을 동시에 실행하면 중복 이벤트와 Commit 충돌이 발생할 수 있다.

### 11.2 Spark

Spark 배치가 실패하면 Driver 로그, Executor 메모리, Shuffle, Catalog 접근, 대상 Snapshot을 확인한다. Spark 작업이 실패했더라도 일부 임시 파일이 객체 저장소에 남을 수 있으므로 즉시 orphan cleanup을 실행하지 않는다.

Streaming Spark의 Checkpoint 경로를 사용할 경우 다음과 같은 형태를 확인한다.

~~~bash
spark-submit +  --conf spark.sql.streaming.checkpointLocation=object-storage-checkpoint-path +  /opt/spark/jobs/transform.py
~~~

이 명령은 Checkpoint 위치를 지정하는 개념적 예시다. 저장소 프로토콜과 Credential 설정은 Spark 배포 환경에 맞게 변경한다.

### 11.3 ClickHouse

ClickHouse 장애는 Query 오류와 Data Part·Merge·디스크 문제를 분리한다. 적재가 늦다고 해서 테이블을 삭제하거나 전체 재적재를 먼저 수행하지 않는다.

~~~sql
SELECT
    event_time,
    query_id,
    type,
    query_duration_ms,
    read_rows,
    memory_usage,
    exception
FROM system.query_log
WHERE event_time >= now() - INTERVAL 30 MINUTE
ORDER BY event_time DESC;
~~~

복구 후에는 다음을 확인한다.

- 적재 대상 기간의 행 수
- 집계 합계
- 마지막 처리 시각
- 동일 Batch 또는 키의 중복
- ClickHouse Merge 상태
- Superset에서 표시되는 최신 결과

### 11.4 Airflow

Airflow 장애는 DAG 정의 오류, Scheduler·Worker 오류, Metadata Database 오류, 외부 Operator 오류를 구분한다. DAG가 보이지 않는다고 외부 데이터가 손상된 것은 아니다.

확인 순서는 다음과 같다.

1. Dag Processor의 import 오류를 확인한다.
2. Scheduler heartbeat와 실행 대기 Task를 확인한다.
3. Worker와 Executor 상태를 확인한다.
4. Metadata Database 연결과 Migration 상태를 확인한다.
5. 외부 Spark·Flink·ClickHouse Job의 실제 상태를 확인한다.

Airflow Metadata Database는 다음과 같이 백업할 수 있다.

~~~bash
pg_dump +  -h airflow-postgres +  -U airflow +  -d airflow_db +  > airflow_db_backup.sql
~~~

복구 명령은 새 데이터베이스의 상태와 기존 서비스 중지 여부를 먼저 확인한 뒤 실행한다.

~~~bash
psql +  -h airflow-postgres +  -U airflow +  -d airflow_db +  < airflow_db_backup.sql
~~~

[검토 필요: Airflow 3.3.0의 Metadata Database 백업·복구 시 서비스 중지 조건, Migration 순서, Compose 서비스명과 공식 복구 절차를 최종 이미지에서 검증해야 합니다.]

### 11.5 Superset

Superset 장애는 Metadata Database, 연결 Driver, 생성 SQL, Cache, RLS로 나누어 확인한다.

| 증상 | 점검 |
|---|---|
| UI 접속 실패 | Superset 프로세스·포트·로그 |
| Database 연결 실패 | URI·Driver·네트워크·권한 |
| Chart 실패 | 생성 SQL·컬럼 타입·원본 데이터 |
| Dashboard 지연 | Chart 수·기간·Cache·ClickHouse |
| 사용자별 결과 차이 | 역할·Dataset 권한·RLS |
| 저장된 Chart 소실 | Metadata Database와 Volume |

Superset Metadata Database도 정기적으로 백업한다.

~~~bash
pg_dump +  -h superset-postgres +  -U superset +  -d superset_db +  > superset_db_backup.sql
~~~

Airflow와 Superset이 같은 PostgreSQL 서버를 사용하더라도 데이터베이스와 백업 파일을 분리한다.

## 12. 보안: RBAC·RLS·암호화·Credential

### 12.1 계층별 보안 경계

보안은 한 제품의 설정으로 완성되지 않는다.

| 계층 | 통제 예 |
|---|---|
| Source DB | 계정·권한·TLS·감사 |
| Kafka | Topic ACL·인증·전송 암호화 |
| Flink·Spark | Job 실행 권한·Secret 전달 |
| Polaris | Catalog·Namespace·Table RBAC |
| Object Storage | Bucket·Prefix·Credential |
| ClickHouse | Database·Table·Row 정책 |
| Superset | 사용자·역할·Dataset·RLS |

상위 계층의 화면 제한만으로 하위 저장소의 접근을 통제할 수 있다고 가정하지 않는다. 예를 들어 Superset에서 숨긴 Dataset이 Trino나 ClickHouse의 동일 계정으로 직접 조회될 수 있다면 RLS는 완전한 보안 경계가 아니다.

### 12.2 Polaris RBAC

조사본은 Polaris에서 Catalog·Namespace·Table 수준의 역할과 권한을 관리하는 구성을 제시한다. 실제 권한 이름은 Polaris 버전과 API에 따라 확인한다.

~~~text
역할: raw_writer
허용: Raw Namespace의 Table 생성·쓰기

역할: analytics_reader
허용: Analytics Namespace의 Table 읽기
~~~

Raw Writer와 Analytics Reader를 분리하면 분석 사용자가 원천 Raw를 수정하는 위험을 줄일 수 있다.

### 12.3 Credential Vending

Credential Vending은 처리 엔진에 장기 저장소 키를 배포하는 대신, 특정 위치와 시간으로 제한된 단기 자격 증명을 제공하는 패턴이다. 조사본은 Polaris의 Credential Vending과 Prefix 제한을 보안 항목으로 제시한다.

Credential을 설계할 때 확인할 항목은 다음과 같다.

- 발급 주체
- 유효 기간
- 허용된 Bucket·Prefix
- 읽기·쓰기 권한
- 만료·폐기 방식
- 발급과 사용 감사 로그

[검토 필요: Polaris 1.7.0의 Credential Vending API, allowedLocations 검증, Ozone S3 호환 저장소의 지원 범위와 감사 이벤트를 공식 문서와 실제 환경에서 확인해야 합니다.]

### 12.4 Iceberg 암호화

조사본은 Iceberg v3의 테이블 수준 암호화와 KMS 연계를 보안 항목으로 제시한다. 이 기능의 실제 구현·실행 엔진·키 관리 범위는 버전별로 확인해야 한다.

저장소 암호화, 전송 암호화, 애플리케이션·Catalog 권한은 서로 다른 통제다. 하나를 적용했다고 나머지가 자동으로 해결되는 것은 아니다.

[검토 필요: Apache Iceberg 1.11.0에서 암호화 기능의 정확한 상태, 지원되는 암호화 방식, Spark·Flink·Trino·Polaris 연계와 KMS 요구사항을 공식 문서로 보강해야 합니다.]

### 12.5 Superset RLS

Superset RLS는 Dataset에 SQL 조건을 적용해 역할별 행 접근 범위를 줄이는 기능이다.

~~~sql
country = 'KR'
~~~

RLS를 적용한 뒤에는 Dashboard뿐 아니라 SQL Lab, Virtual Dataset, CSV 다운로드, API 경로를 테스트한다. RLS의 정확한 적용 범위와 우회 가능성은 Superset 버전과 권한 설정에 따라 달라질 수 있다.

조사본에는 Superset 4.1.3의 RLS 우회 취약점에 대한 경고가 포함되어 있다. 이 장의 기준 버전이 4.1.2 또는 6.1.0으로 충돌하므로, 해당 취약점과 수정 버전은 출판 전에 공식 보안 공지와 NVD에서 확인한다.

[검토 필요: CVE-2026-23984의 영향 버전·수정 버전·공식 advisory, Superset 6.1.0의 해당 여부를 확인해야 합니다.]

## 13. 감사 로그와 컴플라이언스

### 13.1 감사 로그의 목적

운영 로그가 장애 원인을 찾기 위한 것이라면, 감사 로그는 누가 언제 어떤 데이터와 권한을 사용했는지 추적하기 위한 기록이다. 두 로그를 같은 보존 정책으로 처리하지 않는다.

감사 이벤트에는 가능한 한 다음 정보를 포함한다.

- 주체 사용자·서비스 계정
- 요청 시각과 시간대
- 대상 Catalog·Namespace·Table
- 요청 유형: 읽기·쓰기·삭제·스키마 변경·권한 변경
- 결과: 성공·실패·거부
- Source IP 또는 실행 환경
- Job·Query·DAG·Dashboard 식별자
- 오류와 거부 사유

### 13.2 감사 로그 아키텍처

~~~mermaid
flowchart TD
    A["Flink and Spark"] --> D["Polaris or storage"]
    B["ClickHouse"] --> E["Query audit"]
    C["Superset"] --> E
    D --> F["Central audit store"]
    E --> F
    F --> G["Retention and review"]
~~~

Polaris REST Catalog를 통과하는 Catalog 상호작용, ClickHouse Query, Superset 사용자 작업을 서로 연결할 수 있도록 공통 실행 ID를 기록한다.

### 13.3 규제 요구와 기술 통제

| 요구 영역 | 고려할 통제 |
|---|---|
| 개인정보 | PII 분류·최소 권한·접근 로그·보존·삭제 |
| 결제 정보 | 암호화·접근 통제·변경 이력 |
| 의료 정보 | 사용자·목적별 접근·RLS·감사 |
| 변경 관리 | Schema·DAG·권한 변경 승인 기록 |
| 보존 정책 | Snapshot·Log·Backup 보존 기간과 삭제 기록 |

GDPR·PCI-DSS·HIPAA·SOC 2의 구체적인 준수 여부는 기술 설정만으로 판단할 수 없다. 적용 법령, 데이터 분류, 조직 정책, 감사 범위를 함께 검토해야 한다.

[검토 필요: 이 장에서 언급하는 규제별 요구사항은 법률·감사 자문을 대체하지 않으므로, 출판본에서는 법률적 준수 보장처럼 표현하지 않도록 검토해야 합니다.]

### 13.4 감사 기록 보존과 삭제

감사 로그도 개인정보와 보안 정보를 포함할 수 있다. 무기한 보존이 항상 올바른 것은 아니다. 보존 기간, 접근 권한, 무결성 보호, 삭제 승인과 삭제 이력을 함께 정한다.

## 14. 단계별 장애 복구 실습

### 14.1 실습 전 안전 조건

이 절의 실습은 학습용 데이터와 테스트 Volume을 대상으로 한다. 운영 데이터나 공유 서버에서 같은 명령을 실행하지 않는다.

실습 전 다음을 확인한다.

- Compose 파일과 환경 파일을 백업했다.
- Kafka·Iceberg·PostgreSQL·ClickHouse의 데이터 경로를 식별했다.
- 테스트용 Source와 Table을 사용한다.
- 재현 가능한 입력 데이터를 보관했다.
- 삭제 명령의 대상 이름을 확인했다.

### 14.2 Healthcheck 실패 재현

1. PostgreSQL 또는 Redis 서비스를 중지한다.
2. Superset의 healthcheck 상태를 관찰한다.
3. Compose events와 서비스 로그를 저장한다.
4. 서비스를 다시 시작한다.
5. Superset Metadata Database 연결을 확인한다.

~~~bash
docker compose stop postgres
docker compose ps
docker compose events --since 5m
docker compose logs --tail=100 superset
docker compose start postgres
docker compose ps
~~~

서비스가 다시 healthy가 되더라도 Dashboard·Dataset·사용자 정보가 유지되는지 확인한다.

### 14.3 Kafka lag 관찰

1. Flink CDC Job의 Sink 또는 처리 서비스를 일시적으로 중지한다.
2. Source에 테스트 변경을 입력한다.
3. Consumer Group lag이 증가하는지 확인한다.
4. 처리 서비스를 다시 시작한다.
5. lag 감소와 Iceberg Raw 반영을 확인한다.

~~~bash
docker compose exec kafka kafka-consumer-groups.sh +  --bootstrap-server kafka:9092 +  --describe +  --group flink-cdc-group
~~~

Topic과 Group 이름은 실제 Compose·Flink 설정에 맞게 변경한다.

### 14.4 ClickHouse 적재 지연 관찰

1. Iceberg에서 ClickHouse로 복사하는 Task를 중지한다.
2. Source와 Iceberg의 최신 시각을 확인한다.
3. ClickHouse의 최신 시각이 멈추는지 확인한다.
4. 적재 Task를 재개한다.
5. 중복과 합계 오류가 없는지 검증한다.

이 실습은 “Dashboard가 오래된 것”과 “Iceberg 자체가 오래된 것”을 구분하는 연습이다.

### 14.5 복구 후 검증

복구 완료의 조건을 서비스가 running인 것으로 끝내지 않는다.

~~~text
1. 모든 필수 컨테이너가 running 또는 healthy인가?
2. Kafka Consumer lag이 감소하고 있는가?
3. Flink Checkpoint가 새로 성공했는가?
4. Iceberg의 최신 Snapshot이 예상 시각 이후인가?
5. Clean의 중복·NULL·DELETE 상태가 정상인가?
6. ClickHouse의 Row Count와 Sum이 일치하는가?
7. Superset Dashboard가 최신 기준 시각을 표시하는가?
8. RLS 사용자에게 의도한 행만 노출되는가?
9. 장애 로그와 복구 조치가 기록되었는가?
~~~

## 15. 장애 대응 Runbook

### 15.1 공통 Runbook

| 순서 | 행동 | 산출물 |
|---:|---|---|
| 1 | 증상과 영향 기록 | Incident 요약 |
| 2 | 추가 쓰기·삭제 위험 제한 | 보호 조치 |
| 3 | 상태·로그·최근 변경 수집 | 증거 묶음 |
| 4 | 장애 계층 분리 | 원인 후보 |
| 5 | 복구 계획 승인 | 실행 명령과 롤백 |
| 6 | 최소 범위 복구 | 복구 상태 |
| 7 | 정합성 검증 | 검증 결과 |
| 8 | 재발 방지 조치 | Action item |

### 15.2 Iceberg 복구 Runbook

- 현재 Catalog pointer와 최근 Snapshot을 기록한다.
- 영향을 받은 Snapshot과 정상 Snapshot을 구분한다.
- Reader와 Writer를 확인한다.
- Snapshot rollback 가능성을 판단한다.
- Metadata·Manifest·Data File의 존재를 확인한다.
- rollback 후 대표 쿼리와 Row Count를 검증한다.
- Orphan cleanup은 복구 검증 후 별도 승인으로 실행한다.

### 15.3 CDC 복구 Runbook

- Source의 변경 로그 보존 범위를 확인한다.
- Kafka Topic과 Consumer Group Offset을 기록한다.
- Flink Job과 Checkpoint·Savepoint 상태를 확인한다.
- 중복 Job을 종료하거나 제출을 차단한다.
- 재처리 범위와 중복 제거 키를 결정한다.
- Clean·Mart·ClickHouse 순서로 복구한다.

### 15.4 보안 장애 Runbook

- 노출된 Token·Password·Credential을 즉시 폐기한다.
- 영향받은 사용자·서비스 계정을 식별한다.
- Polaris·ClickHouse·Superset의 권한 변경 이력을 보존한다.
- RLS·RBAC 우회 가능성을 재현하지 말고 테스트 계정으로 검증한다.
- 필요한 경우 해당 Dataset 또는 Catalog를 일시적으로 읽기 제한한다.
- 감사 로그와 조치 이력을 별도 보존한다.

## 16. 핵심 정리

- 장애 대응은 재시작보다 영향 범위 고정과 증거 보존이 먼저다.
- Docker healthcheck가 실패했다는 사실과 애플리케이션 데이터가 손상되었다는 사실은 다르다.
- Kafka lag은 데이터 유실을 의미하지 않지만, 보존 기간을 넘기면 복구 가능성이 줄어든다.
- Flink Checkpoint와 Savepoint는 서로 다른 목적을 가지므로 복구 계획에서 구분한다.
- Iceberg 복구는 Data File만이 아니라 Catalog·Metadata·Snapshot·Manifest·Data File 관계를 함께 보존해야 한다.
- ClickHouse 적재 재시도는 중복을 만들 수 있으므로 Batch·키·기간 교체 전략이 필요하다.
- 디스크 부족과 OOM은 여러 서비스의 연쇄 장애로 이어질 수 있다.
- Volume 초기화는 복구가 아니라 데이터 삭제이므로 대상과 백업을 확인한 뒤 실행한다.
- Airflow·Superset의 Metadata Database는 정기적으로 백업하고, 복구 테스트를 수행한다.
- RBAC·Credential Vending·암호화·RLS·감사 로그는 서로 다른 보안 통제다.
- 복구 완료는 컨테이너가 살아난 상태가 아니라 데이터 정합성과 보안 정책을 검증한 상태다.

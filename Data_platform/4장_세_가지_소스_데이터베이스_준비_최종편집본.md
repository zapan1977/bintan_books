# 4장. 세 가지 소스 데이터베이스 준비

이 장에서는 데이터 플랫폼의 입력 지점이 되는 세 가지 소스 데이터베이스를 구성합니다. 대상은 Percona Server for MySQL, MongoDB Community Server, PostgreSQL입니다. 세 데이터베이스는 같은 주문 업무를 저장하지만, 변경 사항을 기록하고 외부 파이프라인으로 전달하는 방식은 서로 다릅니다.

이 책의 실습에서는 각 데이터베이스를 Docker 컨테이너로 실행합니다. MySQL은 바이너리 로그(binlog), MongoDB는 Replica Set과 Change Streams, PostgreSQL은 WAL과 logical decoding을 사용합니다. 이 설정은 뒤에서 Apache Kafka와 Flink CDC를 연결할 때 필요한 기반이 됩니다.

## 이 장의 목표

- 세 가지 소스 데이터베이스를 Docker Compose로 실행합니다.
- 각 데이터베이스의 CDC 전제 조건을 설정하고 상태를 확인합니다.
- 관계형 데이터베이스와 문서 데이터베이스에 같은 업무 개념을 표현합니다.
- 초기화 스크립트, 합성 데이터, 데이터 재생성 절차를 구성합니다.
- Windows 11의 WSL2 환경과 Apple Silicon 환경에서 발생할 수 있는 차이를 이해합니다.

> **집필 기준과 버전 확인**
>
> 제공된 조사 자료에는 Percona Server for MySQL 8.4.11과 8.4.11-11, MongoDB 8.0-ubi8-slim과 8.0.29-ubi8, PostgreSQL 16.15와 17.11이 함께 제시되어 있습니다. 이 원고의 예제는 Percona Server for MySQL 8.4.11-11, MongoDB Community Server 8.0.29-ubi8, PostgreSQL 17.11을 기준으로 작성합니다. 정확한 태그와 멀티 아키텍처 매니페스트는 집필 시점에 다시 확인해야 합니다. [검토 필요: 공식 레지스트리의 최종 이미지 태그와 PostgreSQL 기준 버전]

## 1. 소스 데이터베이스의 역할

소스 데이터베이스는 애플리케이션의 업무 데이터를 처음 기록하는 저장소입니다. 이 책에서는 주문 관리 시스템을 예제로 사용합니다. 고객, 제품, 주문, 주문 항목을 데이터베이스에 저장한 뒤, 각 데이터베이스에서 발생한 INSERT, UPDATE, DELETE를 변경 데이터로 읽어 분석 플랫폼으로 전달합니다.

세 데이터베이스를 함께 사용하는 이유는 특정 데이터베이스의 사용법만 익히기 위해서가 아닙니다. 같은 업무 변화가 데이터베이스별로 어떻게 기록되는지 비교하고, 이후의 CDC 파이프라인이 서로 다른 변경 기록 형식을 어떻게 다루는지 확인하기 위해서입니다.

| 소스 데이터베이스 | 변경 기록의 출발점 | 이 장에서 구성할 핵심 요소 |
|---|---|---|
| Percona Server for MySQL | 바이너리 로그 | ROW 형식, 전체 행 이미지, GTID 관련 설정 |
| MongoDB Community Server | oplog를 기반으로 한 Change Streams | 단일 노드 Replica Set, oplog, 변경 스트림 |
| PostgreSQL | WAL과 logical decoding | logical WAL, replication slot, publication |

세 시스템 모두 데이터 변경을 외부로 전달할 수 있지만, CDC가 자동으로 활성화되는 것은 아닙니다. 소스 데이터베이스가 변경 로그를 남기도록 설정하고, CDC 사용자가 필요한 권한을 갖도록 구성해야 합니다.

## 2. 프로젝트 디렉터리 구성

실습 프로젝트의 디렉터리는 서비스 정의, 비밀 정보, 초기화 스크립트를 분리하는 형태로 구성합니다.

~~~text
data-platform/
├── compose.yaml
├── .env.example
├── .env
├── secrets/
│   ├── mysql_root_password.txt
│   ├── mysql_password.txt
│   ├── mongo_root_password.txt
│   └── postgres_password.txt
└── init-scripts/
    ├── mysql/
    │   ├── 01-create-tables.sql
    │   ├── 02-create-users.sql
    │   └── 03-insert-sample-data.sql
    ├── mongodb/
    │   ├── 01-create-collections.js
    │   ├── 02-create-users.js
    │   └── 03-insert-sample-data.js
    └── postgres/
        ├── 01-create-tables.sql
        ├── 02-create-users.sql
        └── 03-insert-sample-data.sql
~~~

초기화 파일은 번호를 붙여 실행 순서를 명확하게 합니다. 데이터베이스 이미지의 엔트리포인트는 데이터 디렉터리가 비어 있을 때 초기화 디렉터리의 파일을 실행합니다. 이미 데이터가 존재하는 named volume을 다시 연결하면 초기화 파일이 다시 실행되지 않습니다. 따라서 초기화 스크립트를 수정한 뒤에는 데이터 재생성 절차를 별도로 수행해야 합니다.

> **보안 주의**
>
> 이 책의 비밀번호는 로컬 학습을 위한 예시입니다. `.env`와 `secrets/` 파일은 버전 관리 저장소에 커밋하지 않습니다. 실습 저장소에는 실제 비밀번호 대신 `.env.example`과 비밀 파일의 예시 이름만 제공합니다.

## 3. Percona Server for MySQL 준비

### 3.1 이미지와 CDC 전제 조건

Percona Server for MySQL은 MySQL과 호환되는 서버로, 이 책에서는 8.4 계열 이미지를 사용합니다. 수집 자료에서는 8.4 계열을 신규 구성의 기준으로 제시하고 있으며, Apple Silicon에서 사용할 수 있는 ARM64 이미지도 함께 언급합니다.

MySQL의 변경 사항을 CDC 커넥터가 읽으려면 바이너리 로그가 필요합니다. 행 단위 변경을 기록하는 ROW 형식과 전체 행 이미지를 사용하는 FULL 설정은 변경 전후의 값을 해석하는 데 사용됩니다.

| 설정 | 실습 기준 | 목적 |
|---|---|---|
| `binlog_format` | `ROW` | SQL 문장이 아니라 행 변경을 기록합니다. |
| `binlog_row_image` | `FULL` | 변경 행의 전체 이미지를 기록합니다. |
| `binlog_row_metadata` | `FULL` 권장 | 컬럼 메타데이터를 CDC 도구가 해석하는 데 도움을 줍니다. |
| `gtid_mode` | `ON` 권장 | GTID 기반 위치 추적과 복제 구성을 준비합니다. |
| `enforce_gtid_consistency` | `ON` 권장 | GTID 사용 시 일관성을 강제합니다. |
| `server_id` | 고유 값 지정 | 복제 토폴로지에서 서버를 식별합니다. |
| `sync_binlog` | `1` 권장 | 트랜잭션 단위의 바이너리 로그 동기화를 명시합니다. |

`binlog_row_image=MINIMAL`은 변경된 컬럼과 식별에 필요한 정보만 기록할 수 있으므로, 이 책의 초기 CDC 실습에서는 사용하지 않습니다. 실제 커넥터가 요구하는 행 이미지와 메타데이터는 커넥터 버전에 따라 다시 확인해야 합니다. (출처: [Percona PMM의 binlog_row_image 문서](https://docs.percona.com/percona-monitoring-and-management/3/advisors/checks/binlog-row-image.html), 제공된 4장 조사 자료)

### 3.2 Compose 서비스 정의

다음은 MySQL 서비스의 핵심 구성입니다. 비밀번호는 파일 기반 Secret으로 전달하도록 작성했습니다.

~~~yaml
services:
  mysql:
    image: percona/percona-server:8.4.11-11
    container_name: mysql
    environment:
      MYSQL_ROOT_PASSWORD_FILE: /run/secrets/mysql_root_password
      MYSQL_DATABASE: sourcedb
      MYSQL_USER: cdc_user
      MYSQL_PASSWORD_FILE: /run/secrets/mysql_password
    command:
      - --server-id=101
      - --gtid-mode=ON
      - --enforce-gtid-consistency=ON
      - --binlog_format=ROW
      - --binlog_row_image=FULL
      - --binlog_row_metadata=FULL
      - --binlog_expire_logs_seconds=604800
      - --sync_binlog=1
    ports:
      - "3306:3306"
    volumes:
      - mysql-data:/var/lib/mysql
      - ./init-scripts/mysql:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h localhost -u root -p$$(cat /run/secrets/mysql_root_password)"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped
    secrets:
      - mysql_root_password
      - mysql_password

volumes:
  mysql-data:

secrets:
  mysql_root_password:
    file: ./secrets/mysql_root_password.txt
  mysql_password:
    file: ./secrets/mysql_password.txt
~~~

`binlog_expire_logs_seconds`는 실습 환경에서 바이너리 로그가 무한히 쌓이지 않도록 보관 기간을 지정합니다. 예제의 604800초는 7일입니다. CDC 커넥터가 장기간 중단될 수 있는 운영 환경에서는 보관 기간을 처리 지연과 복구 정책에 맞춰 정해야 합니다. 이 책의 값은 운영 권고값이 아니라 로컬 실습값입니다.

### 3.3 초기 스키마와 사용자

MySQL 초기화 파일에는 주문 업무에 필요한 테이블을 생성합니다. 관계형 모델에서는 주문과 주문 항목을 별도 테이블로 관리하고 외래 키로 관계를 표현합니다.

~~~sql
CREATE DATABASE IF NOT EXISTS sourcedb;
USE sourcedb;

CREATE TABLE IF NOT EXISTS customers (
    customer_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS products (
    product_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS orders (
    order_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    customer_id BIGINT NOT NULL,
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    status ENUM('PENDING', 'CONFIRMED', 'SHIPPED', 'DELIVERED', 'CANCELLED')
        DEFAULT 'PENDING',
    total_amount DECIMAL(10, 2) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT fk_orders_customer
        FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
) ENGINE=InnoDB;

CREATE TABLE IF NOT EXISTS order_items (
    order_item_id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    unit_price DECIMAL(10, 2) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT fk_order_items_order
        FOREIGN KEY (order_id) REFERENCES orders(order_id),
    CONSTRAINT fk_order_items_product
        FOREIGN KEY (product_id) REFERENCES products(product_id)
) ENGINE=InnoDB;
~~~

CDC 사용자에게는 바이너리 로그를 읽고 소스 테이블을 조회하는 권한이 필요합니다. 수집 자료에서는 `REPLICATION SLAVE`, `REPLICATION CLIENT`, `SELECT` 등을 제시합니다.

~~~sql
CREATE USER IF NOT EXISTS 'cdc_user'@'%' IDENTIFIED BY 'cdc_password';
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'cdc_user'@'%';
GRANT SELECT ON sourcedb.* TO 'cdc_user'@'%';
FLUSH PRIVILEGES;
~~~

> **권한 검토**
>
> 실제 사용할 CDC 커넥터가 요구하는 최소 권한은 커넥터 버전과 초기 스냅숏 방식에 따라 달라질 수 있습니다. 위 권한은 제공된 조사 자료에 기반한 실습 예시이며, 운영 환경에서는 전체 서버 권한을 그대로 사용하지 않고 커넥터의 최소 권한을 다시 검토해야 합니다. [검토 필요: 선택한 Flink CDC 커넥터 버전의 Percona 권한 요구사항]

### 3.4 상태 확인

컨테이너가 실행된 뒤 다음 명령으로 CDC 관련 설정을 확인합니다.

~~~bash
docker exec mysql mysql -u root -psecret -e "SHOW VARIABLES LIKE 'log_bin';"
docker exec mysql mysql -u root -psecret -e "SHOW VARIABLES LIKE 'binlog_format';"
docker exec mysql mysql -u root -psecret -e "SHOW VARIABLES LIKE 'binlog_row_image';"
docker exec mysql mysql -u root -psecret -e "SHOW VARIABLES LIKE 'gtid_mode';"
docker exec mysql mysql -u root -psecret -e "SHOW BINARY LOGS;"
docker exec mysql mysql -u root -psecret -e "SHOW GRANTS FOR 'cdc_user'@'%';"
~~~

Secret을 사용하는 Compose 설정에서는 책의 단순한 확인 명령 대신 환경에 맞는 비밀번호 전달 방법을 적용해야 합니다. 위 명령의 `secret`은 읽기 쉬운 실습 예시일 뿐입니다.

## 4. MongoDB Community Server 준비

### 4.1 Change Streams와 Replica Set

MongoDB Change Streams는 데이터 변경을 애플리케이션이나 CDC 커넥터가 구독할 수 있게 하는 기능입니다. 수집 자료에서는 Change Streams를 standalone 서버에서 사용할 수 없고, Replica Set 또는 Sharded Cluster가 필요하다고 설명합니다.

로컬에서는 여러 노드로 구성된 운영용 Replica Set을 만들지 않고 단일 노드 Replica Set을 사용합니다. 단일 노드 구성은 Change Streams의 실행 조건을 충족시키기 위한 학습용 구성입니다. 장애 허용이나 고가용성을 제공하는 운영 클러스터로 해석해서는 안 됩니다. (출처: 제공된 4장 조사 자료의 MongoDB Change Streams 조사 결과)

Replica Set을 실행하려면 서버에 `--replSet rs0` 옵션을 지정한 뒤, 서버가 준비된 시점에 `rs.initiate()`를 실행해야 합니다. 이 초기화는 MySQL이나 PostgreSQL의 단순한 스키마 초기화와 실행 시점이 다르므로 별도의 일회성 초기화 서비스로 분리합니다.

### 4.2 Compose 서비스 정의

~~~yaml
services:
  mongodb:
    image: mongodb/mongodb-community-server:8.0.29-ubi8
    container_name: mongodb
    command:
      - --replSet
      - rs0
      - --oplogSize
      - "128"
    environment:
      MONGO_INITDB_ROOT_USERNAME: admin
      MONGO_INITDB_ROOT_PASSWORD_FILE: /run/secrets/mongo_root_password
      MONGO_INITDB_DATABASE: sourcedb
    ports:
      - "27017:27017"
    volumes:
      - mongodb-data:/data/db
      - mongodb-config:/data/configdb
      - ./init-scripts/mongodb:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD", "mongosh", "--eval", "db.adminCommand({ ping: 1 })"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s
    restart: unless-stopped
    secrets:
      - mongo_root_password

  mongodb-init:
    image: mongodb/mongodb-community-server:8.0.29-ubi8
    container_name: mongodb-init
    depends_on:
      mongodb:
        condition: service_healthy
    command: >
      mongosh --host mongodb --port 27017
      --username admin
      --password "$$(cat /run/secrets/mongo_root_password)"
      --authenticationDatabase admin
      --eval "rs.initiate({
        _id: 'rs0',
        members: [{ _id: 0, host: 'mongodb:27017' }]
      });"
    restart: "no"
    secrets:
      - mongo_root_password

volumes:
  mongodb-data:
  mongodb-config:

secrets:
  mongo_root_password:
    file: ./secrets/mongo_root_password.txt
~~~

실습용 oplog 크기는 예제에서 128MB로 지정했습니다. 수집 자료에서는 운영 환경에서 복제 지연을 고려해 더 큰 크기를 권장하지만, 로컬 환경에 그대로 적용할 수 있는 일반값으로 확정된 것은 아닙니다. 실제 필요한 oplog 크기는 변경량, CDC 중단 시간, 디스크 용량을 기준으로 정해야 합니다. [추가 자료 조사 필요: 로컬 실습 데이터량에 따른 MongoDB oplog 크기 산정 기준]

`mongodb-init`는 초기화 명령을 실행하는 일회성 서비스입니다. 로그에서 Replica Set이 초기화되었는지 확인한 뒤, 이후 서비스 상태를 조회합니다. 데이터 volume이 이미 초기화되어 있으면 동일한 `rs.initiate()` 명령이 다시 실행될 때 결과가 달라질 수 있으므로, 반복 실행을 위한 idempotent 스크립트는 별도로 보강해야 합니다.

### 4.3 문서 모델과 Change Streams 사용자

MongoDB에서는 주문 항목을 `orders` 문서 안의 `items` 배열에 임베드합니다. 고객과 제품은 별도 컬렉션에 두고 식별자만 참조합니다. 이 모델은 관계형 데이터베이스의 `order_items` 테이블과 같은 정보를 표현하지만, 저장 단위는 하나의 주문 문서입니다.

~~~javascript
db = db.getSiblingDB("sourcedb");

db.createCollection("customers", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["customer_id", "name", "email"],
      properties: {
        customer_id: { bsonType: "long" },
        name: { bsonType: "string" },
        email: { bsonType: "string" },
        created_at: { bsonType: "date" },
        updated_at: { bsonType: "date" }
      }
    }
  }
});

db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: [
        "order_id", "customer_id", "order_date", "status",
        "total_amount", "items"
      ],
      properties: {
        order_id: { bsonType: "long" },
        customer_id: { bsonType: "long" },
        order_date: { bsonType: "date" },
        status: {
          bsonType: "string",
          enum: ["PENDING", "CONFIRMED", "SHIPPED", "DELIVERED", "CANCELLED"]
        },
        total_amount: { bsonType: "decimal" },
        items: {
          bsonType: "array",
          items: {
            bsonType: "object",
            required: ["product_id", "quantity", "unit_price"],
            properties: {
              product_id: { bsonType: "long" },
              quantity: { bsonType: "int" },
              unit_price: { bsonType: "decimal" }
            }
          }
        }
      }
    }
  }
});

db.customers.createIndex({ customer_id: 1 }, { unique: true });
db.orders.createIndex({ order_id: 1 }, { unique: true });
db.orders.createIndex({ customer_id: 1 });
db.orders.createIndex({ order_date: -1 });
~~~

수집 자료에는 CDC 사용자를 `read` 및 `clusterMonitor` 역할로 만드는 예와 `readWrite` 및 `dbAdmin` 역할을 부여하는 예가 함께 있습니다. 이 차이는 사용하는 커넥터와 초기 스냅숏·메타데이터 조회 범위에 따라 확인해야 합니다. 다음 예는 상대적으로 범위를 좁힌 구성에서 시작하고, 연결 실패 시 선택한 커넥터의 권한 요구사항을 확인하는 흐름으로 제시합니다.

~~~javascript
use admin;

db.createUser({
  user: "cdc_user",
  pwd: "cdc_password",
  roles: [
    { role: "read", db: "sourcedb" },
    { role: "clusterMonitor", db: "admin" }
  ]
});
~~~

> **권한 검토**
>
> 제공된 자료에는 MongoDB CDC 사용자의 권한 구성이 일치하지 않습니다. 실제 Flink CDC 커넥터가 Change Streams와 초기 스냅숏을 위해 요구하는 권한을 확인한 뒤 이 예제를 확정해야 합니다. [검토 필요: 선택한 MongoDB CDC 커넥터 버전의 최소 권한 및 `fullDocument`·before 이미지 설정]

### 4.4 Replica Set과 Change Streams 확인

먼저 Replica Set 상태를 확인합니다.

~~~bash
docker exec mongodb mongosh \
  -u admin -p secret \
  --authenticationDatabase admin \
  --eval "rs.status()"
~~~

별도 터미널에서 Change Stream을 열고, 다른 터미널에서 주문을 변경합니다.

~~~javascript
use sourcedb;

const cursor = db.orders.watch();
cursor.forEach(change => printjson(change));
~~~

변경을 발생시키는 예는 다음과 같습니다.

~~~javascript
use sourcedb;

db.orders.insertOne({
  order_id: NumberLong(1),
  customer_id: NumberLong(1),
  order_date: new Date(),
  status: "PENDING",
  total_amount: Decimal128("1029.98"),
  items: [
    { product_id: NumberLong(1), quantity: 1, unit_price: Decimal128("999.99") },
    { product_id: NumberLong(2), quantity: 1, unit_price: Decimal128("29.99") }
  ]
});

db.orders.updateOne(
  { order_id: NumberLong(1) },
  { $set: { status: "SHIPPED", updated_at: new Date() } }
);

db.orders.deleteOne({ order_id: NumberLong(1) });
~~~

Change Stream 이벤트에는 변경 유형과 문서 식별자 등이 포함됩니다. `fullDocument`를 이용한 변경 후 문서나 before 이미지의 제공 여부는 MongoDB 버전, 컬렉션 설정, 구독 옵션에 영향을 받으므로 이 책에서는 해당 기능을 모든 환경에서 자동으로 보장한다고 표현하지 않습니다. [검토 필요: MongoDB 8.0 공식 문서와 선택한 커넥터의 before 이미지 지원 범위]

## 5. PostgreSQL 준비

### 5.1 logical replication의 전제 조건

PostgreSQL은 WAL을 기반으로 변경 사항을 기록합니다. CDC가 logical decoding을 사용하려면 `wal_level`을 `logical`로 설정하고, replication slot과 WAL sender를 위한 수를 지정해야 합니다.

| 설정 | 실습 기준 | 설명 |
|---|---|---|
| `wal_level` | `logical` | logical decoding에 필요한 WAL 수준입니다. |
| `max_replication_slots` | `10` | CDC 커넥터가 사용할 replication slot 수를 고려합니다. |
| `max_wal_senders` | `10` | 복제·CDC 연결에 사용할 WAL sender 수를 고려합니다. |
| `max_slot_wal_keep_size` | `100MB` | 실습 중 slot이 WAL을 무제한 보존하지 않도록 제한합니다. |
| `wal_compression` | `lz4` 선택 | WAL 용량을 줄이기 위한 선택 설정입니다. |

`wal_level`처럼 서버 시작 시 적용되는 설정을 변경하면 PostgreSQL을 재시작해야 합니다. replication slot이 소비되지 않으면 WAL이 계속 보존될 수 있으므로, 실습에서도 slot과 WAL 보존량을 함께 확인해야 합니다. (출처: [PostgreSQL logical replication 설정 문서](https://www.postgresql.org/docs/current/runtime-config-replication.html), [logical decoding 개념 문서](https://www.postgresql.org/docs/19/logicaldecoding-explanation.html))

### 5.2 Compose 서비스 정의

services:

      - postgres_password

volumes:
  postgres-data:

~~~

`max_slot_wal_keep_size=100MB`는 데이터 변경량이 작은 로컬 실습을 위한 예시입니다. 이 값을 운영 환경에 그대로 사용하면 CDC 중단 시 재동기화가 필요해질 수 있고, 반대로 너무 크게 설정하면 디스크를 압박할 수 있습니다. 운영값은 데이터 변경량과 최대 허용 중단 시간을 기준으로 산정해야 합니다. [추가 자료 조사 필요: 실제 변경량에 따른 PostgreSQL slot 보존량 산정]

### 5.3 스키마, replication role, publication

PostgreSQL에서는 MySQL과 유사한 관계형 구조를 사용합니다. 아래 예제는 테이블과 인덱스를 만들고, logical replication에 사용할 역할과 publication을 구성합니다.

~~~sql
CREATE TABLE IF NOT EXISTS customers (
    customer_id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS products (
    product_id BIGSERIAL PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price NUMERIC(10, 2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS orders (
    order_id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(customer_id),
    order_date TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
        CHECK (status IN ('PENDING', 'CONFIRMED', 'SHIPPED', 'DELIVERED', 'CANCELLED')),
    total_amount NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE IF NOT EXISTS order_items (
    order_item_id BIGSERIAL PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(order_id),
    product_id BIGINT NOT NULL REFERENCES products(product_id),
    quantity INT NOT NULL,
    unit_price NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_orders_customer_id ON orders(customer_id);
CREATE INDEX IF NOT EXISTS idx_orders_status ON orders(status);
CREATE INDEX IF NOT EXISTS idx_orders_created_at ON orders(created_at DESC);
~~~

CDC 역할에는 데이터베이스 연결과 스키마 조회 권한, replication 로그인 권한이 필요합니다. publication 생성은 초기화 스크립트를 실행하는 관리자 역할로 수행하고, CDC 역할에는 필요한 권한만 부여하는 방식을 사용할 수 있습니다.

~~~sql
CREATE ROLE cdc_user WITH REPLICATION LOGIN PASSWORD 'cdc_password';
GRANT CONNECT ON DATABASE sourcedb TO cdc_user;
GRANT USAGE ON SCHEMA public TO cdc_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO cdc_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
    GRANT SELECT ON TABLES TO cdc_user;

CREATE PUBLICATION cdc_publication FOR ALL TABLES;
~~~

기본 Replica Identity는 기본 키를 기준으로 UPDATE와 DELETE의 행을 식별합니다. 기본 키가 없는 테이블에서 이전 행을 식별해야 한다면 `REPLICA IDENTITY FULL`을 검토해야 합니다. 이 책의 공통 테이블은 기본 키를 갖기 때문에 우선 `DEFAULT`를 사용합니다. (출처: [PostgreSQL publication 문서](https://www.postgresql.org/docs/17/logical-replication-publication.html))

### 5.4 설정과 slot 확인

~~~bash
docker exec postgres psql -U admin -d sourcedb -c "SHOW wal_level;"
docker exec postgres psql -U admin -d sourcedb -c "SHOW max_replication_slots;"
docker exec postgres psql -U admin -d sourcedb -c "SHOW max_wal_senders;"
docker exec postgres psql -U admin -d sourcedb -c "SELECT * FROM pg_replication_slots;"
docker exec postgres psql -U admin -d sourcedb -c "SELECT pg_current_wal_lsn();"
docker exec postgres psql -U admin -d sourcedb -c "SELECT relname, relreplident FROM pg_class WHERE relkind = 'r';"
~~~

`pg_current_wal_lsn()`은 현재 WAL 위치를 확인하는 명령입니다. 이 값만으로 논리적 변경 이벤트의 내용이 해석되었다고 볼 수는 없습니다. 실제 CDC 검증에서는 커넥터가 slot을 소비하고 이벤트를 전달하는지까지 확인해야 합니다.

## 6. 세 데이터베이스의 공통 업무 모델

### 6.1 관계형 모델과 문서 모델의 대응

세 데이터베이스에서 같은 주문 업무를 표현하되, 데이터베이스의 기본 모델에 맞춰 구조를 다르게 설계합니다.

| 업무 개념 | MySQL·PostgreSQL | MongoDB |
|---|---|---|
| 고객 | `customers` 테이블 | `customers` 컬렉션 |
| 제품 | `products` 테이블 | `products` 컬렉션 |
| 주문 | `orders` 테이블 | `orders` 컬렉션 |
| 주문 항목 | `order_items` 테이블 | `orders.items` 배열에 임베드 |
| 관계 표현 | 외래 키와 JOIN | 식별자 참조와 중첩 문서 |
| 기본 식별자 | 자동 증가 정수 | 실습용 `long` 업무 ID와 MongoDB `_id` |

관계형 데이터베이스에서는 정규화된 여러 테이블이 하나의 업무 관계를 구성합니다. MongoDB에서는 주문 조회 시 함께 사용되는 주문 항목을 주문 문서 안에 넣습니다. 이 차이는 CDC 이벤트의 모양에도 영향을 줍니다. 관계형 데이터베이스의 주문 항목 변경은 별도 테이블 이벤트가 되지만, MongoDB의 주문 항목 변경은 주문 문서의 배열 변경으로 표현됩니다.

### 6.2 합성 데이터 삽입

관계형 데이터베이스의 초기 데이터는 외래 키 순서를 지켜 삽입합니다. 먼저 고객과 제품을 넣고, 그 뒤 주문과 주문 항목을 넣습니다.

~~~sql
INSERT INTO customers (name, email)
VALUES
    ('Alice', 'alice@example.com'),
    ('Bob', 'bob@example.com'),
    ('Charlie', 'charlie@example.com');

INSERT INTO products (name, price, stock)
VALUES
    ('Laptop', 999.99, 100),
    ('Mouse', 29.99, 500),
    ('Keyboard', 79.99, 200);

INSERT INTO orders (customer_id, status, total_amount)
VALUES
    (1, 'PENDING', 1029.98),
    (2, 'CONFIRMED', 79.99),
    (3, 'SHIPPED', 999.99);

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES
    (1, 1, 1, 999.99),
    (1, 2, 1, 29.99),
    (2, 3, 1, 79.99),
    (3, 1, 1, 999.99);
~~~

MongoDB에서는 주문 문서 안에 주문 항목을 넣습니다.

~~~javascript
use sourcedb;

db.customers.insertMany([
  {
    customer_id: NumberLong(1),
    name: "Alice",
    email: "alice@example.com",
    created_at: new Date(),
    updated_at: new Date()
  },
  {
    customer_id: NumberLong(2),
    name: "Bob",
    email: "bob@example.com",
    created_at: new Date(),
    updated_at: new Date()
  }
]);

db.products.insertMany([
  {
    product_id: NumberLong(1),
    name: "Laptop",
    price: Decimal128("999.99"),
    stock: 100,
    created_at: new Date(),
    updated_at: new Date()
  },
  {
    product_id: NumberLong(2),
    name: "Mouse",
    price: Decimal128("29.99"),
    stock: 500,
    created_at: new Date(),
    updated_at: new Date()
  }
]);

db.orders.insertOne({
  order_id: NumberLong(1),
  customer_id: NumberLong(1),
  order_date: new Date(),
  status: "PENDING",
  total_amount: Decimal128("1029.98"),
  items: [
    { product_id: NumberLong(1), quantity: 1, unit_price: Decimal128("999.99") },
    { product_id: NumberLong(2), quantity: 1, unit_price: Decimal128("29.99") }
  ],
  created_at: new Date(),
  updated_at: new Date()
});
~~~

대규모 테스트에서는 고객 100명, 제품 50개, 주문 1,000건, 주문 항목 3,000건을 합성 데이터의 기준으로 사용할 수 있습니다. 제공된 자료는 이 수치를 예시로 제시하지만, 데이터 생성 시간과 컨테이너 자원에 대한 검증 결과는 포함하지 않습니다. [추가 자료 조사 필요: Windows 11과 Apple Silicon에서의 합성 데이터 생성 시간 및 자원 요구량]

## 7. 변경 이벤트 실습

### 7.1 INSERT·UPDATE·DELETE 시나리오

세 데이터베이스에서 동일한 업무 변화를 발생시켜 CDC가 이벤트를 포착하는지 확인합니다.

| 단계 | 업무 변화 | 확인할 내용 |
|---|---|---|
| 1 | 새 고객·제품·주문 삽입 | INSERT 이벤트가 생성되는지 확인합니다. |
| 2 | 주문 상태를 `PENDING`에서 `CONFIRMED`, `SHIPPED`로 변경 | UPDATE 이벤트와 변경 후 값이 전달되는지 확인합니다. |
| 3 | 제품 가격 또는 고객 이메일 변경 | 컬럼·필드 변경이 올바르게 식별되는지 확인합니다. |
| 4 | 주문 삭제 | DELETE 이벤트와 행·문서 식별자가 전달되는지 확인합니다. |
| 5 | 새 컬럼 또는 필드 추가 | 스키마 변화가 커넥터에서 어떻게 처리되는지 확인합니다. |

MySQL에서는 바이너리 로그의 행 이미지 설정이 UPDATE와 DELETE 이벤트 해석에 영향을 줍니다. PostgreSQL에서는 publication과 Replica Identity가 변경 이벤트의 범위와 행 식별에 영향을 줍니다. MongoDB에서는 Change Streams가 문서 변경을 전달하며, 관계형 테이블의 DDL 이벤트와 동일한 방식으로 취급해서는 안 됩니다.

### 7.2 스키마 변화

관계형 데이터베이스의 컬럼 추가는 다음과 같이 수행합니다.

~~~sql
ALTER TABLE orders
    ADD COLUMN discount_amount DECIMAL(10, 2) DEFAULT 0;
~~~

PostgreSQL에서는 자료형만 바꾸어 다음과 같이 작성할 수 있습니다.

~~~sql
ALTER TABLE orders
    ADD COLUMN discount_amount NUMERIC(10, 2) DEFAULT 0;
~~~

MongoDB에서는 문서에 새 필드를 추가하는 방식으로 스키마 변화를 만들 수 있습니다.

~~~javascript
db.orders.updateMany(
  {},
  { $set: { discount_amount: Decimal128("0.00") } }
);
~~~

이 장에서는 데이터베이스별로 스키마 변화가 기록되는 차이를 관찰하는 데 목적이 있습니다. MySQL·PostgreSQL의 DDL 이벤트와 MongoDB의 문서 필드 추가를 동일한 이벤트로 단정하지 않습니다. 특정 CDC 커넥터가 DDL 또는 컬렉션·인덱스 작업을 어느 범위까지 전달하는지는 커넥터 버전과 구독 범위에 따라 검증해야 합니다. [검토 필요: 선택한 Flink CDC 커넥터의 DDL·MongoDB 메타데이터 이벤트 처리 범위]

## 8. 데이터베이스별 변경 기록 확인

### 8.1 MySQL 바이너리 로그

바이너리 로그가 활성화되어 있고 로그 파일이 생성되는지 확인합니다.

~~~bash
docker exec mysql mysql -u root -psecret \
  -e "SHOW MASTER STATUS;"

docker exec mysql mysql -u root -psecret \
  -e "SHOW BINARY LOGS;"
~~~

`SHOW BINARY LOGS`는 서버에 존재하는 로그 파일 목록을 확인하는 데 사용합니다. 실제 이벤트의 상세 구조를 해석하는 단계는 사용하는 클라이언트와 커넥터의 방법에 따라 달라지므로, 이 장에서는 바이너리 로그 활성화와 기본 상태 확인에 초점을 둡니다.

### 8.2 PostgreSQL WAL과 replication slot

PostgreSQL에서는 현재 WAL 위치와 replication slot을 확인합니다.

~~~bash
docker exec postgres psql -U admin -d sourcedb \
  -c "SELECT pg_current_wal_lsn();"

docker exec postgres psql -U admin -d sourcedb \
  -c "SELECT slot_name, plugin, slot_type, active, restart_lsn FROM pg_replication_slots;"
~~~

logical replication slot이 생성되었는지, 활성 상태인지, `restart_lsn`이 계속 유지되는지 확인합니다. slot을 만들기만 하고 소비하지 않으면 WAL 보존량이 늘어날 수 있습니다.

### 8.3 MongoDB Change Streams

MongoDB에서는 Replica Set이 정상 상태인지 확인한 뒤 Change Stream을 열어 문서 변경을 관찰합니다.

~~~bash
docker exec mongodb mongosh \
  -u admin -p secret \
  --authenticationDatabase admin \
  --eval "rs.status().members.map(m => ({name: m.name, stateStr: m.stateStr}))"
~~~

Change Stream 테스트는 앞에서 작성한 `db.orders.watch()` 구독과 별도 터미널의 INSERT·UPDATE·DELETE 조합으로 수행합니다. 단일 노드 Replica Set은 이벤트 관찰에는 사용할 수 있지만, 노드 장애와 자동 failover를 검증하는 실습은 아닙니다.

## 9. 초기화와 데이터 재생성

### 9.1 초기화 스크립트의 실행 시점

세 데이터베이스의 Docker 이미지 초기화 스크립트는 데이터 디렉터리가 비어 있을 때 적용됩니다. named volume이 이미 존재하면 컨테이너를 재시작해도 초기화 파일이 다시 실행되지 않습니다.

따라서 다음 두 동작을 구분해야 합니다.

| 명령 | 결과 |
|---|---|
| `docker compose restart` | 컨테이너를 재시작하지만 데이터를 보존합니다. |
| `docker compose down` | 컨테이너를 제거하고 named volume은 기본적으로 보존합니다. |
| `docker compose down -v` | Compose가 관리하는 named volume까지 삭제합니다. 데이터가 손실됩니다. |
| `docker compose up -d` | 삭제된 데이터 디렉터리가 새로 생성되면 초기화 스크립트가 실행됩니다. |

### 9.2 전체 데이터 재생성

학습 환경을 완전히 처음 상태로 되돌릴 때는 다음 순서를 사용합니다.

~~~bash
docker compose down -v
docker compose up -d
docker compose ps
~~~

`down -v`는 데이터베이스의 데이터를 삭제하므로, 운영 환경이나 보존이 필요한 실습 데이터에는 사용하지 않습니다. 실행 전 현재 Compose 프로젝트와 volume 목록을 확인해야 합니다.

### 9.3 volume을 보존하는 수동 초기화

데이터베이스 전체 volume을 삭제하지 않고 업무 데이터만 초기화하는 방법도 있습니다. 이 경우 데이터베이스별 명령과 초기화 스크립트 실행 순서를 직접 관리해야 합니다.

~~~bash
# MySQL: 데이터베이스를 다시 만들고 SQL을 적용하는 예
docker exec mysql mysql -u root -psecret \
  -e "DROP DATABASE sourcedb; CREATE DATABASE sourcedb;"

# PostgreSQL: public 스키마를 재생성하는 예
docker exec postgres psql -U admin -d sourcedb \
  -c "DROP SCHEMA public CASCADE; CREATE SCHEMA public;"

# MongoDB: 데이터베이스를 삭제하는 예
docker exec mongodb mongosh -u admin -p secret \
  --authenticationDatabase admin sourcedb \
  --eval "db.dropDatabase()"
~~~

수동 초기화는 인증 정보, 스키마 파일 위치, publication과 Replica Set 상태까지 함께 관리해야 하므로 초보자에게는 `down -v` 후 재기동하는 방법이 더 재현하기 쉽습니다. 다만 `down -v`는 데이터 손실을 일으키므로 명령의 대상을 반드시 확인합니다.

## 10. Windows 11과 Apple Silicon에서 실행하기

### 10.1 플랫폼별 기본 실행 방식

Windows 11에서는 Docker Desktop의 WSL2 백엔드를 사용하고, Apple Silicon에서는 ARM64 컨테이너를 우선 사용합니다. 제공된 조사 자료는 세 데이터베이스 이미지가 `linux/amd64`와 `linux/arm64` 계열을 지원한다고 정리합니다.

| 항목 | Windows 11 | Apple Silicon |
|---|---|---|
| Docker 실행 기반 | Docker Desktop + WSL2 | Docker Desktop의 ARM64 환경 |
| 기본 이미지 아키텍처 | 일반적으로 `linux/amd64` | 가능하면 `linux/arm64` |
| 파일 시스템 주의점 | Windows 경로와 WSL 경로 간 I/O 차이 | APFS와 컨테이너 volume 경로 차이 |
| 이미지 실행 | amd64 이미지 실행 | ARM64 이미지 우선, 필요 시 amd64 에뮬레이션 |
| 실습 권장 | 프로젝트를 WSL 파일 시스템에 배치 | named volume과 ARM64 이미지 사용 |

Apple Silicon에서 amd64 이미지를 에뮬레이션하면 네이티브 ARM64 실행과 성능이 다를 수 있습니다. 특정 이미지가 ARM64 매니페스트를 제공하는지 먼저 확인하고, 이미지가 여러 아키텍처를 제공하지 않을 때만 플랫폼 지정 실행을 검토합니다. 정확한 성능 차이는 호스트 모델, Docker Desktop 설정, 저장 장치, 데이터량에 따라 달라집니다. [추가 자료 조사 필요: 각 이미지 태그의 최종 ARM64 매니페스트와 호스트별 성능 비교]

### 10.2 실행과 상태 확인

두 플랫폼 모두 Compose 명령 자체는 동일하게 사용합니다.

~~~bash
docker compose up -d
docker compose ps
docker compose logs --tail=100 mysql
docker compose logs --tail=100 mongodb
docker compose logs --tail=100 postgres
~~~

컨테이너가 즉시 종료되면 먼저 `docker compose ps`와 해당 서비스 로그를 확인합니다. 그 다음 이미지 아키텍처, volume 권한, 비밀번호 파일 경로, healthcheck 명령을 순서대로 점검합니다.

## 11. 실습 진행 순서

다음 순서는 세 소스 데이터베이스를 한 번에 구성할 때의 권장 흐름입니다.

### 1단계: 파일과 비밀 정보 준비

`.env.example`을 복사해 `.env`를 만들고, `secrets/` 아래에 로컬 실습용 비밀번호 파일을 배치합니다. 비밀번호 파일은 한 줄의 값만 포함하도록 유지합니다.

### 2단계: Compose 파일 검사

~~~bash
docker compose config
~~~

이 단계에서는 YAML 문법, 변수 치환, Secret 파일 경로, volume 정의를 확인합니다.

### 3단계: 세 데이터베이스 실행

~~~bash
docker compose up -d
docker compose ps
~~~

healthcheck 상태가 정상으로 바뀌는지 확인합니다. MongoDB는 데이터베이스 컨테이너가 healthy가 된 뒤 `mongodb-init`가 Replica Set을 초기화하는 흐름을 따릅니다.

### 4단계: 데이터베이스별 기본 상태 확인

- MySQL: `log_bin`, `binlog_format`, `binlog_row_image`, `gtid_mode`
- MongoDB: `rs.status()`, oplog 및 Change Streams
- PostgreSQL: `wal_level`, replication slot, publication

### 5단계: 합성 데이터 삽입

각 데이터베이스에 고객, 제품, 주문 데이터를 삽입합니다. 관계형 데이터베이스는 외래 키 순서를 지키고, MongoDB는 주문 문서 안에 `items` 배열을 구성합니다.

### 6단계: 변경 이벤트 발생

INSERT, UPDATE, DELETE를 차례로 실행하고 변경 기록의 위치와 CDC 커넥터의 출력이 일치하는지 확인합니다. 커넥터 연결은 다음 장 이후의 파이프라인 실습에서 수행합니다.

## 12. 설계 원칙

이 장에서 구성한 환경은 다음 원칙을 따릅니다.

1. **버전을 고정합니다.** 재현성을 위해 이미지 태그를 `latest`로 두지 않습니다.
2. **CDC 전제 조건을 명시합니다.** 바이너리 로그, Replica Set, logical WAL을 각각 확인합니다.
3. **데이터와 초기화 파일을 분리합니다.** named volume은 데이터를 보존하고, bind mount는 스크립트를 제공합니다.
4. **비밀 정보와 Compose 정의를 분리합니다.** 실습용 비밀번호라도 저장소에 직접 기록하지 않습니다.
5. **공통 업무 모델과 네이티브 모델을 함께 유지합니다.** 같은 주문을 비교하되, MongoDB의 문서 구조를 관계형 테이블과 억지로 같게 만들지 않습니다.
6. **단일 노드 구성을 운영 클러스터로 오해하지 않습니다.** 로컬 Replica Set은 Change Streams를 연습하기 위한 구조입니다.
7. **초기화의 비멱등성을 이해합니다.** volume이 존재하면 초기화 스크립트가 재실행되지 않으므로 재생성 절차를 문서화합니다.

## 장 요약

이 장에서는 Percona Server for MySQL, MongoDB Community Server, PostgreSQL을 Docker Compose 기반의 소스 데이터베이스로 준비했습니다.

MySQL에서는 ROW 기반 바이너리 로그와 FULL 행 이미지를 사용하고, GTID 관련 설정과 CDC 사용자를 구성했습니다. MongoDB에서는 standalone이 아닌 단일 노드 Replica Set을 구성해 Change Streams의 실행 조건을 마련했습니다. PostgreSQL에서는 `wal_level=logical`, replication slot, publication을 사용해 logical decoding을 준비했습니다.

세 데이터베이스에는 고객·제품·주문이라는 공통 업무 개념을 넣었지만, 관계형 데이터베이스는 테이블과 외래 키를 사용하고 MongoDB는 주문 항목을 중첩 배열로 표현했습니다. 이 차이는 뒤에서 CDC 이벤트를 분석할 때 중요한 기준이 됩니다.

마지막으로 초기화 스크립트의 실행 시점, named volume 삭제에 따른 데이터 손실, Windows 11과 Apple Silicon의 이미지 아키텍처 차이를 확인했습니다. 이제 소스 데이터베이스에서 발생한 변경을 스트리밍 계층으로 전달할 준비가 되었습니다.

## 확인 문제

1. MySQL CDC 실습에서 `binlog_format=ROW`와 `binlog_row_image=FULL`을 사용하는 이유는 무엇입니까?
2. MongoDB standalone 서버 대신 단일 노드 Replica Set을 사용하는 이유는 무엇입니까?
3. PostgreSQL에서 `wal_level=logical`을 설정한 뒤 재시작이 필요한 이유는 무엇입니까?
4. PostgreSQL replication slot을 소비하지 않을 때 발생할 수 있는 문제는 무엇입니까?
5. 관계형 데이터베이스의 `order_items` 테이블을 MongoDB에서는 어떻게 표현했습니까?
6. `docker compose down`과 `docker compose down -v`의 차이는 무엇입니까?
7. 초기화 스크립트를 수정했는데 컨테이너 재시작 후 변경이 반영되지 않는 이유는 무엇입니까?
8. Apple Silicon에서 ARM64 이미지를 우선 사용하는 이유는 무엇입니까?
9. MongoDB의 Change Stream 이벤트와 관계형 데이터베이스의 DDL 이벤트를 동일하게 취급하면 안 되는 이유는 무엇입니까?
10. CDC 사용자의 권한을 운영 환경에서 다시 검토해야 하는 이유는 무엇입니까?

## 이 장에서 자료가 부족했던 부분

- 제공된 자료에서 PostgreSQL 16.15와 17.11이 모두 제시되어 최종 기준 버전 확인이 필요합니다.
- Percona와 MongoDB의 정확한 2026년 8월 Docker 이미지 태그 및 ARM64 매니페스트 확인이 필요합니다.
- 선택한 Flink CDC 커넥터 버전별 MySQL·MongoDB·PostgreSQL 최소 권한이 확정되지 않았습니다.
- MongoDB 8.0의 before 이미지와 DDL·인덱스 이벤트 처리 범위는 공식 문서와 커넥터 문서의 교차 확인이 필요합니다.
- 로컬 데이터량에 따른 MongoDB oplog, PostgreSQL WAL 보존량, 합성 데이터 생성 시간의 기준값이 없습니다.
- Windows 11 WSL2와 Apple Silicon의 정확한 성능 차이는 실험 자료가 부족합니다.

# 7장. 이벤트 계약과 데이터 품질

6장에서는 세 소스 데이터베이스의 변경을 Apache Flink CDC로 읽고 Kafka로 전달하는 흐름을 살펴보았습니다. 그러나 이벤트가 Kafka에 기록되었다는 사실만으로 downstream 시스템이 안전하게 처리할 수 있는 것은 아닙니다.

이벤트를 받는 시스템은 누가, 언제, 어떤 데이터에, 어떤 변경을 수행했는지 알아야 합니다. 또한 필드의 자료형과 의미가 바뀌었을 때 이전 소비자가 계속 동작할 수 있어야 하고, 잘못된 이벤트는 정상 이벤트와 분리해야 합니다.

이 장에서는 CDC 이벤트의 구조를 이벤트 계약으로 정리하고, Kafka key와 파티션 key, 스키마 버전, JSON과 Apache Avro, 순서·중복·지연 이벤트, Dead Letter Topic, 데이터 품질 규칙을 다룹니다.

## 이 장의 목표

- CDC 이벤트 envelope의 공통 필드와 연산 유형을 이해합니다.
- 이벤트 key와 Kafka 파티션 key를 업무 식별자에 맞게 설계합니다.
- 스키마 버전과 호환성 규칙을 정의합니다.
- JSON과 Apache Avro의 실습·운영 사용 차이를 이해합니다.
- 파티션 단위 순서 보장의 의미와 한계를 설명합니다.
- 중복·지연·재처리 이벤트를 처리하는 기준을 세웁니다.
- 잘못된 이벤트를 Dead Letter Topic으로 격리합니다.
- NULL, 타입, 범위, 형식, 참조 무결성, 업무 규칙을 검증합니다.

> **자료의 적용 범위**
>
> 이 장의 이벤트 예시는 Debezium 스타일 envelope과 Kafka·Flink CDC의 일반적인 처리 모델을 바탕으로 구성했습니다. Flink CDC가 실제로 생성하는 필드명과 Kafka format에 따른 최종 envelope은 connector 및 format 설정에 따라 달라질 수 있습니다. 따라서 예시의 구조를 모든 Flink CDC 조합의 고정된 출력 형식으로 해석하지 않습니다. [검토 필요: 선택한 Flink CDC 3.6.0 connector와 Kafka Sink의 최종 이벤트 envelope]

## 1. CDC 이벤트 계약

### 1.1 이벤트 계약이 필요한 이유

이벤트 계약은 생산자와 소비자가 공유하는 데이터 구조와 의미의 약속입니다. 생산자는 약속된 필드와 자료형으로 이벤트를 작성하고, 소비자는 그 계약을 기준으로 이벤트를 해석합니다.

계약이 없으면 다음과 같은 문제가 발생합니다.

- 소비자가 어떤 필드가 식별자인지 알 수 없습니다.
- INSERT와 UPDATE를 구분하지 못합니다.
- DELETE를 null 데이터로 볼지 오류로 볼지 결정할 수 없습니다.
- 스냅샷 데이터와 실시간 변경을 구분하기 어렵습니다.
- 컬럼 추가나 자료형 변경이 기존 소비자를 중단시킬 수 있습니다.
- 잘못된 이벤트가 정상 토픽에 섞여 downstream 데이터를 오염시킬 수 있습니다.

이 책에서 최소한 정의할 이벤트 계약은 다음 질문에 답해야 합니다.

1. 이 이벤트는 어떤 소스에서 왔는가?
2. 어떤 엔터티와 레코드에 대한 변경인가?
3. 변경 유형은 INSERT, UPDATE, DELETE 중 무엇인가?
4. 변경 전과 변경 후의 값은 무엇인가?
5. 변경이 발생한 시각과 소스 위치는 무엇인가?
6. 초기 스냅샷 이벤트인가, 실시간 변경 이벤트인가?
7. 이벤트를 중복해서 받아도 같은 최종 결과를 만들 수 있는가?

### 1.2 Debezium 스타일 envelope

제공된 자료는 다음과 같은 Debezium 스타일의 CDC envelope을 예시로 제시합니다.

~~~json
{
  "schema": {},
  "payload": {
    "before": {
      "id": 123,
      "status": "PENDING"
    },
    "after": {
      "id": 123,
      "status": "CONFIRMED"
    },
    "source": {
      "version": "1.9.0.Final",
      "connector": "mysql",
      "name": "mysql-server-1",
      "ts_ms": 1630000000000,
      "snapshot": false,
      "db": "sourcedb",
      "table": "orders",
      "sequence": "mysql-bin.000001:12345",
      "server_id": 101,
      "gtid": "uuid:123",
      "file": "mysql-bin.000001",
      "pos": 12345,
      "row": 0
    },
    "op": "u",
    "ts_ms": 1630000000000,
    "transaction": {
      "id": "uuid:123",
      "total_order": 2,
      "data_collection_order": 1
    }
  }
}
~~~

이 구조에서 schema는 이벤트 자료형을 설명하는 영역이고, payload는 실제 변경 내용입니다. schema 영역의 존재와 형태는 직렬화 방식에 따라 달라질 수 있습니다. JSON 실습에서는 생략될 수 있고, Avro를 사용할 때는 별도 스키마 관리 방식이 적용될 수 있습니다.

### 1.3 핵심 필드

| 영역 | 필드 | 의미 |
|---|---|---|
| 데이터 | before | 변경 전 행·문서입니다. UPDATE 또는 DELETE에서 사용될 수 있습니다. |
| 데이터 | after | 변경 후 행·문서입니다. INSERT 또는 UPDATE에서 사용될 수 있습니다. |
| 출처 | source.connector | MySQL, PostgreSQL, MongoDB 등 소스 유형입니다. |
| 출처 | source.name | CDC 커넥터 또는 소스 인스턴스 이름입니다. |
| 출처 | source.db | 원본 데이터베이스 이름입니다. |
| 출처 | source.table | 원본 테이블 이름입니다. MongoDB에서는 컬렉션 식별자로 표현될 수 있습니다. |
| 출처 | source.ts_ms | 소스 변경 시각으로 사용되는 타임스탬프입니다. |
| 출처 | source.snapshot | 초기 스냅샷 이벤트인지 나타내는 값입니다. |
| 위치 | source.sequence | 소스 로그 위치를 표현하는 값입니다. |
| 위치 | source.gtid | MySQL GTID를 나타낼 수 있습니다. |
| 위치 | source.file·pos | MySQL binlog 파일과 위치를 나타낼 수 있습니다. |
| 연산 | op | c(create), r(read/snapshot), u(update), d(delete) 등의 연산 유형입니다. |
| 시간 | ts_ms | CDC 이벤트가 생성되거나 전달된 시각으로 사용될 수 있습니다. |
| 트랜잭션 | transaction.id | 트랜잭션 식별자입니다. |
| 트랜잭션 | transaction.total_order | 트랜잭션 내 전체 순서를 나타낼 수 있습니다. |
| 트랜잭션 | transaction.data_collection_order | 특정 컬렉션 또는 테이블 기준 순서를 나타낼 수 있습니다. |

이 표의 필드는 모든 CDC 커넥터에서 동일한 이름과 의미로 제공된다고 보장되지 않습니다. 특히 MongoDB의 source metadata와 Flink CDC의 Table API changelog 표현은 Debezium 스타일 JSON과 다를 수 있습니다. 이벤트 계약을 확정할 때는 실제 connector 출력 샘플을 저장하고 필드별 의미를 검증해야 합니다.

### 1.4 연산 유형별 before·after

| 연산 | before | after | 설명 |
|---|---|---|---|
| INSERT | null | 새 데이터 | 새 행 또는 문서가 생성되었습니다. |
| UPDATE | 이전 데이터 또는 일부 이전 값 | 수정 후 데이터 | 기존 데이터가 변경되었습니다. |
| DELETE | 삭제 전 데이터 또는 식별자 | null | 행 또는 문서가 삭제되었습니다. |
| SNAPSHOT READ | null 또는 snapshot 표시 | 현재 데이터 | 초기 스냅샷에서 읽은 데이터입니다. |
| TRUNCATE | null | null | 테이블 전체 삭제를 별도 연산으로 표현할 수 있습니다. |

DELETE 이벤트에서 before 전체가 제공되는지는 소스 설정과 connector에 따라 달라질 수 있습니다. downstream이 삭제를 수행하려면 최소한 안정적인 식별자가 필요합니다. before 데이터가 없더라도 Kafka key 또는 이벤트 내부 key 필드가 보존되어야 합니다.

### 1.5 이벤트 최소 계약

로컬 실습과 이후 파이프라인의 기준으로 다음 최소 필드를 정의할 수 있습니다.

~~~json
{
  "event_id": "mysql:sourcedb:orders:123:00000042",
  "schema_version": 1,
  "source_db": "mysql",
  "source_entity": "orders",
  "key": {
    "id": 123
  },
  "operation": "UPDATE",
  "event_time": "2026-08-29T12:00:00Z",
  "snapshot": false,
  "before": {
    "id": 123,
    "status": "PENDING"
  },
  "after": {
    "id": 123,
    "status": "CONFIRMED"
  },
  "source_position": "mysql-bin.000001:12345"
}
~~~

event_id를 구성하는 규칙은 반드시 소스 위치와 업무 식별자를 함께 검토해 정해야 합니다. 단순히 현재 시각을 event_id로 사용하면 재전송된 같은 이벤트를 식별하기 어렵습니다. 최종 event_id 구성은 connector가 제공하는 위치와 트랜잭션 metadata를 확인한 뒤 확정합니다. [추가 자료 조사 필요: 세 소스의 중복 판별용 event_id 구성 기준]

## 2. 이벤트 key와 파티션 key

### 2.1 Kafka 레코드의 key와 value

Kafka 레코드는 일반적으로 key, value, headers, timestamp로 설명할 수 있습니다. key는 파티션 선택과 엔터티 식별에 사용하고, value는 변경 내용과 metadata를 담습니다.

이벤트 key와 이벤트 value를 분리하면 다음과 같은 장점이 있습니다.

- 파티션 선택 기준을 명확히 할 수 있습니다.
- 같은 엔터티의 변경을 같은 파티션으로 보낼 수 있습니다.
- value의 데이터 구조가 바뀌어도 식별 기준을 유지할 수 있습니다.
- compact 토픽에서 키별 최신 상태를 관리할 수 있습니다.

### 2.2 기본 키를 파티션 key로 사용하는 이유

주문 상태가 PENDING에서 CONFIRMED, SHIPPED로 바뀌는 상황을 생각해 봅시다. 세 이벤트가 서로 다른 파티션에 기록되면 downstream 소비자는 상태 변경 순서를 보장받지 못합니다.

order_id를 Kafka key로 사용하면 같은 주문의 이벤트를 같은 파티션으로 라우팅하도록 설계할 수 있습니다.

| 소스 | 엔터티 | key 후보 |
|---|---|---|
| MySQL | orders | order_id |
| MySQL | customers | customer_id |
| MySQL | products | product_id |
| PostgreSQL | orders | order_id |
| PostgreSQL | customers | customer_id |
| PostgreSQL | products | product_id |
| MongoDB | orders | order_id 또는 _id |
| MongoDB | customers | customer_id 또는 _id |
| MongoDB | products | product_id 또는 _id |

MongoDB에서 업무 식별자와 MongoDB 내부 _id가 함께 존재할 수 있습니다. 두 식별자의 생명주기와 유일성 범위가 다를 수 있으므로, 단순히 _id를 항상 Kafka key로 사용한다고 확정하지 않습니다.

### 2.3 파티션 단위 순서

Kafka가 보장하는 순서는 파티션 단위입니다.

~~~mermaid
flowchart TB
    T["orders 토픽"] --> P0["파티션 0"]
    T --> P1["파티션 1"]
    T --> P2["파티션 2"]
    P0 --> O1["order_1: INSERT"]
    P0 --> O2["order_1: UPDATE"]
    P0 --> O3["order_1: DELETE"]
~~~

위 예에서 order_1의 이벤트는 파티션 0 안에서 INSERT, UPDATE, DELETE 순서로 기록됩니다. 하지만 order_2가 파티션 1에 있다면 order_1과 order_2 사이의 전역 순서는 보장되지 않습니다.

| 범위 | 순서 보장 |
|---|---|
| 같은 파티션 | 기록 순서에 따른 순차 처리 |
| 같은 key | 같은 파티션으로 라우팅하도록 설계한 경우 key 단위 순서 |
| 서로 다른 key | 같은 파티션이면 파티션 순서, 다른 파티션이면 전역 순서 없음 |
| 토픽 전체 | 다중 파티션에서는 전역 순서가 보장되지 않음 |

순서가 정말로 토픽 전체에서 필요하다면 단일 파티션을 사용할 수 있지만, 병렬 처리 능력이 제한됩니다. 높은 처리량을 위해 다중 파티션을 사용하는 경우에는 업무 엔터티 단위의 순서 보장으로 요구사항을 좁히는 것이 일반적인 설계 방향입니다. 특정 처리량과 파티션 수의 관계는 환경별 측정이 필요합니다.

### 2.4 복합 key

단일 컬럼만으로 전체 이벤트의 식별 범위를 표현할 수 없을 때는 복합 key를 사용합니다. 예를 들어 여러 source_db가 같은 업무 ID를 사용할 수 있다면 source_db와 id를 함께 key에 넣을 수 있습니다.

~~~json
{
  "key": {
    "source_db": "mysql",
    "id": 123
  },
  "value": {
    "operation": "UPDATE",
    "after": {
      "id": 123,
      "status": "CONFIRMED"
    }
  }
}
~~~

복합 key는 다음 상황에서 유용합니다.

- 여러 소스 데이터베이스의 이벤트를 하나의 토픽으로 합칩니다.
- 하나의 업무 엔터티 안에서 부모·자식 식별자를 조합해야 합니다.
- 단일 ID가 소스별로만 유일합니다.
- 파티션 분배와 downstream의 중복 판별 범위를 일치시켜야 합니다.

order_id와 product_id가 함께 주문 항목을 식별한다면 다음과 같은 key를 사용할 수 있습니다.

~~~json
{
  "key": {
    "order_id": 123,
    "product_id": 456
  }
}
~~~

복합 key를 JSON 객체로 직렬화할 때 key serialization 방식과 필드 순서가 모든 생산자에서 동일해야 합니다. 다른 언어의 JSON 직렬화 결과가 달라지면 같은 논리적 key가 서로 다른 바이트로 계산될 수 있습니다. [검토 필요: 최종 Kafka key serializer와 복합 key 정규화 규칙]

## 3. 스키마 버전 관리

### 3.1 스키마 진화

스키마 진화는 시간이 지나면서 이벤트의 필드와 자료형이 바뀌는 과정입니다. 데이터 플랫폼은 소스 데이터베이스의 변경과 downstream 소비자의 배포 시점이 항상 일치하지 않으므로, 구·신 스키마가 일정 기간 공존할 수 있어야 합니다.

대표적인 변경은 다음과 같습니다.

- 새 nullable 필드 추가
- 기본값이 있는 새 필드 추가
- 필드 삭제
- 필드 이름 변경
- 자료형 확대
- 자료형 축소 또는 호환되지 않는 자료형 변경
- 필수 필드와 선택 필드의 변경
- 이벤트 envelope에 metadata 추가

### 3.2 호환성 방향

제공된 자료는 Apache Avro의 호환성 방향을 다음처럼 정리합니다.

| 호환성 | 의미 | 예시 |
|---|---|---|
| BACKWARD | 새 스키마로 과거 데이터를 읽을 수 있습니다. | 기본값이 있는 새 필드 추가 |
| FORWARD | 과거 스키마로 새 데이터를 읽을 수 있습니다. | 소비자가 이해하지 못하는 필드 처리 |
| FULL | BACKWARD와 FORWARD를 모두 만족하도록 관리합니다. | 호환 가능한 추가·삭제 조합 |
| NONE | 호환성 검사를 적용하지 않습니다. | 변경 책임을 생산자·소비자가 직접 부담 |

실제 호환성의 성립 여부는 필드의 기본값, nullable 여부, 자료형, reader·writer schema 규칙을 함께 확인해야 합니다. 필드 삭제가 항상 FORWARD 호환이고 필드 추가가 항상 BACKWARD 호환인 것은 아닙니다. 선택한 Avro 구현과 schema 관리 도구의 검증 결과를 기준으로 판단해야 합니다. [추가 자료 조사 필요: Apache Avro 1.12.2의 공식 호환성 규칙과 이 책의 스키마 관리 방식]

### 3.3 이벤트에 schema_version 추가

이벤트 envelope에 명시적인 schema_version을 추가하면 소비자가 버전에 따라 처리 경로를 선택할 수 있습니다.

~~~json
{
  "schema_version": 2,
  "operation": "UPDATE",
  "source_db": "mysql",
  "after": {
    "id": 123,
    "status": "CONFIRMED",
    "discount_amount": 10.00
  }
}
~~~

스키마 버전은 이벤트 payload 구조의 변경을 나타내는 값으로 사용합니다. 소스 데이터베이스의 애플리케이션 버전, connector 버전, Kafka 토픽 버전과 혼동하지 않도록 이름을 분리해야 합니다.

스키마 변경 시 기본 절차는 다음과 같습니다.

1. 변경 내용을 문서화합니다.
2. schema_version을 증가시킵니다.
3. 새 필드가 없는 과거 이벤트를 소비할 수 있도록 기본값을 정합니다.
4. 새 필드를 이해하지 못하는 소비자가 실패하지 않는지 확인합니다.
5. 생산자와 소비자를 단계적으로 배포합니다.
6. 일정 기간 동안 구·신 버전 이벤트를 함께 검증합니다.

### 3.4 안전한 변경과 위험한 변경

| 변경 | 일반적인 위험도 | 처리 방향 |
|---|---:|---|
| nullable 필드 추가 | 낮음 | 기본값 또는 null 허용 |
| 기본값이 있는 필드 추가 | 낮음 | 구형 이벤트를 읽을 때 기본값 적용 |
| 선택 필드의 이름 변경 | 중간 | 새 필드 추가 후 이전 필드를 단계적으로 폐기 |
| 필드 삭제 | 중간·높음 | 모든 소비자의 사용 여부를 확인 |
| 자료형 확대 | 중간 | reader·writer 호환성을 검증 |
| 자료형 축소 | 높음 | 데이터 손실 가능성을 검증 |
| 필수 필드 추가 | 높음 | 구형 이벤트와 구형 소비자에 영향을 줌 |
| key 필드 변경 | 매우 높음 | 파티션·순서·중복 판별이 달라짐 |

특히 Kafka key를 바꾸면 같은 엔터티의 이벤트가 다른 파티션으로 이동할 수 있습니다. 따라서 value의 스키마 변경보다 key 변경을 더 보수적으로 다루어야 합니다.

## 4. JSON과 Apache Avro

### 4.1 JSON의 특성

JSON은 사람이 읽기 쉽고 CLI와 로그에서 내용을 확인하기 좋습니다. 이 책의 로컬 실습에서는 변경 이벤트의 구조를 확인하고 디버깅하기 위해 JSON을 우선 사용합니다.

JSON의 장점은 다음과 같습니다.

- 별도의 바이너리 디코더 없이 내용을 확인할 수 있습니다.
- 임시 필드를 추가하기 쉽습니다.
- Console Consumer로 이벤트를 확인하기 쉽습니다.
- 초보자가 key·value와 before·after 구조를 이해하기 쉽습니다.

하지만 JSON은 생산자와 소비자가 같은 스키마를 자동으로 공유하지 않습니다. 필드가 없거나 자료형이 바뀌어도 메시지 자체는 전송될 수 있으므로, 소비자에서 검증과 오류 처리를 수행해야 합니다.

### 4.2 Apache Avro의 특성

Apache Avro는 스키마를 기반으로 데이터를 직렬화하는 형식입니다. 제공된 자료는 Avro를 바이너리 직렬화와 스키마 진화를 고려하는 운영 환경의 선택지로 제시합니다.

Avro를 사용하면 다음을 체계화할 수 있습니다.

- 필드와 자료형을 명시합니다.
- 스키마 호환성을 검증합니다.
- JSON보다 작은 바이너리 표현을 사용할 수 있습니다.
- 생산자와 소비자 사이의 계약을 별도 스키마로 관리합니다.

다만 Avro만 도입한다고 스키마가 자동으로 안전하게 관리되는 것은 아닙니다. writer schema와 reader schema의 호환성 정책, 스키마 배포 방식, 버전 등록 위치, 실패 시 처리 절차를 함께 정해야 합니다.

### 4.3 JSON과 Avro 비교

| 항목 | JSON | Apache Avro |
|---|---|---|
| 가독성 | 높음 | 낮음 |
| 실습·디버깅 | 적합 | 별도 도구 필요 |
| 스키마 강제 | 기본적으로 약함 | 스키마 기반 |
| 메시지 크기 | 상대적으로 클 수 있음 | 바이너리로 줄일 수 있음 |
| 스키마 진화 | 애플리케이션이 직접 관리 | 호환성 규칙 적용 가능 |
| 자료형 검증 | 소비자 구현에 의존 | 스키마로 정의 |
| 이 책의 용도 | 로컬 실습 기본 | 운영 전환 검토 |
| 추가 구성 | 없음 또는 단순 | serializer·schema 관리 필요 |

제공된 자료에는 Avro와 Confluent Schema Registry 조합이 운영 권장안으로 제시되어 있습니다. 그러나 Confluent Schema Registry는 이 책의 Apache 중심 구성과 별도의 제품 구성입니다. 이 책에서는 Apache Avro를 설명하되, 특정 Schema Registry를 핵심 실습 구성으로 확정하지 않습니다. [검토 필요: Apache-only 원칙을 유지할 때 Avro schema 저장·배포 방식]

### 4.4 JSON 이벤트 예시

~~~json
{
  "schema_version": 1,
  "operation": "UPDATE",
  "source": {
    "connector": "mysql",
    "db": "sourcedb",
    "table": "orders"
  },
  "before": {
    "id": 123,
    "status": "PENDING"
  },
  "after": {
    "id": 123,
    "status": "CONFIRMED"
  }
}
~~~

실습에서는 Console Consumer로 위 구조를 확인하고, 필수 필드와 operation 값이 계약에 맞는지 검증합니다.

### 4.5 Avro 스키마 예시

~~~json
{
  "type": "record",
  "name": "OrderChangeEvent",
  "namespace": "com.example.cdc",
  "fields": [
    {
      "name": "before",
      "type": [
        "null",
        {
          "type": "record",
          "name": "OrderBefore",
          "fields": [
            { "name": "id", "type": "long" },
            { "name": "status", "type": "string" }
          ]
        }
      ],
      "default": null
    },
    {
      "name": "after",
      "type": [
        "null",
        {
          "type": "record",
          "name": "OrderAfter",
          "fields": [
            { "name": "id", "type": "long" },
            { "name": "status", "type": "string" }
          ]
        }
      ],
      "default": null
    },
    {
      "name": "operation",
      "type": {
        "type": "enum",
        "name": "Operation",
        "symbols": ["INSERT", "SNAPSHOT", "UPDATE", "DELETE"]
      }
    }
  ]
}
~~~

이 Avro 예시는 계약의 형태를 보여 주기 위한 것입니다. 실제 스키마에서는 source metadata, schema_version, event_time, key, transaction metadata의 포함 여부를 프로젝트 규칙으로 정해야 합니다.

## 5. 순서·중복·지연 이벤트

### 5.1 파티션 내 순서와 전역 순서

이벤트 순서는 세 가지 층위로 나누어 생각해야 합니다.

1. 소스 데이터베이스 로그의 순서
2. Kafka 파티션 안의 기록 순서
3. 여러 파티션과 여러 시스템을 통과한 최종 처리 순서

소스 로그가 순서를 제공하더라도, Kafka에 여러 파티션으로 분산하고 downstream에서 병렬 처리하면 토픽 전체의 전역 순서는 자동으로 유지되지 않습니다. 업무적으로 필요한 순서를 엔터티 단위로 정의하고, 그 엔터티의 key를 일관되게 유지해야 합니다.

### 5.2 순서 전략

- 주문 상태 변경은 order_id를 key로 사용합니다.
- 고객 속성 변경은 customer_id를 key로 사용합니다.
- 여러 소스를 통합할 때 source_db와 업무 ID의 범위를 확인합니다.
- 이벤트에 source timestamp와 source sequence를 기록합니다.
- 서로 다른 파티션의 이벤트를 비교해야 하면 재정렬 기준을 별도로 정의합니다.
- 단일 파티션은 전역 순서를 얻는 대신 처리량을 희생하는 선택입니다.

순서 보장은 중복 제거와도 연결됩니다. 오래된 이벤트가 늦게 도착한 경우 단순히 마지막으로 도착한 값을 적용하면 최신 상태가 훼손될 수 있습니다. 이벤트 시각, 소스 위치, 버전 컬럼을 함께 검증해야 합니다.

### 5.3 중복 이벤트

중복은 정상적인 복구 과정에서도 발생할 수 있습니다.

- Flink checkpoint 실패 후 마지막 성공 checkpoint에서 재개합니다.
- offset 커밋 전에 소비자가 재시작됩니다.
- 네트워크 재시도로 같은 이벤트가 다시 전달됩니다.
- Kafka 소비자 그룹이 리밸런싱됩니다.
- 초기 스냅샷을 다시 실행합니다.
- DLQ 이벤트를 수정 후 재전송합니다.

중복을 허용하지 않는다고 선언하는 것보다, 중복이 발생해도 최종 결과가 안전하도록 처리하는 편이 현실적입니다.

### 5.4 멱등성 처리

멱등성은 동일 이벤트를 한 번 또는 여러 번 적용해도 최종 결과가 같도록 하는 성질입니다.

| 방법 | 설명 |
|---|---|
| 기본 키 upsert | 같은 업무 key에 대해 최신 값을 덮어씁니다. |
| event_id 기록 | 이미 처리한 이벤트 ID를 저장하고 재처리를 건너뜁니다. |
| 버전 비교 | source sequence 또는 updated_at을 비교해 오래된 이벤트를 무시합니다. |
| operation 처리 | INSERT·UPDATE·DELETE를 서로 다른 방식으로 적용합니다. |
| 트랜잭션 적용 | 이벤트와 처리 이력을 하나의 원자적 단위로 기록합니다. |

event_id 저장 방식은 별도 저장소와 보존 기간이 필요합니다. 자료에는 재시도 창에 맞추어 24~72시간 TTL을 사용할 수 있다는 설명이 있지만, 이 책의 실제 재처리 기간과 일치하는지 검증되지 않았습니다. [추가 자료 조사 필요: event_id 중복 제거 저장소와 TTL 산정 기준]

### 5.5 exactly-once의 범위

Kafka와 Flink에서 exactly-once 설정을 사용할 수 있지만, 이를 최종 시스템 전체의 중복 없음으로 확대해서는 안 됩니다. 정확한 결과를 얻으려면 다음 경계를 함께 확인해야 합니다.

- source가 동일 이벤트를 재전송할 때 위치를 복구할 수 있는가?
- Flink checkpoint가 소스와 연산 상태를 함께 복구하는가?
- Kafka Sink가 멱등적·트랜잭션 방식으로 기록하는가?
- Kafka Consumer가 read_committed 설정을 사용하는가?
- 최종 sink가 upsert·merge·delete를 지원하는가?
- sink의 커밋 결과와 Flink checkpoint가 일치하는가?

제공된 자료에 포함된 설정 예는 다음과 같습니다.

~~~text
execution.checkpointing.interval: 60000
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 300000
execution.checkpointing.max-concurrent-checkpoints: 1
execution.checkpointing.min-pause: 30000

properties.enable.idempotence = true
transactional.id = flink-cdc-tx
isolation.level = read_committed
~~~

이 설정은 개념 예시입니다. Flink Kafka Sink 버전과 배포 방식에 따라 설정 키가 다를 수 있고, transactional.id는 병렬 writer 간 고유성까지 검토해야 합니다. [검토 필요: 선택한 Flink Kafka Sink의 exactly-once·transactional.id 최종 설정]

### 5.6 지연 이벤트와 Event Time

지연 이벤트는 이벤트가 실제로 발생한 시점과 처리 시스템에 도착한 시점 사이에 차이가 있는 이벤트입니다. 네트워크 지연, source 지연, consumer lag, 재처리로 인해 발생할 수 있습니다.

처리 시각(processing time)만 사용하면 늦게 도착한 과거 이벤트를 현재 이벤트로 오인할 수 있습니다. 따라서 source timestamp나 이벤트 timestamp를 Event Time으로 사용하고, 허용 지연 범위와 처리 규칙을 정의해야 합니다.

~~~text
watermark = max_event_time - allowed_out_of_orderness
~~~

처리 범위는 다음과 같이 나눌 수 있습니다.

1. Watermark 이전: 정상적인 Event Time 처리
2. Watermark 이후이지만 허용 지연 이내: 윈도우 재계산 또는 보정
3. 허용 지연 초과: 별도 지연 이벤트 스트림이나 DLQ로 분리

자료에는 CDC 소스의 watermark 지연을 2초, 배치·ETL을 1~24시간으로 제시하지만, 이 값은 이 책의 환경에서 측정된 기준이 아닙니다. 소스별 timestamp 의미와 지연 분포를 측정한 뒤 결정해야 합니다. [추가 자료 조사 필요: 세 CDC 소스의 Event Time·watermark·allowed lateness 기준]

## 6. Dead Letter Topic

### 6.1 Dead Letter Topic의 목적

Dead Letter Topic(DLT)은 정상 경로에서 처리할 수 없는 이벤트를 별도 토픽으로 격리하는 패턴입니다. 반복해서 실패하는 이벤트를 메인 토픽에서 계속 재시도하면 정상 이벤트 처리까지 지연될 수 있습니다.

DLT는 다음 목적으로 사용합니다.

- 잘못된 이벤트를 정상 이벤트와 분리합니다.
- 실패 원인과 원본 이벤트를 보존합니다.
- 담당자가 오류를 분석할 수 있게 합니다.
- 수정 후 선택적으로 재처리합니다.
- 메인 처리 경로의 처리량과 안정성을 보호합니다.

### 6.2 DLT 토픽 이름

메인 토픽에 접미사를 붙이는 규칙을 사용합니다.

~~~text
<main-topic>-dlq
~~~

| 정상 토픽 | DLT 토픽 |
|---|---|
| mysql-orders-cdc | mysql-orders-cdc-dlq |
| mongo-customers-cdc | mongo-customers-cdc-dlq |
| postgres-products-cdc | postgres-products-cdc-dlq |

DLT에 보낼 때는 원본 이벤트를 그대로 보존하는 것과 오류 metadata를 추가하는 것을 모두 검토해야 합니다.

~~~json
{
  "failed_event": {
    "schema_version": 1,
    "operation": "INSERT",
    "source_db": "mysql",
    "after": {
      "id": 123,
      "email": "invalid"
    }
  },
  "error": {
    "code": "INVALID_EMAIL",
    "message": "email format validation failed",
    "stage": "data-quality",
    "failed_at": "2026-08-29T12:00:00Z"
  },
  "original_topic": "mysql-customers-cdc",
  "original_partition": 1,
  "original_offset": 42,
  "retry_count": 0
}
~~~

원본 topic, partition, offset을 보존하면 실패 이벤트의 출처를 추적하기 쉽습니다. 이 metadata가 실제 connector와 Flink API에서 어떻게 전달되는지는 구현을 확인해야 합니다.

### 6.3 DLT 처리 원칙

DLT를 만들었다고 오류가 해결되는 것은 아닙니다. 다음 운영 절차를 함께 정의해야 합니다.

1. 오류 유형을 분류합니다.
2. 같은 오류가 반복되는지 확인합니다.
3. 원본 이벤트와 실패 단계의 로그를 분석합니다.
4. 데이터 또는 코드의 수정 방법을 결정합니다.
5. 수정된 이벤트를 재처리할 대상을 결정합니다.
6. 재처리 결과와 중복 가능성을 확인합니다.
7. 처리 완료한 DLT 이벤트의 보존·삭제 정책을 정합니다.

DLT 소비자는 메인 소비자와 별도의 소비자 그룹을 사용해야 합니다. 그렇지 않으면 정상 처리와 오류 처리가 서로의 offset과 재시도 흐름에 영향을 줄 수 있습니다.

### 6.4 Flink 처리 예시

다음 Java 코드는 개념적인 Side Output 패턴입니다.

~~~java
OutputTag<String> deadLetterTag =
    new OutputTag<String>("dead-letter") {};

SingleOutputStreamOperator<CDCEvent> mainStream =
    cdcSource.process(new ProcessFunction<CDCEvent, CDCEvent>() {
        @Override
        public void processElement(
                CDCEvent event,
                Context context,
                Collector<CDCEvent> output) {
            try {
                validateEvent(event);
                output.collect(event);
            } catch (ValidationException exception) {
                context.output(
                    deadLetterTag,
                    toDeadLetterJson(event, exception)
                );
            }
        }
    });

DataStream<String> deadLetters =
    mainStream.getSideOutput(deadLetterTag);
~~~

이 코드는 DLT로 분리할 위치와 원본 이벤트·오류 메시지의 관계를 보여 주기 위한 예시입니다. 실제 Flink API의 타입, serializer, Kafka Sink 연결, 예외 처리 정책은 사용하는 Flink 버전과 DataStream 또는 Table API에 맞게 조정해야 합니다. [검토 필요: Flink 1.20.x·2.2.x에서의 최종 Side Output 및 Kafka DLT Sink 구현]

## 7. 데이터 품질 검증

### 7.1 품질 검증이 필요한 이유

CDC는 소스 데이터베이스의 변경을 빠르게 전달하지만, 소스에 존재하는 모든 데이터 오류를 자동으로 제거하지는 않습니다. 잘못된 이메일, 음수 수량, 미래 시각, 존재하지 않는 고객 ID가 정상 이벤트로 전달될 수 있습니다.

데이터 품질 검증은 이벤트를 정상 경로에 보낼지 DLT로 보낼지 결정하는 단계입니다. 검증을 너무 늦게 수행하면 오류 데이터가 Kafka, 레이크하우스, 서빙 저장소로 퍼진 뒤 되돌리기 어려워집니다.

### 7.2 검증 규칙의 범주

| 범주 | 검증 항목 | 주문 업무 예시 |
|---|---|---|
| NULL | 필수 필드가 null인지 확인 | id, name, email은 null 불가 |
| 타입 | 자료형이 계약과 일치하는지 확인 | id는 정수, price는 숫자 |
| 범위 | 값이 허용 범위에 있는지 확인 | quantity > 0, price >= 0 |
| 형식 | 문자열 패턴과 날짜 형식 확인 | 이메일, ISO 8601 시각 |
| 참조 무결성 | 참조 대상이 존재하는지 확인 | customer_id가 고객 데이터에 존재 |
| 업무 규칙 | 도메인 규칙을 만족하는지 확인 | total_amount가 항목 합계와 일치 |
| 시간 | 시각의 순서와 미래 여부 확인 | updated_at이 created_at 이후 |
| 스키마 | 버전·필드·자료형 확인 | schema_version과 필수 필드 일치 |

모든 검증 실패를 같은 수준으로 취급할 필요는 없습니다. 파싱 불가, 식별자 없음, 자료형 오류는 즉시 DLT로 보낼 수 있지만, 참조 데이터가 아직 도착하지 않은 경우에는 일정 시간 재시도하는 전략을 검토할 수 있습니다. 이 책에서는 오류별 재시도 정책을 확정하지 않습니다.

### 7.3 주문 이벤트 검증 예

~~~text
필수 필드
- event_id
- source_db
- source_entity
- operation
- key
- event_time

주문 INSERT·UPDATE의 after
- id는 null이 아니어야 합니다.
- customer_id는 null이 아니어야 합니다.
- quantity는 0보다 커야 합니다.
- total_amount는 0 이상이어야 합니다.
- status는 PENDING, CONFIRMED, SHIPPED, DELIVERED, CANCELLED 중 하나여야 합니다.
- created_at과 updated_at은 미래 시각이 아니어야 합니다.

주문 DELETE
- after가 null이어도 허용합니다.
- key 또는 before.id가 있어야 합니다.
- operation이 DELETE인지 확인합니다.
~~~

UPDATE와 DELETE에서 before 또는 after의 존재 조건은 envelope 계약에 따라 달라질 수 있습니다. 예를 들어 DELETE에 before 전체가 없더라도 key가 있다면 삭제를 수행할 수 있습니다. 반대로 식별자 없이 값만 있는 DELETE는 안전하게 적용할 수 없으므로 DLT 대상으로 분리하는 편이 적절합니다.

### 7.4 Flink SQL 필터 예

다음은 필수 필드, 시간, 이메일 형식을 검사하는 개념적인 SQL입니다.

~~~sql
INSERT INTO kafka_sink
SELECT id, name, email, created_at, updated_at
FROM mysql_source
WHERE id IS NOT NULL
  AND name IS NOT NULL
  AND email IS NOT NULL
  AND created_at <= CURRENT_TIMESTAMP
  AND updated_at <= CURRENT_TIMESTAMP
  AND email REGEXP '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$';
~~~

검증에 실패한 이벤트를 DLT Sink로 보냅니다.

~~~sql
INSERT INTO kafka_dlq_sink
SELECT id,
       name,
       email,
       created_at,
       updated_at,
       'Data quality validation failed' AS error_message,
       CURRENT_TIMESTAMP AS error_timestamp
FROM mysql_source
WHERE id IS NULL
   OR name IS NULL
   OR email IS NULL
   OR created_at > CURRENT_TIMESTAMP
   OR updated_at > CURRENT_TIMESTAMP
   OR email NOT REGEXP '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$';
~~~

위 SQL은 행 형태의 단순 source를 기준으로 한 예시입니다. 실제 CDC changelog에는 DELETE와 UPDATE의 before·after 의미가 있으므로, 동일한 WHERE 조건을 모든 operation에 그대로 적용하면 안 됩니다. DLT에는 원본 envelope과 오류 정보가 함께 들어가야 합니다. [검토 필요: Flink CDC changelog를 Flink SQL에서 operation별로 검증하는 최종 구문]

### 7.5 검증 결과의 세 가지 경로

품질 검증 결과는 세 경로로 나눌 수 있습니다.

~~~mermaid
flowchart LR
    E["CDC 이벤트"] --> V["품질 검증"]
    V --> N["정상 Kafka 토픽"]
    V --> R["재시도 대기"]
    V --> D["Dead Letter Topic"]
~~~

- **정상 토픽**: 계약과 품질 규칙을 통과한 이벤트입니다.
- **재시도 대기**: 일시적 외부 참조 오류나 일시적 시스템 오류입니다.
- **DLT**: 수정 없이는 반복 실패할 구조적 오류입니다.

재시도 대기와 DLT를 구분하지 않으면 데이터가 영원히 재시도되거나, 실제로 복구할 수 있는 이벤트가 영구 격리될 수 있습니다. 오류 코드와 재시도 횟수를 이벤트 metadata로 남겨야 합니다.

## 8. 스키마·품질·파티션을 함께 설계하기

이벤트 계약은 envelope만 정의하는 작업이 아닙니다. key, 파티션, 스키마, 품질 검증, 재처리 정책이 서로 연결되어 있습니다.

| 설계 요소 | 결정해야 할 내용 |
|---|---|
| 이벤트 key | 어떤 업무 식별자를 사용할 것인가 |
| 파티션 key | key와 같은 값을 사용할 것인가 |
| 순서 | 전역·소스·엔터티 중 어느 범위를 보장할 것인가 |
| 스키마 | 필드·자료형·nullable·기본값은 무엇인가 |
| 버전 | schema_version을 어떻게 증가시킬 것인가 |
| 품질 | 정상·재시도·DLT의 조건은 무엇인가 |
| 중복 | event_id와 upsert 기준은 무엇인가 |
| DELETE | 실제 삭제, soft delete, tombstone 중 무엇을 사용할 것인가 |
| 보존 | 정상 토픽과 DLT의 retention은 얼마인가 |
| 재처리 | offset reset과 DLT replay를 어떻게 수행할 것인가 |

예를 들어 key를 id에서 source_db와 id의 복합 key로 바꾸면 순서, 파티션 분포, compact 결과, 중복 제거 범위가 동시에 달라집니다. 그러므로 스키마 변경 검토에서 key 변경을 별도의 고위험 변경으로 관리해야 합니다.

## 9. 로컬 실습 절차

### 9.1 이벤트 계약 파일 작성

프로젝트에 이벤트 계약 초안을 파일로 저장합니다.

~~~text
contracts/
├── cdc-event-v1.json
├── order-change-v1.avsc
└── validation-rules.md
~~~

JSON 계약은 실습에서 읽기 쉽게 작성하고, Avro 계약은 운영 전환을 검토할 때 비교 대상으로 사용합니다. 계약 파일에는 필드 설명, 필수 여부, 허용 값, 버전, 변경 이력을 기록합니다.

### 9.2 정상 이벤트 생산

Kafka의 정상 토픽에 키와 이벤트를 생산합니다.

~~~text
키: order_123
값: {"schema_version":1,"operation":"INSERT","after":{"id":123,"status":"PENDING"}}

키: order_123
값: {"schema_version":1,"operation":"UPDATE","after":{"id":123,"status":"CONFIRMED"}}
~~~

Consumer에서 key, partition, offset을 함께 출력해 같은 주문 이벤트가 같은 파티션에 기록되었는지 확인합니다.

### 9.3 실패 이벤트 생산

다음과 같은 오류를 의도적으로 발생시킵니다.

- 필수 id 누락
- 잘못된 이메일 형식
- quantity가 0 또는 음수
- 허용되지 않은 status
- 미래의 created_at
- DELETE이지만 key와 before.id가 모두 없음
- 알 수 없는 schema_version

정상 토픽에는 유효 이벤트만 남고, 실패 이벤트는 오류 코드와 원본 위치를 포함해 DLT로 이동해야 합니다.

### 9.4 재처리 확인

DLT의 오류 원인을 수정한 뒤 별도의 DLT 소비자 그룹으로 재처리합니다.

~~~bash
docker exec kafka kafka-consumer-groups \
  --bootstrap-server localhost:9092 \
  --group cdc-dlq-replay-group \
  --topic mysql-orders-cdc-dlq \
  --reset-offsets \
  --to-earliest \
  --execute
~~~

재처리 이벤트를 정상 토픽에 다시 기록할 때는 원본 event_id, replay_count, replayed_at을 보존합니다. 동일 이벤트가 정상 토픽에 중복 기록될 수 있으므로 downstream upsert와 중복 제거 결과를 확인합니다.

### 9.5 검증 체크리스트

- 이벤트 key가 존재하는가?
- source_db와 source_entity가 계약과 일치하는가?
- operation 값이 허용된 집합에 속하는가?
- INSERT·UPDATE·DELETE별 before·after 규칙을 만족하는가?
- schema_version을 해석할 수 있는가?
- event_time이 유효한가?
- 같은 업무 key의 이벤트가 같은 파티션으로 갔는가?
- 오류 이벤트에 원본 topic·partition·offset이 남아 있는가?
- DLT 재처리 후 정상 sink 결과가 중복되지 않는가?
- 처리 결과와 Kafka offset·Flink checkpoint를 함께 확인했는가?

## 장 요약

이벤트 계약은 CDC 데이터의 구조뿐 아니라 생산자와 소비자가 지켜야 할 의미의 약속입니다. Debezium 스타일 envelope은 before, after, source, operation, timestamp, transaction metadata를 사용해 변경의 내용을 표현할 수 있지만, 실제 Flink CDC 출력은 connector와 format에 따라 검증해야 합니다.

Kafka key는 엔터티 식별과 파티션 선택에 사용됩니다. 주문 상태처럼 순서가 중요한 이벤트는 order_id를 key로 사용해 같은 파티션으로 보내는 설계를 검토합니다. Kafka는 파티션 단위 순서만 보장하므로 다중 파티션 토픽의 전역 순서를 자동으로 제공하지 않습니다.

스키마 버전은 이벤트 payload의 구조 변경을 추적합니다. 새 nullable 필드와 기본값이 있는 필드 추가는 비교적 안전하지만, key 변경·자료형 축소·필수 필드 추가는 높은 위험을 가집니다. Apache Avro는 스키마 기반 직렬화와 호환성 검토에 사용할 수 있고, JSON은 로컬 실습과 디버깅에 적합합니다.

중복 이벤트는 checkpoint 복원, offset 커밋 실패, 네트워크 재시도, 리밸런싱, 초기 스냅샷 반복으로 발생할 수 있습니다. event_id, 기본 키 upsert, 버전 비교, operation별 처리로 멱등성을 설계해야 합니다. exactly-once 설정도 최종 sink까지의 상태 일치를 별도로 확인해야 합니다.

Dead Letter Topic은 반복 실패 이벤트를 정상 경로에서 격리하는 장치입니다. DLT에는 원본 이벤트, 오류 코드, 원본 위치, 재시도 횟수를 남기고, 수정 후 재처리 절차와 중복 방지 기준을 함께 관리해야 합니다.

데이터 품질 검증은 NULL, 타입, 범위, 형식, 참조 무결성, 업무 규칙, 시간, 스키마를 대상으로 수행합니다. 검증 결과는 정상 토픽, 재시도 대기, DLT로 분리할 수 있습니다. 이제 다음 장에서는 Kafka와 스트리밍 처리 결과를 Apache Iceberg 또는 분석 저장소로 적재하는 구조를 다루게 됩니다.

- Flink CDC 3.6.0의 실제 connector별 이벤트 envelope과 필드명이 확정되지 않았습니다.
- Debezium 스타일 envelope과 Flink CDC Table API changelog의 정확한 대응 관계 확인이 필요합니다.
- 세 소스의 event_id 생성과 중복 판별 기준이 필요합니다.
- MongoDB의 업무 key와 _id 중 최종 Kafka key로 사용할 값이 확정되지 않았습니다.
- 복합 Kafka key의 serializer와 정규화 규칙이 확정되지 않았습니다.
- Apache Avro 1.12.2의 공식 호환성 규칙과 Apache-only 스키마 배포 방식을 보강해야 합니다.
- Flink Kafka Sink의 exactly-once, transactional.id, read_committed 최종 설정 확인이 필요합니다.
- Flink CDC changelog를 SQL에서 operation별로 검증하고 DLT로 라우팅하는 최종 구문이 필요합니다.
- Flink 버전별 Side Output과 Kafka DLT Sink 구현 예제가 필요합니다.
- Event Time, watermark, allowed lateness의 소스별 기준값이 없습니다.
- DLT 이벤트 보존 기간, 재시도 횟수, replay_count 처리 정책이 확정되지 않았습니다.
- Apache Iceberg·ClickHouse sink에서 중복·UPDATE·DELETE·tombstone을 처리하는 구체적인 구현이 필요합니다.

# 16장. 세 데이터베이스를 통합한 종합 파이프라인과 운영

앞 장까지는 데이터 플랫폼의 각 구성 요소를 개별적으로 다루었다. MySQL·MongoDB·PostgreSQL은 원천 데이터를 저장하고, Kafka는 변경 이벤트를 전달하며, Flink CDC는 변경을 수집한다. Iceberg와 Polaris는 레이크하우스 테이블을 관리하고, Spark는 변환과 유지보수를 수행한다. ClickHouse는 대시보드용 Serving 계층을 제공하며, Airflow와 Superset은 각각 작업 오케스트레이션과 사용자 시각화를 담당한다.

실제 플랫폼에서는 이 구성 요소들이 따로 존재하지 않는다. 세 원천 데이터베이스의 서로 다른 변경 이벤트를 하나의 데이터 모델로 정규화하고, Raw·Clean·Mart 계층을 거쳐 ClickHouse와 Superset에 전달해야 한다. 또한 처리 결과가 정확한지, 얼마나 늦게 반영되는지, 메타데이터와 저장 비용이 증가하고 있지 않은지를 계속 확인해야 한다.

이 장에서는 처음부터 끝까지 이어지는 통합 파이프라인을 구성한다. 핵심은 특정 제품의 명령을 나열하는 것이 아니라 각 단계의 책임과 검증 경계를 분리하는 것이다. 예제는 로컬 Docker Compose 환경에서 학습할 수 있는 골격으로 제시하며, 운영 환경에 필요한 인증·고가용성·백업·보안은 별도 설계 대상으로 표시한다.

- Clean은 중복 제거와 정합성 규칙을 적용한다.
- Mart는 소비 목적에 맞는 집계와 Serving 구조를 제공한다.
- 각 계층 사이에 건수·합계·최신 시각·지연 시간 검증을 둔다.
- 처리 성공과 데이터 품질 통과를 같은 상태로 취급하지 않는다.

## 1. 종합 파이프라인의 전체 구조

### 1.1 구성 요소의 책임

종합 파이프라인은 다음과 같은 단계로 나눈다.

| 단계 | 구성 요소 | 책임 |
|---|---|---|
| Source | MySQL·MongoDB·PostgreSQL | 업무 데이터 생성·수정·삭제 |
| Capture | Flink CDC Connector | Source 변경 이벤트 읽기 |
| Buffer | Kafka | 이벤트 순서·보관·재처리 경계 |
| Stream Processing | Flink | 정규화·필터·통합 |
| Lakehouse | Iceberg·Polaris·Ozone | 테이블·Snapshot·파일 저장 |
| Batch Processing | Spark | 변환·집계·백필·유지보수 |
| Serving | ClickHouse | 대시보드용 조회 모델 |
| Orchestration | Airflow | 제출 순서·재시도·백필·검증 |
| Visualization | Superset | Dataset·Chart·Dashboard |
| Observability | Prometheus·Grafana·로그 | 상태·지연·자원 관찰 |

Airflow는 Flink와 Spark를 대신해 데이터를 처리하지 않는다. Airflow가 성공했다는 것은 제출한 명령이나 Operator가 성공 상태를 반환했다는 뜻이다. Iceberg에 기대한 Snapshot이 생겼는지, ClickHouse에 중복이 없는지, Superset의 지표가 최신인지 확인하는 별도의 검증이 필요하다.

### 1.3 데이터와 메타데이터의 경계

파이프라인을 운영할 때 데이터와 메타데이터를 같은 것으로 취급하지 않는다.

| 구분 | 예 |
|---|---|
| 업무 데이터 | 고객 이메일, 주문 금액, 주문 상태 |
| CDC 메타데이터 | Source 이름, Operation, Event time, Source position |
| Iceberg 메타데이터 | Schema, Partition, Snapshot, Manifest |
| 오케스트레이션 메타데이터 | DAG Run, Task 상태, Retry 횟수 |
| 관측 메타데이터 | 처리량, 지연 시간, 오류 수, 메모리 사용량 |

CDC 이벤트의 Source position이나 Iceberg Snapshot ID를 보존하면 장애가 발생했을 때 어느 시점까지 반영되었는지 추적하기 쉬워진다. 반대로 모든 메타데이터를 생략하고 최종 업무 컬럼만 저장하면 중복·누락·지연 원인을 분석하기 어려워진다.

## 2. CDC Fan-in 설계

### 2.1 Fan-in이 필요한 이유

세 데이터베이스는 같은 고객을 저장하더라도 컬럼명과 타입이 다를 수 있다. MySQL은 customer_email과 DATETIME을 사용하고, PostgreSQL은 email_address와 TIMESTAMP를 사용하며, MongoDB는 usr_email과 BSON Date 또는 문자열을 사용할 수 있다.

이벤트를 그대로 하나의 테이블에 합치면 downstream 단계마다 소스별 분기 로직이 반복된다. Flink 단계에서 Canonical Schema로 변환하면 Clean과 Mart는 통합된 스키마를 기준으로 처리할 수 있다.

### 2.2 소스별 CDC 이벤트

개념적으로 CDC 이벤트는 업무 컬럼과 변경 메타데이터를 함께 가진다.

~~~json
{
  "source_db": "mysql",
  "source_table": "customers",
  "operation": "UPDATE",
  "source_key": "1001",
  "event_time": "2026-08-30T09:00:00Z",
  "source_position": "opaque-source-position",
  "payload": {
    "customer_email": "alice@example.com",
    "creation_date": "2026-08-01T10:00:00Z"
  }
}
~~~

이 구조는 설명을 위한 공통 envelope다. 실제 Flink CDC Connector가 제공하는 메시지 형식, UPDATE의 before·after 표현, DELETE 표현, Source position의 타입은 Connector와 버전에 따라 달라질 수 있다.

[검토 필요: Flink CDC 3.6.0에서 MySQL·MongoDB·PostgreSQL Connector가 반환하는 실제 Changelog RowKind, 메타데이터 컬럼, DELETE 표현과 시간대 처리 방식을 각 Connector별로 확인해야 합니다.]

### 2.3 Canonical Schema

이 장의 고객 예제는 다음과 같은 Canonical Schema를 사용한다.

| Canonical 컬럼 | MySQL 예 | PostgreSQL 예 | MongoDB 예 | 변환 규칙 |
|---|---|---|---|---|
| customer_id | id | id | id 또는 _id | 문자열로 승격 |
| email | customer_email | email_address | usr_email | email로 통일 |
| created_time | creation_date | created_at | creation_date | UTC Timestamp로 변환 |
| source_db | 고정값 mysql | 고정값 postgres | 고정값 mongodb | 이벤트 출처 기록 |
| operation | CDC RowKind | CDC RowKind | CDC RowKind | INSERT·UPDATE·DELETE |
| event_time | Source timestamp | Source timestamp | Event timestamp | 기준 시각 명시 |
| source_position | binlog 위치 | WAL 위치 | oplog 위치 | 문자열 또는 원본 타입 보존 |

Canonical Schema를 설계할 때는 단순히 컬럼명을 맞추는 것보다 의미를 먼저 맞춘다. created_time이 업무 생성 시각인지 이벤트 수집 시각인지 분명히 하고, 두 값을 모두 사용해야 한다면 ingest_time과 분리한다.

### 2.4 타입·시간대·NULL 규칙

| 항목 | 권장 규칙 |
|---|---|
| 식별자 | DB 간 호환을 위해 문자열 표현을 고려 |
| 시간 | 저장 기준 시간대와 표시 시간대를 분리 |
| 숫자 | 금액은 부동소수점보다 정확한 Decimal 규칙을 검토 |
| NULL | NULL과 빈 문자열을 동일하게 취급할지 결정 |
| 삭제 | 삭제 이벤트를 무시하지 말고 operation과 키를 보존 |
| 소스 | source_db와 source_table을 함께 저장 |

시간대를 UTC로 통일할 경우 변환 전 원본 시간대가 무엇인지 기록한다. 소스가 시간대 정보를 제공하지 않으면 단순히 UTC라고 선언해서는 안 된다.

### 2.5 Flink SQL Fan-in 골격

다음 코드는 소스별 스키마를 통일한 뒤 통합하는 개념적 골격이다. 실제 CDC Connector의 옵션과 Changelog 처리 방식은 버전별 검증이 필요하다.

~~~sql
CREATE TABLE mysql_customers (
    id BIGINT,
    customer_email STRING,
    creation_date TIMESTAMP(3),
    operation STRING,
    event_time TIMESTAMP(3),
    source_position STRING
) WITH (
    'connector' = 'mysql-cdc',
    'hostname' = 'mysql',
    'port' = '3306',
    'username' = 'cdc_user',
    'password' = 'change-this-password',
    'database-name' = 'ecommerce',
    'table-name' = 'customers'
);

CREATE TABLE postgres_customers (
    id BIGINT,
    email_address STRING,
    created_at TIMESTAMP(3),
    operation STRING,
    event_time TIMESTAMP(3),
    source_position STRING
) WITH (
    'connector' = 'postgres-cdc',
    'hostname' = 'postgres',
    'port' = '5432',
    'username' = 'cdc_user',
    'password' = 'change-this-password',
    'database-name' = 'ecommerce',
    'schema-name' = 'public',
    'table-name' = 'customers'
);

CREATE TABLE unified_customers (
    customer_id STRING,
    email STRING,
    created_time TIMESTAMP(3),
    source_db STRING,
    operation STRING,
    event_time TIMESTAMP(3),
    source_position STRING
) WITH (
    'connector' = 'iceberg',
    'catalog-type' = 'rest',
    'uri' = 'http://polaris:8181/api/catalog',
    'warehouse' = 'ozone_catalog'
);

INSERT INTO unified_customers
SELECT
    CAST(id AS STRING),
    customer_email,
    creation_date,
    'mysql',
    operation,
    event_time,
    source_position
FROM mysql_customers
UNION ALL
SELECT
    CAST(id AS STRING),
    email_address,
    created_at,
    'postgres',
    operation,
    event_time,
    source_position
FROM postgres_customers;
~~~

MongoDB를 같은 문장에 추가할 때는 MongoDB Connector가 제공하는 컬럼 구조와 DELETE 표현을 먼저 확인한다. UPDATE·DELETE를 가진 여러 CDC Source를 단순 UNION ALL로 append하면 최종 상태가 아니라 이벤트 이력만 저장될 수 있다. Raw 이벤트 저장과 Clean 최종 상태 반영은 분리해서 설계한다.

[검토 필요: 위 Flink SQL을 실행 가능한 완성 예제로 출판하려면 MongoDB Source 정의, Flink CDC 3.6.0의 changelog-to-Iceberg sink semantics, primary key·upsert mode, checkpoint와 exactly-once 보장 조건을 보강해야 합니다.]

## 3. Iceberg Raw·Clean·Mart 계층

### 3.1 계층의 목적

Medallion Architecture에서는 데이터를 Raw·Clean·Mart 같은 품질 계층으로 나눈다. 이 장에서는 이를 Iceberg 테이블로 구현한다.

| 계층 | 다른 표현 | 목적 | 주요 소비자 |
|---|---|---|---|
| Raw | Bronze | 원본 이벤트와 재처리 근거 보존 | 재처리·감사·Replay |
| Clean | Silver | 정규화·중복 제거·삭제 반영 | 분석·데이터 과학 |
| Mart | Gold | 업무 규칙과 집계 적용 | ClickHouse·BI·ML |

계층을 나누었다고 품질이 자동으로 좋아지는 것은 아니다. 각 계층의 Schema, 파티션, 변경 정책, 보존 기간, 검증 기준을 문서화해야 한다.

### 3.2 Raw 설계

Raw는 원천 이벤트를 가능한 한 손실 없이 보존한다. 업무 컬럼 외에 다음 메타데이터를 둔다.

- source_db
- source_table
- operation
- event_time
- ingest_time
- source_position
- schema_version
- raw_payload 또는 원본 필드

Raw를 append-only로 저장하면 이벤트 순서를 재생해 Clean을 다시 만들 수 있다. 다만 Flink CDC 이벤트가 UPDATE·DELETE를 포함하는 경우 append-only는 최종 상태 테이블이 아니라 변경 이력 테이블이라는 점을 분명히 한다.

### 3.3 Clean 설계

Clean은 Canonical Schema와 데이터 품질 규칙을 적용한다.

- 식별자 타입 통일
- 시간대 변환
- NULL·빈 문자열 정책 적용
- 동일 키의 중복 이벤트 제거
- UPDATE의 최신 상태 반영
- DELETE 이벤트 적용
- 잘못된 레코드의 격리와 오류 사유 기록

Clean에서 최신 상태를 만들 때는 event_time만으로 순서를 정하지 않는다. 동일한 업무 시각을 가진 이벤트가 있을 수 있으므로 Source position, Flink 처리 순서 또는 별도의 sequence 규칙을 함께 고려한다.

### 3.4 Mart 설계

Mart는 소비 목적을 기준으로 grain을 결정한다. 고객별 현재 상태, 소스별 고객 수, 일별 주문 집계는 서로 다른 Mart가 될 수 있다.

예를 들어 source_db별 고객 집계는 다음과 같은 grain을 가진다.

~~~text
한 행 = 하나의 source_db에 대한 집계 시점의 고객 지표
키 = source_db
측정값 = total_customers, active_customers
시각 = last_updated
~~~

Mart의 grain을 문서화하지 않으면 Superset에서 SUM을 중복 적용하거나, ClickHouse 재적재 시 같은 기간을 여러 번 더할 수 있다.

### 3.5 Iceberg 테이블 예시

다음 DDL은 계층별 개념을 보여 주는 예시다. PRIMARY KEY의 강제 여부, NOT NULL 처리, Write Mode 속성, 파티션 문법은 사용하는 Iceberg 실행 엔진에서 확인한다.

~~~sql
CREATE TABLE lakehouse.raw.customers_cdc (
    customer_id STRING,
    email STRING,
    created_time TIMESTAMP(3),
    source_db STRING,
    operation STRING,
    event_time TIMESTAMP(3),
    source_position STRING,
    ingest_date DATE,
    ingest_time TIMESTAMP(3)
) USING iceberg
PARTITIONED BY (days(ingest_date));

CREATE TABLE lakehouse.clean.customers (
    customer_id STRING,
    email STRING,
    created_time TIMESTAMP(3),
    source_db STRING,
    updated_time TIMESTAMP(3),
    last_modified TIMESTAMP(3)
) USING iceberg
PARTITIONED BY (source_db);

CREATE TABLE lakehouse.mart.customers_by_source (
    source_db STRING,
    total_customers BIGINT,
    active_customers BIGINT,
    avg_customer_lifetime_days DOUBLE,
    last_updated TIMESTAMP(3)
) USING iceberg;
~~~

[검토 필요: 위 DDL의 파티션 표현, 제약조건, MERGE INTO, Write Mode와 Catalog 접속 설정은 Spark·Flink·Trino 중 어느 엔진에서 실행하는지에 따라 달라질 수 있습니다.]

### 3.6 계층 간 흐름

~~~mermaid
flowchart TD
    A["CDC events"] --> B["Raw"]
    B --> C["Deduplicate and normalize"]
    C --> D["Clean"]
    D --> E["Business aggregation"]
    E --> F["Mart"]
    F --> G["ClickHouse Serving"]
~~~

각 단계는 성공 여부와 품질 검증을 분리한다. 예를 들어 Spark 변환이 성공해도 Clean의 NULL 비율이 허용치를 초과하면 Mart로 진행하지 않도록 Quality Gate를 둔다.

## 4. ClickHouse Serving Mart와 Superset

### 4.1 ClickHouse를 Serving 계층으로 사용하기

Iceberg Mart를 모든 Dashboard Chart가 직접 조회하게 만들 수도 있지만, 반복 집계와 사용자 동시 조회가 증가하면 응답 시간과 컴퓨트 비용을 통제하기 어렵다. ClickHouse Serving Mart는 대시보드에 필요한 조회 모델을 별도로 제공한다.

| 대상 | 주된 목적 |
|---|---|
| Iceberg Mart | 표준화된 장기 보존·다중 엔진 분석 |
| ClickHouse Mart | 짧은 응답 시간·대시보드 동시 조회 |
| Superset | 사용자 인터페이스와 시각화 |

ClickHouse를 원본의 유일한 저장소로 취급하지 않고, Iceberg와 ClickHouse 사이의 갱신·재처리·검증 경계를 명확히 둔다.

### 4.2 ClickHouse Mart DDL

~~~sql
CREATE TABLE mart.customers_by_source
(
    source_db String,
    total_customers UInt64,
    active_customers UInt64,
    avg_customer_lifetime_days Float64,
    last_updated DateTime64(3)
)
ENGINE = ReplacingMergeTree(last_updated)
PARTITION BY toYYYYMM(last_updated)
ORDER BY (source_db);
~~~

ReplacingMergeTree를 사용한다고 즉시 중복이 모두 제거되는 것은 아니다. 동일한 ORDER BY 키와 버전 컬럼의 의미, 조회 시점의 merge 상태, FINAL 사용 여부를 함께 설계한다.

### 4.3 Iceberg에서 ClickHouse로 적재

적재 방식은 ClickHouse가 접근할 수 있는 Iceberg·객체 저장소·Catalog 구성에 따라 달라진다. 조사본은 Iceberg 테이블을 ClickHouse의 Iceberg Table Function으로 읽는 예시를 제시한다.

~~~sql
INSERT INTO mart.customers_by_source
SELECT
    source_db,
    total_customers,
    active_customers,
    avg_customer_lifetime_days,
    last_updated
FROM iceberg(
    'object-storage-path-to-iceberg-table',
    'readonly-user',
    'readonly-password',
    'object-storage-endpoint'
);
~~~

위 SQL은 연결 방식의 개념을 보여 주는 예시이며, Ozone S3 Endpoint, Iceberg Metadata 접근 방식, 인증 인자, Table Function 문법은 실제 ClickHouse 버전에서 검증한다.

[검토 필요: ClickHouse 26.6~26.7과 Apache Ozone·Iceberg 1.11.0 조합에서 Iceberg Table Function이 Polaris Catalog와 어떤 방식으로 동작하는지, 객체 저장소 경로와 Credential 전달 방법을 확인해야 합니다.]

### 4.4 Superset Dashboard 모델

Superset에서는 ClickHouse Mart를 Database로 연결하고 테이블을 Dataset으로 등록한다. 종합 Dashboard에는 다음과 같은 Chart를 둘 수 있다.

| Chart | Dataset | Metric·차원 |
|---|---|---|
| Total Customers | mart.customers_by_source | SUM(total_customers) |
| Active Customers by Source | mart.customers_by_source | source_db·SUM(active_customers) |
| Customer Trend | 일별 Mart | event_date·SUM(active_customers) |
| Data Freshness | Mart 상태 Dataset | MAX(last_updated) |

Dashboard의 숫자를 신뢰하려면 Mart의 집계 grain, 갱신 시각, 지연 시간, 필터 조건을 Dashboard 설명에 기록한다.

## 5. 데이터 품질과 정합성 검증

### 5.1 검증은 네 단계로 나눈다

데이터가 Source에서 Serving까지 이동할 때 다음 네 가지 검증을 조합한다.

1. Row Count: 레코드 수가 예상 범위에 있는가?
2. Sum: 금액·수량·집계 합계가 맞는가?
3. Checksum: 선택한 컬럼의 내용이 일치하는가?
4. Freshness: 최신 변경 시각이 목표 시각까지 도달했는가?

Row Count가 같아도 한 행이 빠지고 다른 행이 중복되면 전체 건수는 같을 수 있다. Sum과 Checksum은 보완 검증이며, 어느 것도 모든 데이터 오류를 자동으로 증명하지는 않는다.

### 5.2 Row Count

~~~sql
-- Source
SELECT COUNT(*) AS row_count
FROM customers;

-- Clean
SELECT COUNT(*) AS row_count
FROM lakehouse.clean.customers;

-- Serving
SELECT COUNT(*) AS row_count
FROM mart.customers;
~~~

원천·Clean·Serving의 grain이 다르면 단순 Row Count를 직접 비교하지 않는다. 예를 들어 Source가 고객 한 행이고 Mart가 소스별 집계 한 행이라면 비교 대상은 고객 상세 테이블 또는 집계 기준으로 맞춰야 한다.

### 5.3 Sum과 그룹별 합계

금액이나 수량 컬럼은 NULL 처리와 Decimal 정밀도를 통일한 뒤 비교한다.

~~~sql
SELECT
    source_db,
    SUM(total_amount) AS total_amount
FROM orders
WHERE order_date >= DATE '2026-08-01'
GROUP BY source_db;
~~~

Source와 Target에서 같은 기간·같은 필터·같은 통화를 사용해야 한다. 부동소수점 변환이 포함되면 허용 오차를 사전에 정한다.

### 5.4 Checksum

Checksum은 비교 대상 컬럼을 정렬 가능한 키로 정렬한 뒤 동일한 직렬화 규칙으로 해시를 계산해야 의미가 있다.

~~~text
row_hash = HASH(key || separator || normalized_email || separator || normalized_time)
table_checksum = HASH(concatenate(row_hash ordered by key))
~~~

Source와 Target의 문자열 인코딩, NULL 표현, 시간 포맷, 정렬 순서가 다르면 값이 달라진다. 따라서 Checksum 규칙을 코드와 문서로 고정하고, 대용량 테이블은 전체 또는 표본 검증 중 어느 방식을 사용하는지 기록한다.

[검토 필요: MySQL·PostgreSQL·MongoDB·Iceberg·ClickHouse 사이에서 동일한 Checksum을 계산하는 함수와 직렬화 규칙을 출판용 실행 예제로 만들려면 각 엔진의 함수 호환성을 추가 검증해야 합니다.]

### 5.5 최신 시각

최신 시각은 데이터가 어디까지 반영되었는지 빠르게 판단하는 지표다.

~~~sql
-- Source
SELECT MAX(updated_at) AS source_last_updated
FROM customers;

-- Clean
SELECT MAX(updated_time) AS clean_last_updated
FROM lakehouse.clean.customers;

-- Serving
SELECT MAX(last_updated) AS serving_last_updated
FROM mart.customers;
~~~

updated_at이 업무 데이터의 변경 시각인지, 파이프라인이 처리한 시각인지 구분한다. 두 값이 모두 필요하면 source_updated_at과 processed_at을 별도로 저장한다.

### 5.6 Quality Gate

Airflow 또는 Flink가 다음 단계로 진행하기 전에 검증 결과를 판정한다.

~~~mermaid
flowchart TD
    A["Transform completed"] --> B["Count check"]
    B --> C["Sum check"]
    C --> D["Freshness check"]
    D --> E{"Quality passed?"}
    E -->|yes| F["Publish to next layer"]
    E -->|no| G["Stop and alert"]
~~~

검증 실패를 단순히 경고 로그로 남기고 다음 단계로 진행하면 잘못된 데이터가 ClickHouse와 Dashboard까지 전달될 수 있다. 다만 Source의 지연으로 일시적으로 freshness가 낮은 경우에는 경고와 차단의 기준을 분리한다.

## 6. End-to-End 지연 시간 측정

### 6.1 지연 시간을 하나의 숫자로 보지 않기

실시간 파이프라인의 지연은 한 구간에서만 발생하지 않는다. Source에서 변경이 Commit된 시각부터 Dashboard가 결과를 표시할 때까지 여러 구간으로 나누어 측정한다.

| 구간 | 측정 기준 |
|---|---|
| Source → Kafka | Source 변경 시각과 Kafka 이벤트 수신 시각 |
| Kafka → Flink | Kafka 이벤트 시각과 Flink 처리 시각 |
| Flink → Iceberg | Flink 처리·Checkpoint 시각과 Iceberg Commit 시각 |
| Iceberg → ClickHouse | Iceberg Snapshot 시각과 ClickHouse 적재 시각 |
| ClickHouse → Superset | ClickHouse 쿼리 종료 시각과 Dashboard 갱신 시각 |
| End-to-End | Source Commit 시각과 최종 조회 시각 |

각 시각의 기준 시간대가 다르면 지연 계산이 틀어진다. 모든 시스템의 시계를 UTC로 맞추거나, 측정 시스템에서 시간대와 Clock skew를 함께 기록한다.

### 6.2 파이프라인에 시각 컬럼을 보존하기

~~~sql
CREATE TABLE lakehouse.raw.customers_cdc (
    customer_id STRING,
    email STRING,
    source_db STRING,
    operation STRING,
    source_updated_at TIMESTAMP(3),
    ingest_time TIMESTAMP(3),
    iceberg_commit_time TIMESTAMP(3)
) USING iceberg;
~~~

source_updated_at은 업무 데이터 또는 Source 이벤트의 시각이고, ingest_time은 파이프라인이 이벤트를 수신한 시각이다. iceberg_commit_time은 테이블에 Snapshot이 커밋된 시각을 의미한다. 실제로 어떤 시각을 어느 엔진이 제공하는지는 구현에서 확인한다.

### 6.3 지연 시간 SLO

조사본은 예시 SLO로 Source에서 Kafka까지 1초 미만, Flink에서 Iceberg까지 5초 미만, Iceberg에서 ClickHouse까지 10초 미만, End-to-End 95퍼센타일 30초 미만을 제시한다. 이 값은 일반적인 보장값이 아니라 실습과 설계 검토를 위한 출발점이다.

| 구간 | 조사본 예시 | 적용 방법 |
|---|---:|---|
| Source → Kafka | 1초 미만 | Offset lag 또는 이벤트 시각 |
| Kafka → Flink | 1초 미만 | Consumer lag |
| Flink → Iceberg | 5초 미만 | 처리·Commit 시각 |
| Iceberg → ClickHouse | 10초 미만 | 적재 시작·완료 시각 |
| End-to-End | 95퍼센타일 30초 미만 | Source → Dashboard |

[검토 필요: 각 SLO는 하드웨어·이벤트 크기·파티션 수·배치 주기·네트워크 조건에 따라 달라지므로, 본문에서는 권장 기본값으로 단정하지 말고 로컬 실험으로 기준선을 측정해야 합니다.]

### 6.4 지연 구간 판별

End-to-End 지연만 증가하면 어느 계층이 원인인지 알 수 없다. 각 구간의 지연을 별도 Metric으로 노출하고 다음과 같이 판단한다.

| 관찰 결과 | 우선 점검 대상 |
|---|---|
| Source→Kafka만 증가 | Source 로그·CDC Connector·Kafka Producer |
| Kafka lag만 증가 | Topic partition·Consumer·Flink 입력 처리량 |
| Flink 처리 시간 증가 | TaskManager·Checkpoint·Backpressure |
| Iceberg commit 지연 | Catalog·객체 저장소·작은 파일·동시 commit |
| ClickHouse 적재 지연 | INSERT·Merge·네트워크·메모리 |
| Dashboard만 지연 | Superset SQL·캐시·Chart 수·ClickHouse 쿼리 |

## 7. Iceberg 메타데이터와 테이블 건강도

### 7.1 메타데이터 트리

Iceberg 테이블은 Catalog의 현재 메타데이터 포인터에서 Snapshot, Manifest List, Manifest, Data File로 이어지는 구조를 가진다. 쿼리 엔진은 이 메타데이터를 이용해 읽을 파일을 선택한다.

~~~mermaid
flowchart TD
    A["Catalog pointer"] --> B["metadata.json"]
    B --> C["Snapshot"]
    C --> D["Manifest List"]
    D --> E["Manifest"]
    E --> F["Data File"]
~~~

메타데이터가 불필요하게 증가하면 테이블을 읽기 전에 계획하는 시간이 늘어날 수 있다. 스트리밍 쓰기에서 Snapshot과 작은 파일이 빠르게 증가하지 않는지 정기적으로 관찰한다.

### 7.2 유지보수 작업

| 작업 | 목적 | 주의점 |
|---|---|---|
| Compaction | 작은 Data File 병합 | 동시 쓰기·리소스 경합 |
| Manifest rewrite | 작은 Manifest 정리 | 엔진별 프로시저 |
| Snapshot expiration | 오래된 Snapshot 정리 | Reader·Time Travel 보존 |
| Orphan cleanup | 참조되지 않는 파일 정리 | 너무 이른 삭제 위험 |

Airflow 14장의 유지보수 DAG와 연결할 때는 Compaction, Manifest rewrite, Snapshot expiration, Orphan cleanup의 순서와 보존 기간을 명시한다. Orphan cleanup을 실행하기 전에 모든 Reader와 동시 쓰기 작업이 참조 파일을 더 이상 사용하지 않는지 확인한다.

### 7.3 건강도 지표

조사본은 평균 파일 크기, 작은 파일 비율, Snapshot 수, Manifest 수, Orphan file 비율을 주요 지표로 제시한다. 다음 값은 책에서 사용하는 관찰 기준의 예시이며 모든 환경에 적용되는 표준 임계치는 아니다.

| 지표 | 양호 예시 | 경고 예시 | 위험 예시 |
|---|---:|---:|---:|
| 평균 파일 크기 | 128~512MB | 32~128MB | 32MB 미만 |
| 10MB 미만 파일 비율 | 5% 미만 | 5~20% | 20% 초과 |
| Snapshot 수 | 1,000 미만 | 1,000~10,000 | 10,000 초과 |
| Manifest 수 | 100 미만 | 100~500 | 500 초과 |
| Orphan file 비율 | 1% 미만 | 1~5% | 5% 초과 |

[검토 필요: 파일 크기·Snapshot·Manifest 임계치는 데이터 크기, 쓰기 빈도, Reader 보존 정책에 따라 달라집니다. 운영 기준으로 사용하려면 실제 workload의 계획 시간·스캔량·스토리지 비용과 함께 보정해야 합니다.]

### 7.4 메타데이터 조회 예시

Iceberg Metadata Table의 이름과 조회 문법은 실행 엔진에 따라 다를 수 있다. 다음은 의도를 보여 주는 개념적 SQL이다.

~~~sql
SELECT
    COUNT(*) AS file_count,
    AVG(file_size_in_bytes) AS avg_file_bytes,
    MIN(file_size_in_bytes) AS min_file_bytes
FROM lakehouse.raw.orders.files;

SELECT COUNT(*) AS snapshot_count
FROM lakehouse.raw.orders.snapshots;

SELECT COUNT(*) AS manifest_count
FROM lakehouse.raw.orders.manifests;
~~~

[검토 필요: Spark·Trino·Flink에서 Metadata Table을 참조하는 정확한 표기와 컬럼명이 다를 수 있으므로, 이 SQL은 특정 엔진의 확정 실행 예제로 사용하지 말고 기준 엔진에서 검증해야 합니다.]

## 8. Iceberg 쿼리·저장·컴퓨트 비용 최적화

### 8.1 비용 버킷

레이크하우스 비용은 하나의 저장 비용으로 끝나지 않는다.

| 비용 버킷 | 발생 원인 | 줄이는 방법 |
|---|---|---|
| 저장 | Data File·Metadata·Snapshot 보관 | 압축·보존·Orphan cleanup |
| 객체 API | 파일과 Metadata 요청 수 | Compaction·Manifest 정리 |
| 쿼리 컴퓨트 | 스캔 바이트·실행 시간 | 파티션 프루닝·파일 스킵 |
| 유지보수 컴퓨트 | Compaction·Rewrite 비용 | 주기·대상 범위·동시성 조절 |
| Serving | ClickHouse 적재·Merge·복제 | Mart 모델·증분 갱신 |
| 관측 | Metric·로그·보관 기간 | 보존 정책·집계 |

### 8.2 파티션 설계

시간 컬럼과 저카디널리티 차원을 파티션에 사용하는 방식은 조회 범위를 줄이는 데 도움이 될 수 있다. user_id처럼 고유값이 많은 컬럼을 무분별하게 파티션으로 사용하면 파티션과 파일 수가 증가할 수 있다.

파티션은 모든 쿼리를 빠르게 만드는 장치가 아니다. 실제 조회 조건, 쓰기 분포, 파일 크기, 파티션 수를 함께 평가한다.

### 8.3 파일 크기와 Compaction

조사본은 128~512MB를 파일 크기의 예시 범위로 제시한다. 이 범위는 작업 엔진과 데이터 분포에 따라 달라질 수 있다. 파일이 지나치게 작으면 파일 열기·Metadata 요청·계획 비용이 증가할 수 있고, 지나치게 크면 특정 파티션만 읽는 작업에서 불필요한 데이터를 함께 읽을 수 있다.

### 8.4 파일 스킵과 정렬

Iceberg 쿼리 엔진은 파티션 정보와 파일 통계를 사용해 읽지 않아도 되는 파일을 제외할 수 있다. 자주 필터하는 컬럼의 분포를 고려해 쓰기 정렬이나 클러스터링을 검토한다.

Z-Order와 같은 기능은 Iceberg 자체의 공통 표준이라기보다 실행 엔진·배포판별 기능일 수 있다. 본문에서는 엔진별 지원 여부를 확인한 뒤 적용한다.

[검토 필요: Spark 3.5.4·4.1.2, Trino 477, ClickHouse 26.x 조합에서 Sort·Z-Order·통계 수집을 실행하는 정확한 명령과 지원 범위를 각각 확인해야 합니다.]

### 8.5 비용 비교 수치의 취급

조사본에는 10TB 기준으로 여러 서비스의 월간 비용을 비교한 표가 포함되어 있지만, 가격·리전·쿼리량·보존 기간·컴퓨트 크기에 따라 값이 달라진다. 이 책의 로컬 오픈 소스 플랫폼 장에서는 특정 금액을 일반적인 비용으로 제시하지 않는다.

비용 비교가 필요하면 다음 변수를 기록한다.

- 저장 데이터량과 복제본 수
- 파일·Metadata API 호출 수
- 일일 스캔 바이트
- Streaming·Batch 처리 시간
- Compaction 실행 빈도와 대상 데이터량
- ClickHouse 노드 수와 보존 기간
- 로그·Metric 보관 비용

## 9. Prometheus·Grafana 모니터링

### 9.1 모니터링 원칙

모든 Metric을 수집한다고 운영이 좋아지는 것은 아니다. 각 구성 요소에서 장애를 발견하고 원인을 좁힐 수 있는 핵심 지표를 선택한다.

| 계층 | 최소 관찰 항목 |
|---|---|
| Source·CDC | 변경량·Connector 오류·Source position |
| Kafka | Consumer lag·Broker 상태·Topic 처리량 |
| Flink | 처리량·Backpressure·Checkpoint·Heap |
| Iceberg | 파일 수·Snapshot·Manifest·Commit 오류 |
| Spark | Job 성공·실행 시간·Shuffle·Executor 메모리 |
| ClickHouse | Query·Memory·Part·Replica delay |
| Airflow | DAG·Task 실패·Scheduler heartbeat·실행 시간 |
| Superset | Query 오류·응답 시간·캐시 hit·Dashboard 실패 |

### 9.2 Prometheus와 Grafana 관계

Prometheus는 Metric을 수집하고 시계열로 저장하며, Grafana는 이를 대시보드로 표현하는 구성으로 사용한다. 각 제품의 Prometheus Exporter나 Endpoint를 연결하는 구체적인 방식은 제품 버전과 배포 형태를 따른다.

~~~mermaid
flowchart LR
    A["Flink"] --> P["Prometheus"]
    B["ClickHouse"] --> P
    C["Airflow"] --> P
    D["Superset"] --> P
    P --> G["Grafana"]
~~~

### 9.3 Flink 핵심 지표

조사본은 처리량, Checkpoint 시간과 성공 여부, JVM Heap 사용량을 핵심 예로 제시한다.

| 지표 범주 | 의미 | 이상 징후 |
|---|---|---|
| Records in/out | 입력·출력 처리량 | 기준선 대비 급락 |
| Consumer lag | Kafka 미처리 이벤트 | 지속적인 증가 |
| Checkpoint duration | Checkpoint 완료 시간 | timeout 또는 급증 |
| Backpressure | downstream 정체 | 높은 상태 지속 |
| JVM Heap | 메모리 사용량 | 상한 근접 |

정확한 Metric 이름은 Flink Reporter와 배포판에 따라 달라질 수 있다. 이름을 원고에 고정하기보다 실제 Endpoint에서 Metric 목록을 확인하는 절차를 함께 둔다.

### 9.4 ClickHouse 핵심 지표

| 지표 범주 | 의미 | 이상 징후 |
|---|---|---|
| Query count·duration | 쿼리량과 시간 | 특정 Dashboard 급증 |
| Memory tracking | 쿼리·서버 메모리 | 메모리 제한 근접 |
| Active parts | 파티션의 활성 Part | 작은 Part 지속 증가 |
| Replica delay | 복제 지연 | 지연 누적 |
| Error events | 쿼리·서버 오류 | 오류율 증가 |

ClickHouse는 Prometheus Endpoint와 System Table을 함께 사용해 서버 상태와 쿼리 원인을 확인한다 (출처: [ClickHouse Self-managed Monitoring](https://clickhouse.com/docs/guides/use-cases/observability/self-managed-monitoring)).

### 9.5 Airflow·Superset 핵심 지표

Airflow에서는 DAG Run duration, Task duration, 실패 Task 수, Scheduler heartbeat를 관찰한다. Superset에서는 쿼리 오류, Dashboard 응답 시간, 캐시 hit·eviction, 비동기 쿼리 상태를 관찰한다.

[검토 필요: Airflow 3.3.0과 Superset 6.1.0의 Prometheus·StatsD 설정명, Metric 이름, Label 구조는 현재 배포 이미지에서 확인해야 합니다. 조사본에 포함된 airflow.cfg와 superset_config.py 예시를 그대로 표준 설정으로 단정하지 않습니다.]

## 10. 로깅·알림·장애 대응

### 10.1 로그를 단계별로 연결하기

Metric은 이상 현상을 알려 주고, 로그는 원인을 설명한다. 각 단계에서 최소한 다음 식별자를 로그에 남긴다.

- pipeline_run_id
- source_db
- source_table
- topic 또는 partition
- Flink job_id
- Iceberg table
- Iceberg snapshot_id
- ClickHouse query_id
- Airflow dag_id와 task_id
- Superset dashboard 또는 chart 식별자

식별자를 공통으로 기록하면 Source의 특정 변경이 어느 Kafka 이벤트와 Iceberg Snapshot을 거쳐 ClickHouse Query에 도달했는지 추적하기 쉬워진다.

### 10.2 중앙 로그

조사본은 Flink·Spark·ClickHouse·Airflow·Superset의 로그를 중앙 저장소에 보관하는 구성을 제시한다. 로컬에서는 Docker 로그를 사용하고, 운영에서는 중앙 로그 수집 시스템과 보존 기간을 별도로 정한다.

| 구성 요소 | 확인할 로그 |
|---|---|
| Flink | JobManager·TaskManager·Checkpoint·Connector 오류 |
| Spark | Driver·Executor·Shuffle·Commit 오류 |
| ClickHouse | Query log·Error log·Merge·Replica 오류 |
| Airflow | DAG parsing·Task retry·Operator·Scheduler 로그 |
| Superset | SQL 실행·권한·Dashboard·Cache 로그 |

[검토 필요: 각 제품의 로그를 Ozone나 S3 호환 저장소에 직접 아카이브하는 구체적인 설정은 제품별 문서와 실제 배포 환경에서 확인해야 합니다.]

### 10.3 알림의 우선순위

모든 경고를 동일한 채널로 보내면 중요한 장애가 묻힌다. 사용자 영향과 데이터 유실 위험에 따라 우선순위를 정한다.

| 우선순위 | 예 | 대응 |
|---|---|---|
| Critical | CDC 중단, 데이터 삭제 위험, Catalog 접근 불가 | 즉시 파이프라인 정지·담당자 호출 |
| High | Consumer lag 지속 증가, Quality Gate 실패 | 담당자 확인·재처리 계획 |
| Medium | Dashboard 지연, Cache hit 저하 | 업무 시간 내 점검 |
| Low | 파일 크기 경고, 장기 추세 변화 | 정기 유지보수 |

조사본은 Prometheus Alertmanager를 Slack·PagerDuty·이메일과 연결하는 구성을 제시한다. 실제 알림 채널과 보안 정책은 조직 환경에 맞게 정한다.

### 10.4 알림 조건의 예

다음은 고정된 제품 Metric 이름이 아니라 알림을 설계하는 기준이다.

- Kafka Consumer lag이 기준선보다 일정 시간 이상 증가
- Flink Checkpoint가 연속 실패
- Iceberg Commit 실패가 반복
- 작은 Data File 비율이 경고 기준을 초과
- ClickHouse Query 오류율 또는 메모리 사용량 증가
- Airflow DAG Run이 SLA를 초과하거나 Task가 반복 실패
- Superset Dashboard Query가 timeout
- Quality Gate의 Count·Sum·Freshness 검증 실패

정적 임계값만 사용하면 트래픽이 적은 시간대의 정상 변동을 장애로 오인할 수 있다. 업무 시간, 배치 주기, 기준선과 함께 판단한다.

## 11. Airflow 백필과 재처리

### 11.1 백필이 필요한 상황

백필은 과거의 특정 기간을 다시 처리하는 작업이다. 다음 상황에서 필요할 수 있다.

- CDC Connector가 일정 시간 중단됨
- 변환 로직의 오류를 수정함
- Iceberg Clean 또는 Mart의 특정 파티션이 손상됨
- ClickHouse 적재가 누락됨
- 데이터 품질 검증에 실패한 기간이 있음

백필을 실행하기 전에 Raw 이벤트와 Source position이 보존되어 있는지 확인한다. Raw가 없으면 과거 상태를 Source에서 다시 읽어야 하고, 그 과정에서 현재 상태만 가져와 변경 이력을 복원하지 못할 수 있다.

### 11.2 멱등성

Airflow의 재시도와 백필은 동일한 논리 날짜나 파티션을 여러 번 실행할 수 있다. 따라서 결과가 중복되지 않도록 처리 자체를 멱등적으로 설계한다.

| 대상 | 멱등성 패턴 |
|---|---|
| Raw 이벤트 | Source position 또는 Event ID 기반 중복 제거 |
| Clean 상태 | 키 기준 MERGE 또는 대상 파티션 교체 |
| Mart 집계 | 대상 기간 삭제 후 INSERT 또는 교체 |
| ClickHouse | 동일 키·버전 규칙, 중복 방지 적재 |
| 파일 산출물 | 임시 경로 작성 후 성공 시 교체 |

Airflow의 max_active_runs를 1로 설정하면 같은 DAG의 동시 실행을 제한할 수 있지만, 이것만으로 중복 처리가 사라지지는 않는다.

### 11.3 Airflow DAG 골격

다음 코드는 실제 실행 엔진의 세부 구현을 분리한 백필 DAG의 골격이다. Spark·Flink·ClickHouse Provider의 설치와 인자는 사용하는 버전에서 검증한다.

~~~python
from datetime import datetime, timedelta, timezone

from airflow.sdk import dag
from airflow.providers.standard.operators.bash import BashOperator


@dag(
    dag_id="comprehensive_pipeline_backfill",
    start_date=datetime(2026, 1, 1, tzinfo=timezone.utc),
    schedule=None,
    catchup=False,
    max_active_runs=1,
    dagrun_timeout=timedelta(hours=4),
    tags=["backfill", "idempotent"],
)
def comprehensive_pipeline_backfill():
    rebuild_clean = BashOperator(
        task_id="rebuild_clean_partition",
        bash_command=(
            "/opt/airflow/scripts/rebuild_clean.sh "
            "--logical-date 2026-08-01"
        ),
        retries=2,
        retry_delay=timedelta(minutes=5),
    )

    rebuild_mart = BashOperator(
        task_id="rebuild_mart_partition",
        bash_command=(
            "/opt/airflow/scripts/rebuild_mart.sh "
            "--logical-date 2026-08-01"
        ),
        retries=2,
        retry_delay=timedelta(minutes=5),
    )

    verify = BashOperator(
        task_id="verify_partition",
        bash_command=(
            "/opt/airflow/scripts/verify_pipeline.sh "
            "--logical-date 2026-08-01"
        ),
    )

    rebuild_clean >> rebuild_mart >> verify


comprehensive_pipeline_backfill()
~~~

실제 백필 날짜를 코드에 고정하지 않고 Airflow의 논리 날짜나 DAG Run 설정으로 전달하려면 현재 Airflow 3.x의 Template Context와 공개 SDK 사용법을 확인한다.

[검토 필요: Airflow 3.3.0에서 백필 날짜를 UI·CLI·Template Context로 전달하는 정확한 방식과, BashOperator에서 외부 엔진의 종료 상태를 안전하게 확인하는 방법을 최종 검증해야 합니다.]

### 11.4 재처리 순서

재처리 순서는 일반 처리와 같은 데이터 의존성을 따른다.

~~~mermaid
flowchart TD
    A["Raw replay"] --> B["Clean rebuild"]
    B --> C["Mart rebuild"]
    C --> D["ClickHouse refresh"]
    D --> E["Quality validation"]
    E --> F["Dashboard release"]
~~~

검증이 실패한 상태에서 Dashboard를 갱신하면 사용자는 잘못된 결과를 보게 된다. 따라서 ClickHouse 적재와 Superset 공개 사이에 Quality Gate를 둔다.

5. Clean 중복·NULL·DELETE 반영 확인
6. Mart 집계 결과 확인
7. ClickHouse 적재 건수와 최신 시각 확인
8. Superset Dashboard 숫자 확인
9. Prometheus와 Grafana에서 지연·오류 확인
10. 동일 논리 날짜 재실행 후 결과 비교
~~~

### 12.6 동일 결과 재실행 실험

멱등성을 확인하려면 동일한 입력과 동일한 논리 날짜를 두 번 처리한다.

| 비교 대상 | 첫 실행 | 두 번째 실행 | 기대 결과 |
|---|---:|---:|---|
| Clean 고객 수 | 기록 | 기록 | 동일 |
| Mart 합계 | 기록 | 기록 | 동일 |
| ClickHouse 행 수 | 기록 | 기록 | 중복 증가 없음 |
| 최신 시각 | 기록 | 기록 | 정책에 맞는 값 |
| Quality Gate | 통과 여부 | 통과 여부 | 동일한 판정 |

결과가 달라졌다면 Airflow 재시도 문제가 아니라 Raw 중복, Clean Merge 규칙, Mart 적재 전략, ClickHouse 테이블 엔진을 함께 점검한다.

## 13. 전체 운영 점검표

### 데이터 흐름

- [ ] 세 Source의 CDC 이벤트가 각각 확인된다.

- [ ] Canonical Schema의 타입·시간대·NULL 규칙이 문서화되어 있다.

- [ ] Snapshot·Manifest·Data File을 확인할 수 있다.
- [ ] 작은 파일과 Snapshot 증가 추세를 관찰한다.
- [ ] Compaction과 Orphan cleanup의 보존 정책이 정의되어 있다.
- [ ] Catalog와 객체 저장소의 권한이 분리되어 있다.

- [ ] Dashboard의 필터가 각 Chart에 의도대로 적용된다.

- [ ] Dashboard 지표의 기준일과 grain이 설명되어 있다.

### 운영

- [ ] Source부터 Dashboard까지 지연 시간을 측정한다.
- [ ] Flink·Spark·ClickHouse·Airflow·Superset 로그를 추적할 수 있다.
- [ ] 핵심 장애에 대한 알림 채널과 담당자가 정의되어 있다.
